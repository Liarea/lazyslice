# Hard problems: subsetting, deterministic masking, PII classification, streaming Postgres

Technical survey for the engineer implementing lazysnap's pipeline in Go. Four problems, each in the same shape: the simplest approach that is actually correct, the refinement that makes it good, and the trap that catches implementers. Every claim links to its source. Tool status was checked on 2026-09-05; "unverified" marks anything I could not confirm from a primary source.

Vocabulary used throughout, because the field does not agree on it:

- **Parent** row: the row a foreign key points at (the referenced side). **Child** row: the row holding the foreign key (the referencing side).
- **Parents to completeness**: every parent of every selected row must be in the subset, or the target rejects the load. Non-negotiable.
- **Children**: optional. This is where subsets explode.
- Tonic calls child tables "upstream" and parent tables "downstream": "Downstream tables have data that is required to maintain referential integrity for the subset. These tables have primary keys that are referenced by foreign keys in related tables", while "Upstream tables contain data that has a foreign key that references a primary key in the target table" ([Tonic: about subsetting](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)); condenser inherits the same words ([condenser README](https://github.com/TonicAI/condenser)). Jailer calls the parent-direction edges "dependencies" and everything else "associations" ([Jailer tutorial](https://wisser.github.io/Jailer/exporting-data.htm)). Read every source with this inversion in mind.

## 1. Subsetting: walking the foreign-key graph

### What the graph looks like in Postgres

Everything is in `pg_constraint`. For `contype = 'f'`: `conrelid` is the child table, `confrelid` the parent, `conkey` and `confkey` are position-aligned `int2[]` arrays of column numbers (a composite key is just an array longer than one), `confmatchtype` is `f` full / `p` partial / `s` simple, `condeferrable` and `condeferred` say whether the constraint can be deferred, `convalidated` says whether the source actually trusts it, and `conparentid` links a partition's constraint to the partitioned parent's ([pg_constraint](https://www.postgresql.org/docs/current/catalog-pg-constraint.html)). "A foreign key must reference columns that either are a primary key or form a unique constraint, or are columns from a non-partial unique index" ([ddl-constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)), so every edge has a unique target you can key on. `MATCH PARTIAL is not yet implemented` ([CREATE TABLE](https://www.postgresql.org/docs/current/sql-createtable.html)), so you will only ever see `f` and `s`.

### 1.1 Simplest correct approach: a monotone worklist

Keep, per table, a set of selected primary keys. Seed the root table's set (500 customers, or a `WHERE`). Then loop:

Every queue entry carries a provenance tag, `CHILD_OK` or `PARENT_ONLY`, and the child step below runs only for `CHILD_OK` entries. This is not a cosmetic detail: it is the whole difference between this algorithm and the closure explosion the rest of this section documents.

```
queue := [(root, rootKeys, CHILD_OK)]
for (t, keys, mode) := pop(queue); keys != nil {
    new := keys − selected[t]; selected[t] ∪= new
    // parents: mandatory, uncapped, any depth. Rows pulled here are tagged
    // PARENT_ONLY: they complete referential integrity but are never
    // themselves a starting point for the child step below.
    for fk := range outgoing(t) {                       // t.(conkey) → parent.(confkey)
        pk := SELECT DISTINCT fk.cols FROM t WHERE t.pk IN new AND <no fk col IS NULL>
        push(parent(fk), pk − selected[parent(fk)], PARENT_ONLY)
    }
    // children: optional, capped per parent key, depth-limited, and run
    // ONLY when mode == CHILD_OK — i.e. only from the root itself or from
    // rows this same loop already reached via a child edge. A row reached
    // only as someone's parent is a leaf for this step: its own children
    // are never pulled in.
    if mode == CHILD_OK {
        for fk := range incoming(t) {                    // child.(conkey) → t.(confkey)
            ck := SELECT child.pk FROM child WHERE fk.cols IN new   (≤ cap per parent key)
            push(child(fk), ck − selected[child(fk)], CHILD_OK)
        }
    }
}
```

A row's mode is decided once, the first time it is pushed: `selected[t]` still holds one set of keys per table, not one per mode, so a row first reached as a parent is never re-expanded as a child even if a later step would also have reached it via a child edge — it stays `PARENT_ONLY` for the life of the run. That is the deliberate size control, not an oversight; if a future version wants "a row's mode is the most permissive mode it was ever reached under" instead, that is a different, larger algorithm and should be a separate decision, not a silent upgrade.

Every set only grows and every set is finite, so the loop terminates; the parent step guarantees that when it terminates, every selected row's parents are selected. That is the whole correctness argument, and it holds for cycles and self-references without special casing: a self-referencing `employees.manager_id` keeps pushing `employees` (as `PARENT_ONLY`, so a manager's own children are not additionally pulled in through this edge) until the chain of managers is closed. Postgres itself describes the self-referential case as the ordinary one: "Sometimes it is useful for the 'other table' of a foreign key constraint to be the same table; this is called a self-referential foreign key" ([ddl-constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)).

This is the algorithm the field converged on, under different names:

- condenser: "Upstream subsetting happens when a row is imported, and there are rows with foreign keys to that row. The subsetter then greedily grabs as many rows from the database as it can, based on the rows already imported" ([README](https://github.com/TonicAI/condenser)). Its v2 "makes two passes on your database, ordered by a topological sort of the tables": first "greedily includes rows from tables that are upstream of the initial targets", then a second pass "grabs all required keys given the greedily derived database" ([condenser v2 post, 2019-08-13](https://www.tonic.ai/post/condenser-v2/)).
- Tonic Structural: targets seed, then "Step 2" walks upstream (children) and "Step 3" walks downstream (parents) ([Tonic: about subsetting](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)).
- Snaplet: "Subset traverses tables related to the `target` table and selects all the rows that are connected to the `target` table via foreign key relationship", with knobs `followNullableRelations` (default true), `maxCyclesLoop` (default 1), `maxChildrenPerNode` (default `Number.MAX_SAFE_INTEGER`), `eager` (default false) and `traversalMode` ([Snaplet capture docs, mirror](https://snaplet-snapshot.netlify.app/snapshot/core-concepts/capture); durable primary: [snaplet/docs, pages/snapshot/core-concepts/capture.mdx](https://github.com/snaplet/docs/blob/main/pages/snapshot/core-concepts/capture.mdx)).
- Neosync: "When a subset condition (such as a WHERE clause) is specified on a table, Neosync can propagate this condition to related tables through foreign key relationships", "directionally from top down" ([Neosync subsetting doc](https://raw.githubusercontent.com/nucleuscloud/neosync/main/docs/docs/table-constraints/subsetting.md)).
- pg_sample follows FKs to keep integrity and warns that "sample tables may end up with significantly more rows in order to satisfy foreign key constraints" ([pg_sample](https://github.com/mla/pg_sample)).
- Jailer: an extraction model is a subject table plus a condition; "Exporting an employee requires to export his boss and department too. Otherwise the set of exported entities would not be consistent (due to the dependencies based on foreign key constraints)" ([Jailer tutorial](https://wisser.github.io/Jailer/exporting-data.htm)).

**Lookup tables.** Copy them whole rather than walk them. Phil Factor: "tables that are used as enumerations, such as countries, currencies, or part-lists, need to be copied in full because it can easily become impossible to add an entity if a relation doesn't exist in the subset" ([Simple Talk, 2024-04-17](https://www.red-gate.com/simple-talk/databases/theory-and-design/database-subsetting-and-data-extraction/)). Tonic: "A lookup table contains a static set of values that is used in other tables in your subset" and is copied in full ([Tonic](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)); condenser calls them `passthrough_tables`, "Tables that will be copied to destination database in whole" ([README](https://github.com/TonicAI/condenser)). A zero-config heuristic: a table with no outgoing FKs, at least one incoming FK, and few rows (say under 1,000) is a lookup table; copy it whole and say so in the plan.

**Per-parent child caps in one query**, not one query per parent key: `row_number() OVER (PARTITION BY fk_col ORDER BY pk) <= cap` ([window functions](https://www.postgresql.org/docs/current/tutorial-window.html)).

### 1.2 Refinements

**Cycles at load time.** The worklist handles cycles for *selection*; the hard part is *insertion order*. Compute strongly connected components of the table graph (Tarjan's algorithm "runs in linear time", [Wikipedia](https://en.wikipedia.org/wiki/Tarjan%27s_strongly_connected_components_algorithm)), condense to a DAG, and topologically sort it; "A topological ordering is possible if and only if the graph has no directed cycles" ([Wikipedia](https://en.wikipedia.org/wiki/Topological_sorting)). Inside an SCC there are three options:

1. *NULL-then-UPDATE on a nullable FK.* Jailer 6.5: "Referential cycles can now be exported by deferring the insert of nullable foreign keys" ([release notes](https://github.com/Wisser/Jailer/blob/master/releasenotes.txt)); the site still says "Cycles in parent-child relationships will be detected and broken. Thus, such data can be exported by deferring the insertion of nullable foreign keys" ([Jailer](https://wisser.github.io/Jailer/)). Tonic: "Structural identifies a foreign key column that is `NULL`able, and sets its values to `NULL`", with "the minimum number of `NULL` values that are needed to break the circular dependencies", and "If none of the foreign key values are `NULL`able, then the circular dependency cannot be broken, and the subset generation fails" ([Tonic FK docs](https://docs.tonic.ai/app/generation/subsetting/subsetting-foreign-keys)). Neosync required that "at least one table involved in the dependency must have a column that is nullable", inserted with it empty, cycled through the SCC, then came "back to the original starting table, and update in the foreign key reference into the nullable column" ([Neosync circular-dependencies doc](https://raw.githubusercontent.com/nucleuscloud/neosync/main/docs/docs/table-constraints/circular-dependencies.md)). condenser's blog gives the argument for why a nullable edge exists when the cycle holds data at all: "Any cycle of foreign key columns will contain at least one NULLable column, otherwise you wouldn't be able to insert the first row into the cycle" ([Tonic blog, 2018-08-07](https://www.tonic.ai/blog/condenser-a-database-subsetting-tool)). Deferrable constraints are the exception to that argument; see the trap below.
2. *Deferred constraints.* `SET CONSTRAINTS ALL DEFERRED` means "DEFERRED constraints are not checked until transaction commit", but "only `UNIQUE`, `PRIMARY KEY`, `REFERENCES` (foreign key), and `EXCLUDE` constraints are affected", and a constraint declared `NOT DEFERRABLE` "is always `IMMEDIATE` and is not affected by the `SET CONSTRAINTS` command" ([SET CONSTRAINTS](https://www.postgresql.org/docs/current/sql-set-constraints.html)). Because lazysnap owns the target, it can flip an FK: `ALTER TABLE … ALTER CONSTRAINT … DEFERRABLE`; "Currently only foreign key constraints may be altered in this fashion" ([ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)).
3. *Create FKs after the data.* This is what pg_dump does: post-data items are "definitions of indexes, triggers, rules, statistics for indexes, and constraints other than validated check and not-null constraints" ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)); pgcopydb's clone runs COPY, then indexes, then constraints, then sequences, then vacuum, then "Post-data restore - Applies foreign keys and remaining objects" ([pgcopydb clone](https://pgcopydb.readthedocs.io/en/latest/ref/pgcopydb_clone.html)). Because lazysnap creates the target schema, option 3 removes ordering from the load path entirely and turns "verify foreign keys" into "the post-data FK creation succeeded". Section 4 argues for this as the default.

Choosing *which* edges to break with the fewest breaks is the minimum feedback arc set: "Finding minimum feedback arc sets and maximum acyclic subgraphs is NP-hard; it can be solved exactly in exponential time" ([Wikipedia](https://en.wikipedia.org/wiki/Feedback_arc_set)). Schema SCCs have a handful of nodes; brute force or greedy is fine. Do not write a clever algorithm.

Greenmask pushes cycles into SQL instead of the client: "Greenmask will automatically generate the appropriate queries for the table subset using recursive queries. The subset system ensures data consistency by validating all records found through the recursive queries", with the limit "Currently (v0.2b2), Greenmask can resolve multi-cylces in one strogly connected component, but only for one group of vertexes" which "99% of people will not face" ([Greenmask subset docs](https://docs.greenmask.io/latest/database_subset/), tracked in [#197](https://github.com/GreenmaskIO/greenmask/issues/197), open since 2024-09-06). The cost of that design showed up as [#329](https://github.com/GreenmaskIO/greenmask/issues/329), open since 2025-08-13: `getOneCycleGroup()` panics with "get one group cycle group is not allowed for multy cycles" when the graph has *zero* cycles. A 2026 tool went the other way and simply refuses: msg555/subsetter "cannot support calculating a full transitive closure of foreign key relationships for schemas that contain cycles" and requires that "no target is reachable from another target" ([subsetter](https://github.com/msg555/subsetter)). condenser makes the user break cycles by hand with `dependency_breaks`, "An array containing JSON objects with "fk_table" and "target_table" fields of table relationships to be ignored in order to break cycles", because "The subsetting tool cannot operate on databases with cycles in their foreign key relationships" ([README](https://github.com/TonicAI/condenser)). The worklist plus post-data FKs has none of these cliffs.

**Self-references.** The worklist closes an ancestor chain in as many round trips as the chain is deep. To do it in one query use `WITH RECURSIVE`; evaluation iterates "So long as the working table is not empty", and `UNION` (not `UNION ALL`) discards "duplicate rows and rows that duplicate any previous result row", which is what stops cyclic data looping ([WITH queries](https://www.postgresql.org/docs/current/queries-with.html)). PG14 added the SQL-standard `SEARCH` and `CYCLE` clauses ([PG14 notes](https://www.postgresql.org/docs/release/14.0/)); `CYCLE id SET is_cycle USING path` gives you an explicit flag when A manages B manages A, which is legal data when the FK is nullable. Jailer's maintainer diagnosed a runaway unattended export ("Jailer tried to collect data indefinitely") as "a reflexive association of the subject table with itself", pointed at the `$DISTANCE` and `$IS_SUBJECT` restriction variables, and shipped a `-row-limit` safeguard in response ([SourceForge thread, 2019-12-11](https://sourceforge.net/p/jailer/discussion/700499/thread/953062b743/); "'Limit' parameter as a safeguard for exports" in 9.2.1, [release notes](https://github.com/Wisser/Jailer/blob/master/releasenotes.txt)). Copy the idea: a depth limit on child traversal and a hard row budget that aborts planning with a clear message.

**Composite keys.** Treat a key as a tuple, never as a joined string. `conkey`/`confkey` are aligned by position; resolve attnums via `pg_attribute`. For lookups pass parallel arrays: `WHERE (a, b) IN (SELECT * FROM unnest($1::int[], $2::text[]))`; multi-array `unnest` "Expands multiple arrays (possibly of different data types) into a set of rows. If the arrays are not all the same length then the shorter ones are padded with `NULL`s. This form is only allowed in a query's FROM clause" ([array functions](https://www.postgresql.org/docs/current/functions-array.html)). NULL semantics depend on the match type: under the default `MATCH SIMPLE` "a referencing row need not satisfy the foreign key constraint if any of its referencing columns are null", while under `MATCH FULL` "a mix of null and non-null values is guaranteed to fail" ([ddl-constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)). So for `MATCH SIMPLE` a composite FK with one NULL column references nothing: skip it in the parent step, or you will query for a parent that cannot exist.

**Row identity for tables with no primary key.** The worklist above is written entirely in terms of `t.pk`: `selected[t]` is a set of primary keys, `WHERE t.pk IN new` seeds the parent lookup, and the per-parent cap orders by `pk`. Junction tables, append-only log tables, and legacy tables commonly have no primary key and no unique index at all, and the algorithm as stated has no key to accumulate, no key to de-duplicate new rows against, and no stable order for the cap. Jailer's own history shows this is not a corner case for the schemas this class of tool targets: "Support for nullable primary key columns. This simplifies the definition of pseudo-primary keys for tables without keys" ([release notes, 9.2.1](https://github.com/Wisser/Jailer/blob/master/releasenotes.txt)). lazysnap v1's fallback chain, tried in order per table:
1. Declared primary key.
2. Any unique index from `pg_index` where `indisunique` is true, excluding partial and expression indexes (an expression index has no plain column list to key on, and a partial one does not cover every row).
3. An inferred pseudo-key: the table's own FK columns (which are usually NOT NULL and, combined, usually identify a junction-table row) plus any other NOT NULL discriminator columns the plan step can find, tried as a composite unique probe over a sample before being trusted for the whole table.
4. `ctid` as a last resort, with two costs stated up front: `ctid` is not a stable identifier — a physical row can move to a different `ctid` after `VACUUM FULL`, `CLUSTER`, or an `UPDATE`, and the docs already warn it "should be used to identify a specific physical row" (unverified against a direct citation for a broader stability guarantee, so treat it as scoped to a single unmodified snapshot) — so it is only usable in combination with the exported source snapshot below (a `ctid` looked up and a `ctid` extracted must come from the same held snapshot, not two separate queries against a moving table); and `ctid` cannot appear in a target table at all, so a `ctid`-keyed source row is loaded once and never revisited, dropping any incremental re-sync feature that assumes stable keys.

The plan step must print, per table, which of the four it used, and refuse (rather than silently fall through to `ctid`) when a table is large enough that a `ctid`-only key materially changes the size or reproducibility story — the exact threshold is a v1 product decision, not a technical one, so this document does not set it.

**What must be pinned for a run to be reproducible.** `lazysnap.yml` is committed so CI reproduces a run ([CONCEPT.md](../CONCEPT.md)), which is a stronger promise than "the algorithm is deterministic" — it requires every source of variation between two runs against an unchanged database to be pinned in that file or derived from it. Four things vary if left to defaults: (1) the per-parent child cap's tie-break order — `ORDER BY pk` is stable for a real primary key but is exactly the case above where there is no `pk`, so a run keyed on `ctid` or an inferred pseudo-key is not reproducible across a `VACUUM FULL` on the source even with the same config; (2) the masking key (§2), which must be the same key, not just the same algorithm, for two runs to produce the same fakes — it lives outside the yml by design (§2.1), so "reproducible" here means "the same fakes given the same key," and the plan output should say which key fingerprint was used; (3) any embedded generator word list (gofakeit's or lazysnap's own name/word lists), which changes the mapping if the list changes between lazysnap versions even with the same key and the same input, per the gofakeit version-drift trap in §2.3 — pin the lazysnap version, not just the config, for byte-for-byte reproducibility; (4) the source snapshot itself, discussed next — two runs against a live, changing database are reproducing "the subset as of some snapshot," never "the subset," and the plan output should record which snapshot (LSN or export id) a run used.

**Polymorphic associations without constraints.** Rails stores "the name of the associated model's class" in `imageable_type` next to `imageable_id` ([Rails guide](https://guides.rubyonrails.org/association_basics.html)); Django's generic relations use a `content_type` FK plus an `object_id` integer, and "Unlike for the `ForeignKey`, a database index is not automatically created on the `GenericForeignKey`" ([Django docs](https://docs.djangoproject.com/en/stable/ref/contrib/contenttypes/)). No constraint is possible because "a foreign key points at one table, and `notable_id` points at `events` or `orders` or `seats` depending on a string" ([Weaver, 2026-06-25](https://baweaver.com/writing/2026/06/25/rails-sharp-parts-a-polymorphic-type-is-not-a-foreign-key/)). Every tool handles this with user config: condenser's `fk_augmentation` for "foreign keys that are not codified as constraints on the database" ([README](https://github.com/TonicAI/condenser)); Tonic's "virtual foreign keys", including for polymorphic keys ([Tonic FK docs](https://docs.tonic.ai/app/generation/subsetting/subsetting-foreign-keys)); Greenmask's virtual references with `polymorphic_exprs`, which "cannot be non_null because the `commentable_id` column can be `NULL`" ([Greenmask subset docs](https://docs.greenmask.io/latest/database_subset/)), and whose multi-type case is currently broken: "multi-type refs produce ~0 rows" because a bypass guard is missing from the generated predicate ([#396](https://github.com/GreenmaskIO/greenmask/issues/396), open since 2026-02-17); Jailer added "Discover Associations" in August 2026 ([site](https://wisser.github.io/Jailer/)). For a zero-config tool: detect `<x>_type`/`<x>_id` pairs and `content_type_id`/`object_id`, sample distinct `_type` values, map each to a table (a Rails value is a class name: underscore and pluralize; a Django value is a `django_content_type` row), treat each mapping as a virtual FK in the *parent* direction only, and print what you inferred. If a `_type` value maps to nothing, say so: the FK verification at the end cannot catch it because there is no constraint to violate.

**Children of the root versus everything reachable.** These are different products. "Everything reachable" through child edges from 500 customers on a real schema is most of the database: orders pull products, products pull suppliers, and if child edges run from suppliers you get every other order for that supplier. Every vendor documents the same surprise. Snaplet: "the `precent` / `rowLimit` specified in the subset config may not be exact" and "a 5% subset specified against a specific table may ultimately include more than 5% of the actual database" ([Snaplet docs, mirror](https://snaplet-snapshot.netlify.app/snapshot/core-concepts/capture); durable primary: [snaplet/docs, capture.mdx](https://github.com/snaplet/docs/blob/main/pages/snapshot/core-concepts/capture.mdx)). Tonic: "the percentage only applies to the rows in the target table" and, for tables upstream of several targets, "Structural only pulls records from that table that contain references to targeted records in all of the target tables" ([Tonic](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)). condenser's first algorithm followed the graph transitively and "when we target even a small portion (1%) of the starting dataset, we devolved into importing a large portion of the database (50%)" ([Tonic blog](https://www.tonic.ai/blog/condenser-a-database-subsetting-tool)). Jailer's tutorial exports one employee and, without five hand-written restrictions, gets "all employees assigned to the same department as SCOTT" and "all employees who belong to the same salary-grade" ([tutorial](https://wisser.github.io/Jailer/exporting-data.htm)); a user filed exactly that in 2025 as a bug, "Subject condition is violated due to reverse traversal (unexpected rows in subset)": with `T.customer_id = 1` "Orders for customer_id = 2..10 are included", "due to implicit reverse traversal, which is not documented clearly" ([Jailer #126](https://github.com/Wisser/Jailer/issues/126)).

The rule that keeps size predictable: follow child edges only from rows reached by child edges (root → its children → their children), never from rows reached by the parent step. Parents pulled for completeness are leaves for child traversal. Cap children per parent (Snaplet's `maxChildrenPerNode` example: "1 single row being linked to one millions rows in another table. In that case, setting a limit of 1000 will allow the algorithm to fetch only the first 1000 related rows", [Snaplet docs, mirror](https://snaplet-snapshot.netlify.app/snapshot/core-concepts/capture); durable primary: [snaplet/docs, capture.mdx](https://github.com/snaplet/docs/blob/main/pages/snapshot/core-concepts/capture.mdx)), cap depth, and plan before extracting, which is the CONCEPT's "planning… 23 tables in slice, ~18k rows" line.

**SQL pushdown versus a client worklist.** Greenmask does not walk keys in the client; it "genrates queries for subset conditions based on the introspected schema using joins and recursive queries. It cannot be responsible for query optimization" ([Greenmask subset docs](https://docs.greenmask.io/latest/database_subset/)). msg555/subsetter materializes: "Any sampled tables that are referenced by other tables will first be materialized into temporary tables on the source database" ([subsetter](https://github.com/msg555/subsetter)). Pushdown gives one streaming query per table and no key sets in client memory; it costs you explicit caps, explicit explanations, temp tables or big recursive queries on the source, and dependence on the source planner. For a tool that must print "why this row is here" and must "never hold write access to the source", the client worklist wins; keep the key sets as sorted `int64` slices or roaring bitmaps and they are small — worked example: a sorted `int64` slice is 8 bytes per key, so 20 tables × 5,000,000 keys each is 100,000,000 keys × 8 bytes = 800 MB before any per-slice/map overhead, which is already large enough to be the wrong data structure on a typical development machine; a Roaring bitmap over the same keys is far smaller when key values cluster (most auto-increment PKs do), but "small" stops being a safe assumption once any single table's selected-key set is in the tens of millions, which is the point at which lazysnap should say so in the plan rather than silently grow. A conservative rule for v1: sum `len(selected[t])` across all tables after planning and print the estimated resident set (keys × 8 bytes, doubled for map/slice overhead as a rough ceiling); refuse to proceed past a configurable byte budget (a few hundred MB is a reasonable default) without an explicit override, the same way the row budget in §1.3 already gates depth.

**Academic framing.** Join Synopses (Acharya, Gibbons, Poosala, Ramaswamy, SIGMOD 1999, pp. 275–286, [PDF](http://www.cs.emory.edu/~cheung/Courses/584/Syllabus/papers/Frequency-count/join-synopses_tm.pdf), [ACM](https://dl.acm.org/doi/10.1145/304182.304207)) define our invariant for approximate query answering: sample a relation, then include the tuples in other relations that the sampled tuples reference through foreign keys, so any foreign-key join over the synopsis is answerable. Linked Bernoulli Synopses (Gemulla, Rösch, Lehner, SSDBM 2008, [PDF](https://www.uni-mannheim.de/media/Einrichtungen/dws/Files_People/Profs/rgemulla/publications/gemulla08fksampling.pdf)) "rely on the idea of maintaining foreign-key integrity in the synopses" and "correlate the sampling processes of the different tables in the database so as to minimize the space overhead" of those reference tuples ([Springer](https://link.springer.com/chapter/10.1007/978-3-540-69497-7_4)). Bisbal and Grimson, "Database sampling with functional dependencies" (Information and Software Technology 43(10), 2001, pp. 607–615, [Semantic Scholar](https://www.semanticscholar.org/paper/Database-sampling-with-functional-dependencies-Bisbal-Grimson/fb48f430b9e19ad2c7093f622df559ae103f1307), [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0950584901001653)) samples a relation so the sample itself satisfies a given set of functional dependencies (an Armstrong relation) — a narrower claim than "select data by satisfying integrity constraints, referential constraints included." The paper that matches that broader claim is the same authors' later "Consistent database sampling as a database prototyping approach" (Journal of Software Maintenance and Evolution 14(6), 2002, [doi:10.1002/smr.263](https://doi.org/10.1002/smr.263)), which is the prototyping-database line this document actually means to cite. Dscaler (Zhang, Tay, PVLDB 9(14), 2016, [ACM](https://dl.acm.org/doi/10.14778/3007328.3007333), [PDF](http://www.vldb.org/pvldb/vol9/p1671-zhang.pdf)) frames "the Dataset Scaling Problem": given tables D and a scale factor s, generate D' similar to D but s times its size, "useful for application development (s < 1)", and handles tables that scale at different rates. The practical reading for lazysnap: closure inflation is inherent when you sample in the middle of the graph; start at a root with no parents of its own (customers, tenants, accounts) and it stays bounded. Dscaler matters only if v2 wants "representative" rather than "everything about these 500 customers".

### 1.3 Traps

- **The explosion is in child edges from parents.** See above; every vendor's docs and Jailer's forum have the same story. Budget, depth, and a plan step are the difference between a tool that finishes and one that "tried to collect data indefinitely" ([thread](https://sourceforge.net/p/jailer/discussion/700499/thread/953062b743/)).
- **Unindexed FK columns on the source.** The child step is `WHERE fk_col IN (...)` against the child table. Postgres: "the declaration of a foreign key constraint does not automatically create an index on the referencing columns" ([ddl-constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)); Tonic: "For large upstream tables, if the foreign key columns are not indexed, the subsetting process can be significantly slower" ([Tonic](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)). Check `pg_index` during planning and warn per edge.
- **Huge `IN` lists and `= ANY(ARRAY[...])`.** The famous Datadog case (22 s to 0.2 s by switching `ANY(ARRAY[...])` to `ANY(VALUES ...)` for about 11,000 keys) was a PostgreSQL 9.0 planner problem the article itself says was fixed by 9.3 ([Datadog, 2013](https://www.datadoghq.com/blog/100x-faster-postgres-performance-by-changing-1-line/)), so do not cargo-cult it. What is still true: thousands of literal values cost parse and plan time; Pavel Stehule on pgsql-general: "It is not good - it increases the memory necessary for query parsing, optimizer and executor are slower" ([Stehule's message, 2020-08-31](https://www.postgresql.org/message-id/CAFj8pRAWNM5DVeNrDTvUevTEo6Qc8wt6SwkTuKpdk6bkENhXiQ%40mail.gmail.com); Thorsten Schöning's reply quoting it is at [message-id 986190718.20200831123700@am-soft.de](https://postgresql.org/message-id/986190718.20200831123700%40am-soft.de)). PG14 added "hash lookup for `IN` clauses with many constants" ([PG14 notes](https://www.postgresql.org/docs/release/14.0/)), about 10× for 1,000-value lists per pganalyze, who also recommend `= ANY` with a single bound array parameter for injection safety ([pganalyze, 2022](https://pganalyze.com/blog/5mins-postgres-performance-in-lists-vs-any-operator-bind-parameters)); PG17 lets "btree indexes … more efficiently find a set of values, such as those supplied by `IN` clauses using constants" ([PG17 notes](https://www.postgresql.org/docs/release/17.0/)). The safe pattern across versions: join against `unnest($1)` in chunks of a few thousand keys with one prepared statement shape.
- **Hidden relationships.** Phil Factor's point that many relationships "aren't formally defined in databases" ([Simple Talk](https://www.red-gate.com/simple-talk/databases/theory-and-design/database-subsetting-and-data-extraction/)) plus Weaver's "orphans nothing cleans up" ([post](https://baweaver.com/writing/2026/06/25/rails-sharp-parts-a-polymorphic-type-is-not-a-foreign-key/)). The FK check will pass and the app will 500. Report FK-less `*_id` columns as a warning in the plan.
- **Cycles with no nullable FK.** Possible only with deferrable constraints or bulk-loaded data; NULL-then-UPDATE cannot break them and Tonic simply fails ([Tonic FK docs](https://docs.tonic.ai/app/generation/subsetting/subsetting-foreign-keys)). Post-data FK creation does not care.
- **Composite FK with partial NULLs under MATCH SIMPLE.** Skip, do not look up. Under MATCH FULL the source row is already invalid unless the constraint is `NOT VALID` (`convalidated = false`); treat unvalidated FKs as hints, not guarantees.
- **Tables not connected to the root.** Tonic: "By default, Structural copies only the table schema of out-of-subset tables. It does not populate any of the data" ([Tonic](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)); condenser separates `excluded_tables` from `passthrough_tables` ([README](https://github.com/TonicAI/condenser)). Pick one default, say it in the plan, and never silently copy a disconnected 200 GB events table.
- **Percent is a lie.** Snaplet's docs say so ([capture docs, mirror](https://snaplet-snapshot.netlify.app/snapshot/core-concepts/capture); durable primary: [snaplet/docs, capture.mdx](https://github.com/snaplet/docs/blob/main/pages/snapshot/core-concepts/capture.mdx)). Plan in row counts and print the estimate.
- **Greenmask's zero-cycle panic** ([#329](https://github.com/GreenmaskIO/greenmask/issues/329)) is the generic lesson: test the subsetter on a schema with no cycles, one self-cycle, one two-table cycle, and one SCC with two overlapping cycles, before anything else.

## 2. Deterministic masking

### 2.1 Simplest correct approach: keyed hash to seed, per semantic category

The requirement is that the same input produces the same fake everywhere it appears, so joins on masked columns still match, and that nothing about the mapping is guessable without a secret. That is a keyed pseudorandom function, not a hash and not a seeded sequence.

```
K      := 32 random bytes, generated once per project, stored outside lazysnap.yml
K_cat  := HKDF(K, info = "lazysnap/v1/" + category)       // one subkey per semantic category
h      := HMAC-SHA256(K_cat, canonical(value))            // 32 bytes, deterministic
fake   := generator[category](h)                          // h drives every choice the generator makes
```

HMAC is [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104); HKDF is [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869). Go 1.24 added `crypto/hkdf`, `crypto/pbkdf2` and `crypto/sha3` to the standard library, "based on pre-existing `golang.org/x/crypto/...` packages", alongside the FIPS 140-3 module ([Go 1.24 notes](https://go.dev/doc/go1.24)); the signatures are `hkdf.Key[Hash](h func() Hash, secret, salt []byte, info string, keyLength int)`, `Extract`, `Expand` ([crypto/hkdf](https://pkg.go.dev/crypto/hkdf)). Generators consume `h` as a random source: index a name list, build an email local part from a base32 slice, pick digits for a phone. Do not seed a global faker and call it in row order; a seeded sequence depends on call order and is not a mapping.

Everyone who shipped this landed on the same design:

- copycat: "Under the hood, Copycat hashes the input values (using SipHash), with the intention of making it computationally infeasible for the input values to be inferred from the output values", and `setHashKey()` exists so that attackers who have the code still cannot dictionary-attack the mapping ([copycat README](https://github.com/snaplet/copycat)).
- Greenmask's `hash` engine uses "the `SHA-3` algorithm to hash input values" with a salt from `GREENMASK_GLOBAL_SALT`, "added to the hash input to prevent the possibility of reverse engineering the original value from the hashed output" ([Greenmask engines](https://docs.greenmask.io/latest/built_in_transformers/transformation_engines/)).
- PostgreSQL Anonymizer: `anon.hash()` defaults to sha256 and "The default value of `anon.salt` is an empty string"; the `pseudo_*` functions are "deterministic : the functions always will return the same fake value based on a seed and an optional salt"; and "If an attacker gets access to these 2 elements, he or she could re-identify some persons using `brute force` or `dictionary` attacks" ([pg_anonymizer](https://postgresql-anonymizer.readthedocs.io/en/stable/masking_functions/)).
- Tonic: "Any column, regardless of which table it resides in, is consistent with any other column that uses the same consistent generator", but "By default, consistency is only guaranteed across a single data generation for a single workspace" unless `TONIC_STATISTICS_SEED` is set ([Tonic consistency](https://docs.tonic.ai/app/generation/generators/generator-characteristics/consistency)).
- Neosync did not have it at launch; at the Show HN the founder promised "deterministic anonymizers that output the same value for the same input (like a hash)... within the next quarter" ([HN, 2024](https://news.ycombinator.com/item?id=40447065)).

Why a key rather than a salt: GDPR defines pseudonymisation as processing "in such a manner that the personal data can no longer be attributed to a specific data subject without the use of additional information" ([Art. 4(5)](https://gdpr-info.eu/art-4-gdpr/)), and the EDPB's Guidelines 01/2025 on Pseudonymisation (adopted 2025-01-16, [EDPB](https://www.edpb.europa.eu/our-work-tools/documents/public-consultations/2025/guidelines-012025-pseudonymisation_en), [PDF](https://www.edpb.europa.eu/system/files/2025-01/edpb_guidelines_202501_pseudonymisation_en.pdf)) list cryptographic one-way functions such as MACs and encryption as suitable, prefer one-way functions, and require the secret to have "sufficient entropy" against guessing and brute force; law-firm summaries describe MACs as a stronger technique than a simple hash because they add a secret key ([Allegiance Law summary](https://allegiance.law/news/edpbs-draft-guidelines-01-2025-on-pseudonymisation/), [Stibbe](https://www.stibbe.com/publications-and-insights/key-takeaways-and-insights-from-the-edpb-pseudonymisation-guidelines)). The PDF did not parse in my environment, so the technical wording above is via those summaries; the one line I could confirm directly is that "pseudonymised information constitutes personal data under the GDPR" ([Hunton, 2025-06-05](https://www.hunton.com/insights/publications/edpb-advises-on-pseudonymisation-for-gdpr-compliance)). Emails and names are low-entropy; an unkeyed hash of them is a lookup table waiting to be built.

Where the key lives matters for "safe by default": `lazysnap.yml` is meant to be committed for CI, so it can hold a key *fingerprint* but never the key. Read it from an environment variable or the OS keyring; generate one on first run and tell the user where it went. Without it, a CI run gets a fresh random key and internally consistent joins, just not the same fakes as the laptop.

**Canonicalize before hashing.** `Alice@Example.com` and `alice@example.com` must mask to the same fake if the app treats them as the same user, and the same identifier stored as `bigint` in one table and `text` in another must hash identically. Tonic's doc is blunt that consistency depends on data type as well as value ([Tonic consistency](https://docs.tonic.ai/app/generation/generators/generator-characteristics/consistency)). Canonicalize per category: trim, case-fold emails, normalize phones to E.164 with the Go port of libphonenumber ([nyaruka/phonenumbers](https://github.com/nyaruka/phonenumbers), "a strict port of libphonenumber" tracking the Java implementation), NFKC-normalize names ([x/text/unicode/norm](https://pkg.go.dev/golang.org/x/text/unicode/norm)), and hash the canonical bytes with a type tag.

**Propagate along foreign keys.** If a masked column is the target of an FK (`users.email` referenced by `subscriptions.email`), the referencing column must get the same category and canonicalization or the join breaks. Greenmask's `apply_for_references` does this, with the condition that "The transformer must be deterministic or support `hash` engine and the `hash` engine must be set in the configuration file", and only 15 transformers qualify ([Greenmask inheritance](https://docs.greenmask.io/latest/built_in_transformers/transformation_inheritance/)). In lazysnap the classifier's decision for a unique or PK column must override whatever it decided for the FK columns pointing at it.

**Fake domains that cannot hit real people.** `example.com`, `example.net`, `example.org` and the `.invalid` TLD ("sure to be invalid and which it is obvious at a glance are invalid") are reserved by [RFC 2606](https://www.rfc-editor.org/rfc/rfc2606); in North America "Only 555-0100 through 555-0199 are now specifically reserved for fictional use" ([Wikipedia](https://en.wikipedia.org/wiki/555_(North_American_Numbering_Plan))). Keeping the real domain (`@bigcorp.com`) leaks employer; decide that in the threat model, not in code.

### 2.2 Refinements

**Format-preserving encryption, and why v1 should not ship it.** FPE gives a keyed *permutation* of a domain (all 16-digit strings, all 9-digit numbers): deterministic, invertible, collision-free by construction, which is exactly what you want for identifiers that must keep their shape and stay unique. The state of the standard as of 2026-09-05:

- SP 800-38G (2016, update 1) "specifies two methods, called FF1 and FF3" ([CSRC](https://csrc.nist.gov/pubs/sp/800/38/g/upd1/final)). NIST concluded in 2017 that "FF3 is no longer suitable as a general-purpose FPE method" after Durak and Vaudenay's attack ([NIST news](https://csrc.nist.gov/news/2017/recent-cryptanalysis-of-ff3); [CRYPTO 2017](https://link.springer.com/chapter/10.1007/978-3-319-63715-0_23)); large-domain attacks followed (Hoang, Miller, Trieu, [EUROCRYPT 2019](https://link.springer.com/chapter/10.1007/978-3-030-17656-3_4)), then third-generation attacks on FF3 (Amon, Dunkelman, Keller, Ronen, Shamir, [2021](https://link.springer.com/chapter/10.1007/978-3-030-77886-6_5)) and linear cryptanalysis of the patched FF3-1 (Beyne, [CRYPTO 2021](https://iacr.org/archive/crypto2021/12826083/12826083.pdf)).
- Revision 1's second public draft (2025-02-03, comments to 2025-04-04) makes four changes: "The domain size for the FF1 encryption method is increased", "The encryption method FF3 is no longer specified", the inverse AES function may not be `CIPH`, and "Floating point arithmetic is disallowed in implementations of FF1" ([CSRC news](https://csrc.nist.gov/news/2025/comment-on-the-2nd-draft-of-sp-800-38g-rev-1), [2PD page](https://csrc.nist.gov/pubs/sp/800/38/g/r1/2pd)). The initial draft had set "the minimum domain size for FF1 and FF3-1" at "one million" ([2PD page](https://csrc.nist.gov/pubs/sp/800/38/g/r1/2pd), [IPD](https://csrc.nist.gov/pubs/sp/800/38/g/r1/ipd)). The final Rev. 1 URL returned 404 when I checked and no final publication turned up in search, so treat Rev. 1 as still a draft (final status: unverified).
- Go libraries, surveyed rather than assumed dead from two names: capitalone/fpe is archived and "not maintained or reviewed" since 2021-11-05 ([repo](https://github.com/capitalone/fpe)); ubiq-fpe-go "has been deprecated and is no longer supported" ([repo](https://github.com/ubiqsecurity/ubiq-fpe-go)); cloudtrust/fpe (a capitalone/fpe derivative) is archived 2022-07-20 and its own README documents unpatched FF3 attacks left on `master` while the fix lives on an unmerged branch ([repo](https://github.com/cloudtrust/fpe)) — worse than merely unmaintained, since it is actively wrong if used as-is; Tensai75/go-fpe-bytes is not archived, drops FF3 entirely (matching the Rev. 1 direction below), is FF1-only over bytes rather than Unicode strings, ships NIST test vectors converted to byte form and passing, but carries no maintenance commitment beyond that and is unaudited ([repo](https://github.com/Tensai75/go-fpe-bytes)) — the least-bad of the five, but "least-bad" and "I would put this in a security-critical path" are different bars; unitehere/format-preserving-encryption and ac999/go-fpe both surfaced in the same search and both fail the bar immediately — the former ships as an application with AWS deployment scaffolding rather than a library and states no maintenance status, the latter says outright "This library is provided as-is and should not be used in production systems without a full security audit" and describes itself as built for educational purposes ([unitehere](https://github.com/unitehere/format-preserving-encryption), [ac999](https://github.com/ac999/go-fpe)). None of the five changes the verdict. Go's standard library was proposed a home for FF1/FF3 in 2017 (`golang.org/x/crypto` as `fpe/ff1` and `fpe/ff3`); the proposal was declined and the tracking issue frozen for age, so there is no stdlib answer, only the community packages above ([golang/go#18752](https://github.com/golang/go/issues/18752)).

Verdict: a standard in flux, small domains (4-digit PINs, 6-digit account suffixes) explicitly out of scope, and no library. If v2 needs it, implement FF1 from the spec against NIST's published example vectors and restrict it to digit strings with domain ≥ 10^6. To keep FPE output inside an irregular domain (valid dates, Luhn-valid card numbers) the standard trick is cycle walking: "Repeatedly apply the block cipher until a ciphertext that lies within the original domain is produced" (Black and Rogaway, "Ciphers with Arbitrary Finite Domains", [PDF](https://www.cs.ucdavis.edu/~rogaway/papers/subset.pdf)); it destroys check digits unless you recompute them afterwards.

For v1 the pragmatic split: surrogate keys (`id bigint`) are not PII and are not masked; natural identifiers that are PII (email, phone, national ID, card number) are replaced by keyed-hash-driven fakes with a domain large enough that collisions do not happen in practice.

**Unique-constraint collisions.** A keyed hash is not a permutation; two inputs can map to the same output. For n values drawn from d possibilities, P(collision) ≈ 1 − e^(−n²/2d), and the first collision is expected around √d ([birthday problem](https://en.wikipedia.org/wiki/Birthday_problem)). With a 64-bit-derived email local part, a million rows collide with probability about 2.7 × 10⁻⁸: ignore. With a generator whose domain is a list of 3,000 first names, 100 rows have about an 80% chance of at least one collision (1 − e^(−100²/2·3000) ≈ 0.80, not "almost surely"): fine for `first_name`, fatal under a unique index. The inverted form is the one an implementer actually needs at plan time — solving for the domain that keeps collision probability under a target `ε` given `n` rows: `d_required ≈ n² / (2ε)`. That is the same formula used to size the refusal check in the collision rule above. The vendors all say so: DataVeil, "multiple different original values can produce the same masked value. This is also sometimes referred to as collisions", and it emits "a compile warning if a non-distinct mask is used on a column with a unique constraint" but not reliably for multi-column unique constraints ([DataVeil](https://www.dataveil.com/user-guide/topics/consistent-masking.htm)); Tonic, "It does not guarantee that two different input values produce two different output values" and "Consistent generators are not 1:1 mappings" ([Tonic consistency](https://docs.tonic.ai/app/generation/generators/generator-characteristics/consistency)), whose Unique Email generator "Replaces the username with a randomly generated GUID" and "only guarantees uniqueness if the underlying column is unique" ([Tonic Unique Email](https://docs.tonic.ai/app/generation/generators/generator-reference/unique-email)); Greenmask, "The hash engine does not guarantee the uniqueness of generated values" with uniqueness "currently under development" ([Greenmask engines](https://docs.greenmask.io/latest/built_in_transformers/transformation_engines/), [#111](https://github.com/GreenmaskIO/greenmask/issues/111), open since 2024-05-12); pg_anonymizer, for unique columns "you will need to initialize the extension with a fake dataset that is way bigger than the numbers of rows of the table. Otherwise you may see some 'collisions' happening" ([pg_anonymizer](https://postgresql-anonymizer.readthedocs.io/en/stable/masking_functions/)); copycat's `unique()` retries with `attempts` "Defaults to 10" and "The uniqueness is not guaranteed" ([copycat](https://github.com/snaplet/copycat)).

The implementable rule:

1. Introspect uniqueness properly: `pg_index.indisunique`, including expression and partial indexes, not just `pg_constraint`. A unique index on `lower(col1)` "would prevent creation of rows whose `col1` values differ only in case" ([expression indexes](https://www.postgresql.org/docs/current/indexes-expressional.html)), so two masked emails differing only by case collide.
2. For any column under a unique index, use a generator whose domain is ≥ 2^64 and derive the value from the full hash (name-shaped fakes get a hash-derived suffix: `alice.k7v2x@example.com`). Say in the explanation that uniqueness forced the suffix.
3. Do not "retry with a counter" on collision. The retry depends on which row arrived first, so the mapping becomes order-dependent and the same value in another table (or another run) resolves differently. If a column has a unique index and a small-domain generator is the only acceptable shape, refuse and explain rather than resolve at load time.
4. **Rules 2 and 3 collide whenever the column's own type cannot physically hold a ≥2^64-domain value** — a `varchar(12)` reference code, a 10-character unique account code, or a unique column under `CHECK (col ~ '^[A-Z]{3}-[0-9]{4}$')` admits far fewer than 2^64 distinct values no matter what the generator does, and rule 3 forbids papering over the shortfall with a retry counter. Resolve the collision with an explicit precedence, computed at plan time, not at load time:
   - Compute the column's actual admissible domain size `d`: start from the type and `atttypmod` (e.g. `varchar(12)` over the character set in use), then narrow by any `CHECK` constraint the plan step can parse into a shape (a regex-like pattern, an enum of literals, a numeric range), and by enum labels when the column is an enum type. When a `CHECK` expression cannot be parsed into a domain size, treat `d` as unknown rather than as unlimited.
   - Compute the domain a safe hash-derived generator needs for this table's row count `n`, at a target collision probability `ε` (a reasonable default is `ε ≤ 10^-6`), using the birthday approximation from the previous section solved for the domain: `d_required ≈ n² / (2ε)`. For example, `n = 100,000` rows at `ε = 10^-6` needs `d_required ≈ 10^10 / 2×10^-6 = 5×10^15` — comfortably inside a `varchar(12)` base62 domain (62^12 ≈ 3.2×10^21) but far beyond a `varchar(6)` one (62^6 ≈ 5.7×10^10 is already short of the mark once row counts climb past a few hundred thousand).
   - If `d ≥ d_required`: use the largest generator that fits inside `d` (e.g. a base-62 or base-36 encoding of enough hash bits to fill the column, or an enumeration index into a small legal set when `d` itself is small — a low-cardinality enum is exactly the case where every value should be reachable and near-certain collision is expected and fine, it just is not "unique").
   - If `d < d_required`: refuse the column with a named error ("`accounts.ref_code`: unique index, but the admissible domain (`varchar(10)`, no usable structure) can hold about 3.4×10^17 codes and this table's 8,000,000 rows need about 3.2×10^19 to keep collision risk under 10^-6 — opt this column out of masking or supply an explicit 1:1 mapping") rather than silently colliding or silently retrying. Opting out and supplying a mapping (a lookup table the operator provides, keyed by the original value) are the two escape hatches; both are explicit operator decisions, not defaults.

**Preserve what the application checks.** Length: `varchar(n)` (`atttypmod`) rejects a longer fake. `CHECK` constraints (`email ~ '@'`) and enum types constrain the shape. Validity: a phone that libphonenumber's `IsValidNumber` rejects ([phonenumbers](https://github.com/nyaruka/phonenumbers)) breaks apps that validate on read. NULL stays NULL. Empty string stays empty.

### 2.3 Traps

- **Hashing without a key.** Dictionary attack on emails and names; see pg_anonymizer's warning and the EDPB above. Also why `md5(email)` "anonymization" scripts fail audits.
- **Key in the committed config.** Then anyone with the repo can reverse-map any value they can guess. Fingerprint in the file, key in the environment.
- **Frequency leaks.** Deterministic masking preserves frequency: the most common masked surname is the alias of the most common real surname, and a one-off value stays one-off. This is pseudonymisation under GDPR Art. 4(5), not anonymisation; put that in the threat model rather than claiming otherwise. HN, on Neosync: "every bit of real data in aggregate leads to revealing someone's identity" ([HN](https://news.ycombinator.com/item?id=40445047)).
- **Prefix-preserving masks.** On the Replibyte Show HN a reader spotted a "transformer which appears to retain the first char on string fields. That's not safe if you're dealing with customer data" and followed up that "I could potentially use that information to find a real customer in the DB" ([HN 31190464](https://news.ycombinator.com/item?id=31190464), [HN 31201089](https://news.ycombinator.com/item?id=31201089)). Never keep a character, a length, or a prefix of a masked value.
- **Classifier disagreement across a join.** `users.email` classified as email, `invoices.billing_email` as free text: different generators, join broken. Propagate categories along FK edges and identical column names before masking.
- **Faker version drift.** gofakeit says "If you need a reproducible outcome you can set it via the Seed function call" and nothing about stability across versions ([gofakeit](https://github.com/brianvoe/gofakeit)); when its word lists change, the mapping changes. Embed your own lists for categories that must be stable, pin versions, and derive per-value randomness from `h`, never from a global sequence.
- **Partition keys and sequences.** Masking a column that is a partition key or an identity column moves rows to other partitions or beyond the sequence; section 4.

## 3. PII classification

### 3.1 Simplest correct approach: names plus types plus validated samples, with a reason string

Three signals, combined into a score with a human-readable reason. Every tool that ships this does the first two; the third is what makes the reason credible.

1. **Column and table names.** piicatcher's "shallow" scan is "Match regular expressions with column names" ([piicatcher](https://github.com/tokern/piicatcher)); its whole list fits on a screen, e.g. Person `^.*(firstname|fname|lastname|lname|fullname|maidenname|_name|nickname|name_suffix|name|person).*$`, Email `^.*(email|e-mail|mail).*$`, BirthDate `^.*(date_of_birth|dateofbirth|dob|birthday|date_of_death|dateofdeath|birthdate).*$`, Address `^.*(address|city|state|county|country|zone|borough).*$`, Password `^.*pass.*$`, SSN `^.*(ssn|social_number|social_security|…).*$` ([scanner.py](https://raw.githubusercontent.com/tokern/piicatcher/master/piicatcher/scanner.py)). Note how greedy they are: `.*mail.*` matches `mailing_list_id`, `.*pass.*` matches `passenger_count`, `.*name.*` matches `product_name`. Tonic's scan layers four methods: rule-based analysis of "data type, column name, and column values" using "random sampling of rows from the data" with "regular expression matching and dictionary lookups"; custom rules on type and name; a model that scores table-plus-column names for "semantic similarity to sensitivity types" at medium or low confidence; and an optional LLM over the schema "and, optionally, contextual source data"; it warns that "this process cannot guarantee perfect precision and recall" ([Tonic scan docs](https://docs.tonic.ai/app/generation/identify-sensitive-data/running-the-structural-sensitivity-scan)). Table context matters: `name` in `products` is not PII, `name` in `users` is.
2. **Postgres types.** `inet`, `cidr`, `macaddr`, `uuid`, `citext`, `date` columns named `*birth*`, `bytea` (out of scope per CONCEPT), `jsonb` (below). Domains over text (`CREATE DOMAIN email AS text`) are a gift: the domain name is the category.
3. **Sampled values through validators.** Sample with `TABLESAMPLE`: `BERNOULLI` "scans the whole table and selects or ignores individual rows independently", `SYSTEM` "is significantly faster than the `BERNOULLI` method when small sampling percentages are specified, but it may return a less-random sample of the table as a result of clustering effects", and `REPEATABLE (seed)` makes the sample reproducible ([SELECT](https://www.postgresql.org/docs/current/sql-select.html)). `pg_stats.most_common_vals` and `histogram_bounds` give real values for free if the table has been analyzed, and the view "allows access only to rows of `pg_statistic` that correspond to tables the user has permission to read" ([pg_stats](https://www.postgresql.org/docs/current/view-pg-stats.html)). Run samples through validators, not just regexes: Luhn plus Presidio's rule that a card is "between 12 to 19 digits" with checksum ([Presidio entities](https://presidio.dataprivacystack.org/supported_entities/)), mod-97 for IBAN, `net/mail.ParseAddress` for email, `net.ParseIP`, libphonenumber's `IsValidNumber` with a region hint ([phonenumbers](https://github.com/nyaruka/phonenumbers)), a UUID parser, and a names dictionary. Presidio's own design is exactly this: "Pattern matching & regex" for structured identifiers, "Checksum validation (Luhn, ISO 7064)", NER for names, and context words to lift confidence ([Presidio entities](https://presidio.dataprivacystack.org/supported_entities/)).

Combine: a name hit alone is medium; a name hit plus ≥ 80% of samples validating is high; samples validating with no name hit is medium with the reason "values look like X"; special categories by name alone are high because the cost of missing them is highest. Print the reason ("column `users.email`: name matches email; 100/100 sampled values parse as addresses"). Bias toward recall; the CLAUDE.md rule is "when in doubt, mask it".

**Categories a first release must catch.** Take the union of HIPAA Safe Harbor's 18 identifiers (names; geographic subdivisions smaller than a state; all elements of dates except year; ages over 89; telephone; fax; email; SSN; medical record numbers; health plan beneficiary numbers; account numbers; certificate/license numbers; vehicle identifiers; device identifiers; URLs; IP addresses; biometric identifiers; full-face photos, [45 CFR 164.514(b)(2)](https://www.law.cornell.edu/cfr/text/45/164.514)), GDPR's definition of personal data plus Article 9's special categories ("racial or ethnic origin, political opinions, religious or philosophical beliefs, or trade union membership, … genetic data, biometric data …, data concerning health or data concerning a natural person's sex life or sexual orientation", [Art. 9](https://gdpr-info.eu/art-9-gdpr/)), and the global infoTypes Google's DLP ships (EMAIL_ADDRESS, PHONE_NUMBER, PERSON_NAME, FIRST_NAME, LAST_NAME, DATE_OF_BIRTH, AGE, GENDER, CREDIT_CARD_NUMBER, IBAN_CODE, IP_ADDRESS, MAC_ADDRESS, AUTH_TOKEN, PASSWORD, ETHNIC_GROUP, SEXUAL_ORIENTATION, MEDICAL_RECORD_NUMBER, …, plus country-specific `[COUNTRY]_[ID_TYPE]` types — the reference page lists several hundred built-in infoTypes across its category tables (no single total-count sentence appears on the page; call `infoTypes.list` for the current count, [DLP infoTypes](https://docs.cloud.google.com/sensitive-data-protection/docs/infotypes-reference))). Then add what engineers actually put in databases:

| Category | Name signals (examples) | Value signals | Default action |
|---|---|---|---|
| Person name | `first_name`, `last_name`, `full_name`, `display_name`, `name` in person-like tables | dictionary hit rate; capitalized tokens | fake name (keyed) |
| Email | `email`, `e_mail`, `*_email` | `ParseAddress` | fake email at reserved domain |
| Phone / fax | `phone`, `mobile`, `tel`, `fax`, `msisdn` | libphonenumber valid | fake phone in fictional range |
| Postal address | `address`, `street`, `city`, `postcode`, `zip`, `line1` | mixed digits + words | fake address; HIPAA 3-digit ZIP rule is a v2 option |
| Geolocation | `lat`, `lng`, `latitude`, `geom`, `location` | numeric ranges, PostGIS types | jitter or fixed point |
| Dates about a person | `dob`, `birth*`, `date_of_birth`, `died` | date type | shift or year-only |
| National / government IDs | `ssn`, `nino`, `passport`, `tax_id`, `national_id`, `driver*licen*` | country formats, checksums | fake with same shape |
| Financial account | `iban`, `account_number`, `card`, `pan`, `routing`, `sort_code` | Luhn, mod-97 | fake with valid checksum |
| Network identifiers | `ip`, `ip_address`, `mac`, `user_agent`, `device_id`, `imei` | `net.ParseIP`, inet/macaddr types | fake in documentation ranges |
| Online identifiers | `username`, `handle`, `login`, `url`, `avatar_url` | URL parse | fake handle / URL |
| Credentials and secrets | `password`, `*_hash`, `token`, `secret`, `api_key`, `otp` | high Shannon entropy | replace with a fixed unusable value |
| Free text about people | `notes`, `comment`, `description`, `bio`, `message`, `body`, `reason` | NER hits in samples | replace whole value with same-length filler |

| Semi-structured | `jsonb`, `json`, `hstore`, `text[]` with any of the above as keys | key names in samples | see below |

Secrets need entropy, not names: detect-secrets ships `Base64HighEntropyString` and `HexHighEntropyString` with default limits of 4.5 and 3.0 and says the approach "may require tuning to adjust the scanning precision" ([detect-secrets](https://github.com/Yelp/detect-secrets)). Use them on short text columns only; a UUID column trips the hex detector by design, so check the UUID parser first.

### 3.2 Refinements

**Multilingual names.** Presidio "In its default configuration … contains recognizers and models for English", and while "regular expressions are language agnostic, the context words used to increase the PII detection confidence aren't" ([Presidio languages](https://presidio.dataprivacystack.org/analyzer/languages/)). A dictionary is the honest v1 answer: name-dataset has "730K first names and 983K last names" across 106 countries, derived from "the Facebook massive dump (533M users)", Apache-2.0, and "requires approximately 3.2 GB of RAM to load the full dataset into memory" ([name-dataset](https://github.com/philipperemy/name-dataset)). Embed a trimmed top-N-per-country list with `go:embed`, NFKC-normalize and case-fold before lookup, and treat the dictionary as confirmation for a name-shaped column rather than the sole trigger. Include obvious non-English column names (`nombre`, `courriel`, `telefon`, `名前`) in the name lists, since Presidio's caveat applies to yours too.

**JSON and free text.** Presidio Structured builds "a mapping between these column/keys names and the detected PII entities", picks a per-column entity by "Most Common", "Highest Confidence" or "Mixed" strategy, and for JSON "Nesting objects in lists is not supported in JsonAnalysisBuilder for now" ([Presidio structured](https://presidio.dataprivacystack.org/structured/)). Greenmask's `Json` transformer "applies a sequence of changing operations (`set` and/or `delete`) to a JSON document" at explicit sjson paths; it does not find PII for you ([Greenmask Json](https://docs.greenmask.io/latest/built_in_transformers/advanced_transformers/json/)). Zero-config version: sample rows, collect top-level and one-level-nested keys with `jsonb_object_keys`/`jsonb_each` ([JSON functions](https://www.postgresql.org/docs/current/functions-json.html)), run the column-name heuristics over key names, and if any key hits, mask that key's values at every path with the same category generators, keeping structure. If keys vary wildly per row (event payloads), replace the whole document with `{}` and say why. Free text cannot be classified reliably from samples; classify it by column name plus NER hits, and when masked, replace the whole value. Partial redaction of prose is a research problem, not a v1 feature.

**Where ML is and is not worth it.** Numbers from 2019 to 2026:

- Column-level detection on four datasets: Presidio macro-F1 0.793 (DeSSI), 0.293 (Kaggle), 0.684 (OpenML), 0.662 (MIMIC), average 0.608; CASSED, a fine-tuned classifier, 0.996 on the synthetic DeSSI it was trained on and 0.349 / 0.501 on Kaggle / OpenML, average 0.643; GPT-4o given column names, neighbouring columns and frequent values 0.766 / 0.902 / 0.964 / 0.829, average 0.865. The authors still write "the FN rates on the real-world data are currently still too high for practical applications" and that "Transmitting personal data to external servers poses compliance risks" ([Ntwali, Rück, Heckmann, arXiv 2506.22305](https://arxiv.org/html/2506.22305v1)).
- Sherlock reaches support-weighted F1 0.89 over 78 semantic types with 1,588 features per column and 686,765 training columns ([Hulsebos et al., KDD 2019](https://arxiv.org/abs/1905.10688)). Impressive, and it needs a model and a corpus you do not have.
- Contextual detection ("the sensitivity of data depends on its context") "reaches a recall of 94% compared to 63% with commercial tools" by contextualizing a column's type within the whole dataset ([Telkamp, Hulsebos, arXiv 2512.04120](https://arxiv.org/abs/2512.04120)).
- For PII in free text, GLiNER2-PII (0.3B parameters, 42 types, seven European languages) scores span F1 0.475 / 0.467 on the SPY legal / medical sets with recall 0.722 / 0.681 and precision 0.354 / 0.355, and "tends to over-predict name entities" ([Zaratiana et al., arXiv 2605.09973](https://arxiv.org/html/2605.09973v1)). Recall 0.7 is not a safety property.

Reading: the signal ML adds over names + validators is *context* ("this `name` sits next to `dob` and `ssn`"), and a cheap rule captures most of it: if a table has any high-confidence PII column, raise every ambiguous column in that table to medium. Ship rules, dictionaries, validators and explanations in v1; a local NER pass over free-text samples is a v2 signal, never the gate. A cloud LLM over production values contradicts the CONCEPT's compliance story ("Someone from compliance asks where the prod dump on the shared drive came from").

**Quasi-identifiers.** ZIP + birth date + gender identifies most people; HIPAA's rules (three-digit ZIP, `000` for areas with 20,000 or fewer people; year-only dates; ages over 89 bucketed) exist for this ([45 CFR 164.514](https://www.law.cornell.edu/cfr/text/45/164.514)). v1 masks DOB and postcode by default and does not promise k-anonymity.

### 3.3 Traps

- **Schema drift.** The classic failure, from the Replibyte thread: "database schema changes, but people don't update their script to anonymize new tables or columns" ([HN 31189133](https://news.ycombinator.com/item?id=31189133)); the same commenter elsewhere: "You're assuming that your anonymization script works. What if some data isn't removed?" ([HN 27548530](https://news.ycombinator.com/item?id=27548530)). `lazysnap.yml` must record a decision per column and the tool must fail closed on a column it has never seen, not pass it through.
- **Head-of-table sampling.** `LIMIT 100` returns the oldest rows; PII often appears later (a `notes` column empty for the first two years). Use `TABLESAMPLE` or `pg_stats`.
- **Identifiers stored as numbers.** `account_no bigint`, `nhs_number bigint`. Name heuristics must run on numeric columns too; validators (Luhn, mod-11) apply to digit strings regardless of type.
- **`name` everywhere.** Products, roles, plans. piicatcher's `.*name.*` regex is the cautionary example. Table context and the neighbouring-column rule keep this from masking your product catalogue; the reason string keeps the user from trusting a wrong call silently.
- **Hashed passwords look safe.** They are credentials; replace with a known-invalid value. Same for API keys and session tokens (entropy detector).
- **Enum and domain types.** `gender` as an enum still reveals gender; the mask must be a valid enum label.
- **Masking breaks CHECK constraints and expression indexes.** Detect before load; section 4.
- **Audit and log tables.** `audit_log.old_row jsonb` contains serialized copies of everything. Treat any jsonb column in a table named like audit/log/history/event as free text and mask whole.
- **Language-specific context words.** Presidio's own caveat ([languages](https://presidio.dataprivacystack.org/analyzer/languages/)); do not assume English column names.

## 4. Streaming extract and load at scale in Postgres

### 4.1 Simplest correct approach

Three *roles*, not a fixed count of three: one source connection holds the snapshot open (below), a source reader pool serves key lookups and extract queries, and a target pool sized by however many tables load in parallel serves COPY. Within a single table's load path the minimum is still three live connections doing three different things at once — the reason is pgx's rule that a `Conn` "is not safe for concurrent usage" and "rows must be closed before the connection can be used again" ([pgx v5](https://pkg.go.dev/github.com/jackc/pgx/v5)); you cannot look up parents while a result set is open on the same connection — but §4.2's parallel load across DAG levels multiplies the reader and target roles by the table-parallelism factor, not the fixed number three.

**Source snapshot consistency.** Everything above this line — the worklist's key-selection queries, and every per-table extract query — runs as a sequence of separate statements over a live production database, potentially over several minutes. Nothing so far has said how to keep that sequence from seeing different versions of the truth: a row inserted between the key-selection query and the extract query is invisible to the extract's `WHERE id IN (...)` if the parent it needs was chosen before the insert, and a row deleted in that window can be selected as a key and then vanish before the extract reads it. Either way the result surfaces only at the very end, as `ALTER TABLE ... ADD FOREIGN KEY` failing in post-data, indistinguishable from a genuine subsetting bug. The tool pgcopydb, which this document already cites five times for step order, states the fix as the first thing on its clone page: "In order to be consistent, pgcopydb exports a Postgres snapshot by calling the `pg_export_snapshot()` function on the source database server. The snapshot is then re-used in all the connections to the source database server by using the `SET TRANSACTION SNAPSHOT` command" ([pgcopydb clone](https://pgcopydb.readthedocs.io/en/latest/ref/pgcopydb_clone.html)). lazysnap needs the same mechanism: open a `REPEATABLE READ` transaction on the source connection that will live for the whole run, call `pg_export_snapshot()` on it once ("Saves the transaction's current snapshot and returns a text string identifying the snapshot", [snapshot synchronization functions](https://www.postgresql.org/docs/current/functions-admin.html)), and have every other source connection begin its own `REPEATABLE READ` transaction and run `SET TRANSACTION SNAPSHOT '<id>'` as its first statement, because "`SET TRANSACTION SNAPSHOT` can only be executed at the start of a transaction, before the first query or data-modification statement" ([SET TRANSACTION](https://www.postgresql.org/docs/current/sql-set-transaction.html)). `REPEATABLE READ` isolation, not the default `READ COMMITTED`, is what makes this hold for a multi-statement session: "a query in a repeatable read transaction sees a snapshot as of the start of the first non-transaction-control statement in the transaction, not as of the start of the current statement within the transaction" ([transaction-iso](https://www.postgresql.org/docs/current/transaction-iso.html)), so every subsequent query on that connection reads the same imported snapshot rather than drifting forward. This closes the plan-vs-extract race entirely, at a real cost stated in the trap below.

**Extract.** For each table in load order, for each chunk of selected keys: `SELECT cols FROM t JOIN unnest($1::int8[]) AS k(id) ON t.id = k.id` via `conn.Query`, iterate `rows.Next()`, and check `rows.Err()` afterwards, because "`pgx` defers result-set processing until after the query execution returns" and errors surface during iteration ([pgx #1707](https://github.com/jackc/pgx/issues/1707)). A maintainer-guided benchmark on a million-row table found `Query` (7.87–8.08 s) and raw `PgConn.CopyTo` with binary decoding (7.68–8.74 s) indistinguishable; asked "Does this mean not worth the effort to use CopyTo()?", the maintainer said "In looks that way, at least in this case" ([pgx discussion #1599](https://github.com/jackc/pgx/discussions/1599)). Start with `Query`. `PgConn.CopyTo(ctx, w, sql)` takes a bare SQL string and no arguments ([pgconn](https://pkg.go.dev/github.com/jackc/pgx/v5/pgconn)), so a key-list COPY means interpolating keys into SQL; Greenmask gets away with COPY because it "utilizes the COPY command in TEXT format" over whole tables or pushed-down conditions and transforms "COPY lines" in the stream ([Greenmask architecture](https://docs.greenmask.io/latest/architecture/)).

**Transform** per row in Go, in the same goroutine or via a channel; the masker from section 2 is a pure function of (category, value, key).

**Load** with `conn.CopyFrom(ctx, table, cols, source)`, where `source` is a `CopyFromFunc` that "accepts a function returning rows until signaling end-of-data" ([pgx v5](https://pkg.go.dev/github.com/jackc/pgx/v5)). CopyFrom "requires all values use the binary format", so "A pgtype.Type that supports the binary format must be registered for the type of each column"; enums "appear to be strings" but still must be registered via `LoadType` and `RegisterType`, or you get `unable to encode "yes" into binary format for unknown type (OID 16386): cannot find encode plan` ([pgx v5](https://pkg.go.dev/github.com/jackc/pgx/v5), [pgx #1338](https://github.com/jackc/pgx/issues/1338)); the maintainer's advice is to do the registration "in a AfterConnect hook" so every pooled connection has it ([pgx discussion #1519](https://github.com/jackc/pgx/discussions/1519)). Numbers, PG 16.2 with pgx v5.5 over a local socket: 50,000 rows load in 140 ms with CopyFrom (357,100 rows/s) versus 880 ms with `SendBatch` and 37 s one-by-one; multi-row `INSERT` cannot even run at 50,000 rows because 3 × 50,000 parameters exceeds the 65,535-parameter limit; across a 67 ms cross-region link all three bulk methods converge to about 71–79 ms per 500 rows because "the single network round trip dominates" ([Gold Lapel benchmark, 2026-03-05](https://goldlapel.com/grounds/go-postgres/pgx-bulk-insert-benchmarks)). Postgres's own guidance: "Use `COPY` to load all the rows in one command, instead of using a series of `INSERT` commands", and "loading a large number of rows using `COPY` is almost always faster than using `INSERT`, even if `PREPARE` is used" ([Populating a Database](https://www.postgresql.org/docs/current/populate.html)).

**Column list.** Always pass an explicit column list and exclude generated columns; a generated column "cannot have a value specified directly in `INSERT` or `UPDATE`" ([generated columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html)) and without a list COPY takes "all columns of the table except generated columns" ([COPY](https://www.postgresql.org/docs/current/sql-copy.html)). Identity columns need nothing special under COPY: "For identity columns, the `COPY FROM` command will always write the column values provided in the input data, like the `INSERT` option `OVERRIDING SYSTEM VALUE`" ([COPY](https://www.postgresql.org/docs/current/sql-copy.html)), unlike `INSERT`, where "For an identity column defined as `GENERATED ALWAYS`, it is an error to insert an explicit value (other than `DEFAULT`) without specifying either `OVERRIDING SYSTEM VALUE` or `OVERRIDING USER VALUE`" ([INSERT](https://www.postgresql.org/docs/current/sql-insert.html)).

**Sequences and identity.** After loading each table, for every serial or identity column: `SELECT setval(pg_get_serial_sequence('schema.t', 'id'), max(id))`. `pg_get_serial_sequence` returns "the sequence internally created for that column" for identity columns and the owned sequence for serials, and note its argument quirk: the table name "is lower-cased by default" while the column name "is treated literally and so has its case preserved" ([functions-info](https://www.postgresql.org/docs/current/functions-info.html)). In `setval`'s three-argument form "`true` has the same effect as the two-parameter form", i.e. the next `nextval` returns max+1, and "sequence state changes made by `setval` are immediately visible to other transactions, and are not undone if the calling transaction rolls back" ([functions-sequence](https://www.postgresql.org/docs/current/functions-sequence.html)). `ALTER TABLE … ALTER COLUMN … RESTART WITH n` is the identity-column alternative ([ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)). An empty table needs no special case for the reason it looks like it might: `setval` is a strict function, so `setval(seq, NULL)` — which is what `max(id)` returns over zero rows — simply returns `NULL` and leaves the sequence untouched, no error (`pg_proc` carries no `NOT STRICT`/`CALLED ON NULL INPUT` override for the `setval` entries, and PL/pgSQL's own default is that "by default, a strict function returns null whenever any of its arguments are null", [xfunc-volatility](https://www.postgresql.org/docs/current/xfunc-volatility.html)). What is a real error is "fixing" the NULL yourself with `coalesce(max(id), 0)`: `setval(seq, 0)` raises `ERROR: setval: value 0 is out of bounds for sequence`, because the default sequence minimum is 1 ([functions-sequence](https://www.postgresql.org/docs/current/functions-sequence.html)) — precisely the shape the `coalesce(..., 0)` idiom produces on an empty table. Use `setval(seq, coalesce(max(id), 1), max(id) IS NOT NULL)`, whose third argument makes the call a no-op-equivalent "nothing has been read from this sequence" state when the table is empty, or skip the call outright for a table you already know is empty; either way, do not call `setval` with a literal `0`. Forgetting sequence handling for a non-empty table is condenser issue #14, open since 2019-10-09: "Otherwise, the sequences are all reset to 1" ([condenser #14](https://github.com/TonicAI/condenser/issues/14)); db-condenser lists "Automatic sequence reset after subsetting" as a headline feature ([db-condenser](https://github.com/tkhuu01/db-condenser)); pgcopydb "Resets sequence values to match source" as a distinct step ([pgcopydb clone](https://pgcopydb.readthedocs.io/en/latest/ref/pgcopydb_clone.html)).

**Partitioned tables.** `COPY FROM` into the parent routes rows: "`COPY FROM` can be used with plain, foreign, or partitioned tables"; `COPY TO` from a partitioned parent is not supported, "use `COPY (SELECT * FROM table) TO`" ([COPY](https://www.postgresql.org/docs/current/sql-copy.html)). "All rows inserted into a partitioned table will be routed to the appropriate one of the partitions" and "Inserting data into the parent table that does not map to one of the existing partitions will cause an error" ([partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)). PG12 lets foreign keys "reference partitioned tables" and improved "speed of `COPY` into partitioned tables" ([PG12 notes](https://www.postgresql.org/docs/release/12.0/)); PG17 lets "partitioned tables … have identity columns" ([PG17 notes](https://www.postgresql.org/docs/release/17.0/)). Always target the root, as pg_dump's `--load-via-partition-root` does so that "the appropriate partition to be re-determined for each row when the data is loaded", which matters when "the partitioning column is of type text and the two systems have different definitions of the collation" ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)). Treat partitions as one logical table in the plan (`conparentid` and `pg_inherits`), never as separate subset targets.

**Finish** with `ANALYZE` on every loaded table: "Whenever you have significantly altered the distribution of data within a table, running `ANALYZE` is strongly recommended" ([populate](https://www.postgresql.org/docs/current/populate.html)).

### 4.2 Refinements

**Constraints: use the pg_dump split.** lazysnap creates the target schema, so it can split DDL the way pg_dump does: pre-data (tables without indexes and FKs), data, post-data ("definitions of indexes, triggers, rules, statistics for indexes, and constraints other than validated check and not-null constraints", [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)). Postgres: "a foreign key constraint can be checked 'in bulk' more efficiently than row-by-row. So it might be useful to drop foreign key constraints, load data, and re-create the constraints", and for big loads "it may be necessary, not just desirable" because per-row FK checks can "cause the trigger event queue to overflow available memory" ([populate](https://www.postgresql.org/docs/current/populate.html)). Same for indexes: "Creating an index on pre-existing data is quicker than updating it incrementally as each row is loaded" ([populate](https://www.postgresql.org/docs/current/populate.html)), and the benchmark puts numbers on it: 50,000-row CopyFrom goes from 95 ms with one index to 340 ms with four ([Gold Lapel](https://goldlapel.com/grounds/go-postgres/pgx-bulk-insert-benchmarks)). pgcopydb's order is the template: pre-data, COPY with `--table-jobs` workers, indexes with `--index-jobs` workers, "PRIMARY KEY constraints are created USING the just built indexes", vacuum/analyze, sequences, then post-data with foreign keys ([pgcopydb clone](https://pgcopydb.readthedocs.io/en/latest/ref/pgcopydb_clone.html)). With FKs created last, insertion order and cycle breaking stop being load concerns; the `ALTER TABLE ADD FOREIGN KEY` at the end *is* the integrity verification. For a report instead of a hard failure, add each FK `NOT VALID` (the "potentially-lengthy scan is skipped") then `VALIDATE CONSTRAINT`, which validates "by scanning the table to ensure there are no rows for which the constraint is not satisfied" ([ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)); you get a per-constraint pass/fail with a table name.

When the target already has a schema with constraints (the CONCEPT's `shop-db-test`), the choices are: recreate the schema (cleanest, and what "snapshot" implies); load in topological order with NULL-then-UPDATE for cycle-break edges; or flip FKs `DEFERRABLE` and load one transaction under `SET CONSTRAINTS ALL DEFERRED` ([SET CONSTRAINTS](https://www.postgresql.org/docs/current/sql-set-constraints.html)). Avoid `session_replication_role = replica` as a default path: "setting this parameter to `replica` also disables all foreign key checks, which can leave data in an inconsistent state if improperly used", and "Only superusers and users with the appropriate `SET` privilege can change this setting" ([runtime-config-client](https://www.postgresql.org/docs/current/runtime-config-client.html)). pg_dump's `--disable-triggers` likewise "must be done as superuser" ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)). Managed Postgres frequently withholds both. This is also the pg_dump data-only trap that Supabase users hit: "there are circular foreign-key constraints on this table", "You might not be able to restore the dump without using --disable-triggers or temporarily dropping the constraints", "Consider using a full dump instead of a --data-only dump to avoid this problem" ([pg_dump_sort.c](https://raw.githubusercontent.com/postgres/postgres/master/src/bin/pg_dump/pg_dump_sort.c), [Supabase discussion](https://github.com/orgs/supabase/discussions/29993)). A tool that owns the target schema never sees it.

**User triggers on the target.** "`COPY FROM` will invoke any triggers and check constraints on the destination table. However, it will not invoke rules" ([COPY](https://www.postgresql.org/docs/current/sql-copy.html)). An audit trigger double-writes; a validation trigger rejects masked rows. `ALTER TABLE … DISABLE TRIGGER USER` disables only user triggers, excluding "internally generated constraint triggers, such as those that are used to implement foreign key constraints"; disabling those "requires superuser privileges" ([ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)). Do it per table, re-enable after, and say so in the output.

**Transactions and speed knobs.** One transaction per table. `COPY … FREEZE` is "intended as a performance option for initial data loading", but "Rows will be frozen only if the table being loaded has been created or truncated in the current subtransaction", "It is currently not possible to perform a `COPY FREEZE` on a partitioned table", and it "violates the normal rules of MVCC visibility" ([COPY](https://www.postgresql.org/docs/current/sql-copy.html)). `SET LOCAL synchronous_commit = off` per transaction is safe for a throwaway target: "setting this parameter to `off` does not create any risk of database inconsistency", only of losing "some recent allegedly-committed transactions" on a crash, and "It is therefore possible, and useful, to have some transactions commit synchronously and others asynchronously" ([runtime-config-wal](https://www.postgresql.org/docs/current/runtime-config-wal.html)). Raising `maintenance_work_mem` "will help to speed up `CREATE INDEX` commands and `ALTER TABLE ADD FOREIGN KEY` commands" but not COPY itself; raising `max_wal_size` reduces checkpoints during the load ([populate](https://www.postgresql.org/docs/current/populate.html)); both are session hints, not requirements. Load independent tables (same DAG level) in parallel, as pgcopydb does with `--table-jobs` and by splitting large tables with `--split-tables-larger-than` ([pgcopydb clone](https://pgcopydb.readthedocs.io/en/latest/ref/pgcopydb_clone.html)).

**Batch size and memory on the load path.** `CopyFromFunc` streams rows to the server as it produces them rather than buffering the whole table, so the practical bound is not "rows per CopyFrom call" — a `CopyFrom` call is naturally one call per table — but how far the extract-transform-load pipeline is allowed to run ahead of what has actually been sent over the wire. Structure it as extract → transform → a bounded channel → `CopyFromFunc` pulling from that channel, and size the channel in rows, not bytes, capped low (a few thousand rows is enough to keep the network saturated without holding an unbounded number of transformed rows in memory); a channel with no cap turns a slow target connection into unbounded growth of buffered rows on a fast source. On when `SendBatch` beats `CopyFrom`: per the benchmark already cited in §4.1, it does not, for this workload — 50,000 rows via `CopyFrom` at 140 ms versus `SendBatch` at 880 ms locally, and the gap does not reappear in lazysnap's favor at low latency; `SendBatch`'s advantage shows up only when a workload needs mixed statement types pipelined together, which a straight table load does not need ([Gold Lapel benchmark](https://goldlapel.com/grounds/go-postgres/pgx-bulk-insert-benchmarks)). The one place the same benchmark's convergence result matters is a cross-region link: at 67 ms round-trip latency all three bulk methods converge to about 71–79 ms per 500 rows because "the single network round trip dominates," so on a high-latency source-to-target path the choice between `CopyFrom` and `SendBatch` stops mattering and batching more rows per round trip is what matters instead ([Gold Lapel benchmark](https://goldlapel.com/grounds/go-postgres/pgx-bulk-insert-benchmarks)).

**Key lookups at scale.** Chunk keys (a few thousand per query), join against `unnest`, keep a fixed statement shape so pgx's default statement cache reuses one prepared statement ([pgx v5](https://pkg.go.dev/github.com/jackc/pgx/v5)). A temp table on the source is faster for millions of keys (msg555/subsetter does exactly that, [subsetter](https://github.com/msg555/subsetter)), but it is a write to a source session and some managed environments revoke `TEMPORARY`; the CONCEPT's "never holds write access to the source" argues for arrays. For composite keys use multi-array `unnest` (section 1.2).

**Server-side cursors.** Needed only when you must pause a result set and reuse the connection, or bound the server's memory for a sorted query: `DECLARE … NO SCROLL CURSOR` inside a transaction ("`DECLARE` without `WITH HOLD` is useless outside a transaction block") and `FETCH n`; `WITH HOLD` copies rows "into a temporary file or memory area" at commit ([DECLARE](https://www.postgresql.org/docs/current/sql-declare.html)). The wire protocol's `Execute` takes "a maximum result-row count (zero meaning 'fetch all rows')" and answers with `PortalSuspended` when it stops early ([protocol flow](https://www.postgresql.org/docs/current/protocol-flow.html)), but I found no pgx v5 API exposing that row limit (unverified), so use `DECLARE`/`FETCH` if you need it. With pgx streaming and chunked key joins, you usually do not.

**Text versus binary COPY.** Binary is "Somewhat faster than the text and CSV formats, but a binary-format file is less portable across machine architectures and PostgreSQL versions" and "very data type specific; for example it will not work to output binary data from a `smallint` column and read it into an `integer` column" ([COPY](https://www.postgresql.org/docs/current/sql-copy.html)); PG14 improved "the performance of `COPY FROM` in binary mode" ([PG14 notes](https://www.postgresql.org/docs/release/14.0/)). Greenmask chose text so it can rewrite fields in the stream ([Greenmask architecture](https://docs.greenmask.io/latest/architecture/)). With pgx's typed `CopyFrom` you get binary on the load side for free; a raw `PgConn.CopyTo` → `PgConn.CopyFrom` text pass-through is the fast path for tables with no masked columns, at the cost of hand-parsing COPY text escaping if you ever touch a field. Note pgconn's caveat that context cancellation "will only interrupt operations on the underlying PostgreSQL network connection. Reads on r could still block" ([pgconn](https://pkg.go.dev/github.com/jackc/pgx/v5/pgconn)).

### 4.3 Traps

- **The exported snapshot has a lifetime cost on the source.** Holding a `REPEATABLE READ` transaction open for the run's whole duration pins the source's xmin horizon: rows other transactions delete or update during that window cannot be vacuumed away until the snapshot-holding transaction ends, because "the xmin horizon tells you up to which point the vacuum process can clean up dead rows" and a long-running transaction holds that horizon back ([pganalyze: VACUUM blocked by xmin horizon](https://pganalyze.com/docs/checks/vacuum/xmin_horizon)). The plan step should estimate and print how long the snapshot will need to be held (roughly, the time the worklist plus every extract query is expected to take) so an operator can judge whether that is acceptable against the source's write volume, rather than discovering bloat afterward. On a hot standby the same long-held snapshot is more fragile, not just costly: streaming replay applies WAL as it arrives, and a standby query that conflicts with an about-to-be-applied WAL entry is cancelled once `max_standby_streaming_delay` (default 30 seconds) is exceeded — "this parameter determines how long the standby server should wait before canceling standby queries that conflict with about-to-be-applied WAL entries" ([runtime-config-replication](https://www.postgresql.org/docs/current/runtime-config-replication.html)). "Point it at production" in practice often means pointing it at a read replica, and a multi-minute snapshot-held extract there is exactly the shape of query that gets cancelled mid-run on a busy primary; either raise `max_standby_streaming_delay` for the run (an operator decision, not lazysnap's to make silently) or treat replica cancellation as an expected failure mode with a clear retry-the-whole-snapshot message, not a generic error.
- **Deferred checks fail at COMMIT.** With deferred FKs a violation surfaces at commit, after the whole load, and the per-row trigger queue is what overflows memory ([populate](https://www.postgresql.org/docs/current/populate.html)). Post-data FK creation fails per constraint, with a name.
- **A failed COPY leaves dead rows.** "If the command fails, these rows are left in a deleted state; these rows will not be visible, but still occupy disk space" and "`VACUUM` should be used to recover the wasted space" ([COPY](https://www.postgresql.org/docs/current/sql-copy.html)). Per-table transactions make a failure roll back cleanly; vacuum on retry.
- **`ON_ERROR ignore` is not for you.** PG17 added it, with `LOG_VERBOSITY` to report ignored rows ([PG17 notes](https://www.postgresql.org/docs/release/17.0/)), and "The `ignore` option is applicable only for `COPY FROM` when the `FORMAT` is `text` or `csv`" ([COPY](https://www.postgresql.org/docs/current/sql-copy.html)). Silently dropping rows breaks the integrity promise.
- **Masked partition keys.** Rows route by the *masked* value; a row that "does not map to one of the existing partitions will cause an error", and "`BEFORE ROW` triggers on `INSERT` cannot change which partition is the final destination" ([partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)). Hash partitions on a masked column scatter; range partitions on a shifted date fall off the end. Detect partition-key columns at plan time and either exclude them from masking with an explanation or fail early.
- **Masked columns under unique indexes on expressions.** `lower(email)` again ([expression indexes](https://www.postgresql.org/docs/current/indexes-expressional.html)); and on partitioned tables a unique constraint's "columns must include all of the partition key columns" ([partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)), so a masked partition key is also a masked unique key.
- **Sequence below the data.** Reassign IDs or forget `setval` and the first app insert collides (condenser #14). And because `setval` survives rollback ([functions-sequence](https://www.postgresql.org/docs/current/functions-sequence.html)), set it after the data commit, not before.
- **Enum and custom types in CopyFrom.** Register them per connection or fail on the first row ([pgx #1338](https://github.com/jackc/pgx/issues/1338)). Load `pg_type` for the schema in `AfterConnect`.
- **One connection doing two things.** Fetching parents while a `Rows` is open on the same connection breaks ([pgx v5](https://pkg.go.dev/github.com/jackc/pgx/v5)). This is a per-connection rule, not a total-connection-count rule: any single connection must not be asked to hold an open result set and serve a second query at the same time, however many connections the run has in total.
- **Row-level security on the target.** "Currently, `COPY FROM` is not supported for tables with row-level security. Use equivalent `INSERT` statements instead" ([COPY](https://www.postgresql.org/docs/current/sql-copy.html)). Detect `relrowsecurity` and fall back or fail early.
- **Column count edge cases.** Greenmask's COPY decoder panicked on tables with more than 128 columns because of a fixed-size array ([Greenmask #444](https://github.com/GreenmaskIO/greenmask/issues/444), via [COMPETITORS.md](COMPETITORS.md)). Test with a 300-column table.
- **`--load-via-partition-root`-class surprises.** Collation differences between source and target change routing for text partition keys ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)); target the root, always.
- **Giant literal key lists.** Section 1.3; chunked `unnest` joins avoid both the parser cost and any version-specific planner quirk.

## What this implies for lazysnap v1 (for the ADRs, not decided here)

1. Subsetting is a client-side monotone worklist with provenance-tagged queue entries (`CHILD_OK` vs `PARENT_ONLY`): parents uncapped, children capped and depth-limited and followed only from `CHILD_OK` rows, lookup tables whole, a row budget and a client-memory byte budget, and a plan printed before extraction. Composite keys as tuples; `MATCH SIMPLE` NULL rules; polymorphic pairs inferred and reported; row identity falls back from PK to unique index to inferred pseudo-key to `ctid`, reported per table. The whole run is read against one exported source snapshot, held for a duration the plan estimates up front. No SQL-side recursion on the source.
2. Masking is HMAC-SHA256 under per-category HKDF subkeys, key outside the yml, canonicalization per category, categories propagated along FK edges, ≥ 64-bit-domain generators for any column under a unique index whose type can hold one — a column whose type cannot (a short `varchar`, a `CHECK`-constrained format) is refused by name rather than resolved by collision or retry — no FPE, no retries on collision.
3. Classification is names + types + validated samples + dictionaries, with a reason per column, a neighbouring-column rule for context, whole-value masking for JSON and free text, and fail-closed on unknown columns. No cloud model over values.
4. Load is COPY via pgx with explicit column lists and types registered in `AfterConnect`, pre-data/data/post-data split, FKs and indexes created last as the verification step, a source-snapshot-holder connection plus a source reader pool plus a target pool sized by table-parallelism (never one connection serving two open operations at once), per-table transactions, `setval` after commit with the strict-function empty-table case handled explicitly, partition roots as targets, `ANALYZE` at the end.
