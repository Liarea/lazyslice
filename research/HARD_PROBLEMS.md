# Hard problems: subsetting, deterministic masking, PII classification, streaming Postgres

Technical survey for the engineer implementing lazysnap's pipeline in Go. Four problems, each in the same shape: the simplest approach that is actually correct, the refinement that makes it good, and the trap that catches implementers. Every claim links to its source. Tool status was checked on 2026-09-04; "unverified" marks anything I could not confirm.

Vocabulary used throughout, because the field does not agree on it:

- **Parent** row: the row a foreign key points at (the referenced side). **Child** row: the row holding the foreign key (the referencing side).
- **Parents to completeness**: every parent of every selected row must be included or the target will reject the load. Non-negotiable.
- **Children**: optional. This is where subsets explode.
- Tonic and condenser call child tables "upstream" and parent tables "downstream" ([Tonic docs](https://docs.tonic.ai/app/generation/subsetting/subsetting-about), [condenser README](https://github.com/TonicAI/condenser)). Jailer calls parent-direction edges "dependencies" and child-direction edges "associations" ([Jailer Association API](https://wisser.github.io/Jailer/api/net/sf/jailer/datamodel/Association.html)). Read every source with this inversion in mind.

## 1. Subsetting: walking the foreign-key graph

### What the graph looks like in Postgres

Everything you need is in `pg_constraint`. For `contype = 'f'`: `conrelid` is the child table, `confrelid` the parent, `conkey` and `confkey` are position-aligned `int2[]` arrays of column numbers (composite keys are just arrays longer than one), `confmatchtype` is `f` full / `p` partial / `s` simple, `condeferrable` and `condeferred` tell you whether the constraint can be deferred, and `convalidated` tells you whether the source actually trusts it ([pg_constraint docs](https://www.postgresql.org/docs/current/catalog-pg-constraint.html)). A foreign key must target "columns that either are a primary key or form a unique constraint, or are columns from a non-partial unique index" ([ddl-constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)), so every edge has a unique target you can key on.

### 1.1 Simplest correct approach: a monotone worklist

Keep, per table, a set of selected primary keys. Seed the root table's set (500 customers, or a `WHERE`). Then loop:

```
queue := [(root, rootKeys)]
for (t, keys) := pop(queue); keys != nil {
    new := keys − selected[t]; selected[t] ∪= new
    // parents: mandatory, uncapped
    for fk := range outgoing(t) {                       // t.(conkey) → parent.(confkey)
        pk := SELECT DISTINCT fk.cols FROM t WHERE t.pk IN new AND fk.cols IS NOT NULL
        push(parent(fk), pk − selected[parent(fk)])
    }
    // children: optional, capped, depth-limited
    for fk := range incoming(t) {                       // child.(conkey) → t.(confkey)
        ck := SELECT child.pk FROM child WHERE fk.cols IN new   (≤ cap per parent key)
        push(child(fk), ck − selected[child(fk)])
    }
}
```

Every set only grows and every set is finite, so the loop terminates; the parent step guarantees that when it terminates, every selected row's parents are selected. That is the whole correctness argument, and it holds for cycles and self-references without special casing: a self-referencing `employees.manager_id` just keeps pushing `employees` until the chain of managers is closed.

This is what condenser does, in two directions: it "greedily grabs as many rows from the database as it can, based on the rows already imported" for children, and pulls parents for integrity ([condenser README](https://github.com/TonicAI/condenser)). Tonic's product is the same idea with names: target tables seed, "downstream" (parent) tables are pulled because their records are required for referential integrity, while "upstream" (child) records can be filtered by date or `WHERE` ([Tonic: about subsetting](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)). Snaplet's algorithm had the same two classes with explicit knobs: `followNullableRelations` (default true), `maxCyclesLoop` (default 1), `maxChildrenPerNode`, and `eager` (default false) for pulling extra parent data ([Snaplet capture docs, mirror](https://snaplet-snapshot.netlify.app/snapshot/core-concepts/capture)).

Lookup tables (countries, currencies, statuses) should be copied whole rather than walked; Phil Factor's rule is that enumeration-like tables "need to be copied in full because it can easily become impossible to add an entity" otherwise ([Simple Talk, 2024](https://www.red-gate.com/simple-talk/databases/theory-and-design/database-subsetting-and-data-extraction/)). Tonic has the same "lookup table" class ([Tonic docs](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)); condenser calls them `passthrough_tables` ([README](https://github.com/TonicAI/condenser)). A cheap zero-config heuristic: a table with no outgoing FKs, few rows (say under 1,000), and at least one incoming FK is a lookup table; copy it whole and say so.

Per-parent child caps in one query rather than one query per parent key: use a window function, `row_number() OVER (PARTITION BY fk_col ORDER BY pk) <= cap` ([window functions tutorial](https://www.postgresql.org/docs/current/tutorial-window.html)).

### 1.2 Refinements

**Cycles at load time.** The worklist handles cycles for *selection*; the problem is *insertion order*. Compute strongly connected components of the table graph (Tarjan, [Wikipedia](https://en.wikipedia.org/wiki/Tarjan%27s_strongly_connected_components_algorithm)); condense to a DAG; topologically sort (Kahn, [Wikipedia](https://en.wikipedia.org/wiki/Topological_sorting#Kahn's_algorithm)). Inside an SCC you have three options, and the field has converged on the first:

1. *NULL-then-UPDATE on a nullable FK.* Jailer 6.5: "Referential cycles can now be exported by deferring the insert of nullable foreign keys" ([release notes](https://github.com/Wisser/Jailer/blob/master/releasenotes.txt)). Tonic "identifies a foreign key column that is NULLable, and sets its values to NULL", using the minimum number of NULLs, and "if none of the foreign key values are NULLable… the subset generation fails" ([Tonic FK docs](https://docs.tonic.ai/app/generation/subsetting/subsetting-foreign-keys)). Neosync inserted with the nullable FK empty, cycled through the SCC, then came "back to the original starting table, and update in the foreign key reference into the nullable column" ([Neosync docs source](https://raw.githubusercontent.com/nucleuscloud/neosync/main/docs/docs/table-constraints/circular-dependencies.md)). condenser's blog gives the reason this always works when any row exists at all: "Any cycle of foreign key columns will contain at least one NULLable column, otherwise you wouldn't be able to insert the first row" ([Tonic blog](https://www.tonic.ai/blog/condenser-a-database-subsetting-tool)). Deferrable constraints are the exception to that argument; see the trap below.
2. *Deferred constraints.* `SET CONSTRAINTS ALL DEFERRED` postpones checks to commit, but only for constraints declared `DEFERRABLE`; `NOT DEFERRABLE` ones are "always IMMEDIATE and… not affected" ([SET CONSTRAINTS](https://www.postgresql.org/docs/current/sql-set-constraints.html)). You can flip an FK with `ALTER TABLE … ALTER CONSTRAINT … DEFERRABLE` (the docs say only foreign key constraints can be altered this way, [ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)) because you own the target.
3. *Create FKs after the data.* This is what pg_dump does: the post-data section holds "indexes, triggers, rules… and constraints other than validated check and not-null constraints" ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)); pgcopydb builds "constraints… by the CREATE INDEX processes" after all table data ([pgcopydb](https://github.com/dimitri/pgcopydb)). Because lazysnap creates the target schema itself, option 3 removes ordering from the load path entirely and turns "verify foreign keys" into "the post-data FK creation succeeded". Section 4 argues for this as the default.

Choosing *which* edges to break to make the SCC acyclic with the fewest breaks is the minimum feedback arc set, NP-hard in general (one of Karp's 21 problems, [Wikipedia](https://en.wikipedia.org/wiki/Feedback_arc_set)). Schema graphs have a handful of nodes per SCC, so brute force or greedy is fine; do not write a clever algorithm. Greenmask's subset pushes cycles into SQL instead: it generates a recursive query per SCC and can resolve "multi-cycles in one strongly connected component, but only for one group of vertexes", a limit the authors say "99% of people will not face" ([Greenmask subset docs](https://docs.greenmask.io/dev/database_subset/), [issue #147](https://github.com/GreenmaskIO/greenmask/issues/147)).

**Self-references.** The worklist closes an ancestor chain in as many round trips as the chain is deep. To do it in one query use `WITH RECURSIVE`, and on PG14+ add the SQL-standard `CYCLE col SET is_cycle USING path` clause so cyclic data (A manages B manages A, legal when the FK is nullable) cannot loop forever ([WITH queries](https://www.postgresql.org/docs/current/queries-with.html), [PG14 release notes](https://www.postgresql.org/docs/release/14.0/)). Jailer's maintainer diagnosed a runaway export as "a reflexive association of the subject table with itself" and pointed at its `$DISTANCE` and `$IS_SUBJECT` restriction variables plus a `-row-limit` safeguard ([SourceForge thread](https://sourceforge.net/p/jailer/discussion/700499/thread/953062b743/)). Copy the idea: a depth limit on child-direction traversal and a hard row budget that aborts planning with a clear message.

**Composite keys.** Treat a key as a tuple, never as a joined string. `conkey`/`confkey` are aligned by position; resolve attnums via `pg_attribute`. For lookups, pass parallel arrays: `WHERE (a, b) IN (SELECT * FROM unnest($1::int[], $2::text[]))`; multi-array `unnest` "is only allowed in a query's FROM clause" and pads short arrays with NULLs ([array functions](https://www.postgresql.org/docs/current/functions-array.html)). NULL semantics differ by match type: under the default `MATCH SIMPLE` a child row "need not satisfy the foreign key constraint if any of its referencing columns are null", while `MATCH FULL` fails on "a mix of null and non-null values" ([ddl-constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)). So for `MATCH SIMPLE` a composite FK with one NULL column references nothing: skip it in the parent step, or you will query for a parent that cannot exist.

**Polymorphic associations without constraints.** Rails' `commentable_type` + `commentable_id` ([Rails guide](https://guides.rubyonrails.org/association_basics.html#polymorphic-associations)) and Django's `content_type` + `object_id` ([Django docs](https://docs.djangoproject.com/en/stable/ref/contrib/contenttypes/#generic-relations)) carry no FK. Every tool handles this with user config: condenser's `fk_augmentation` is "unioned with the foreign keys provided by constraints" ([README](https://github.com/TonicAI/condenser)); Tonic has "virtual foreign keys" ([docs](https://docs.tonic.ai/app/generation/subsetting/subsetting-foreign-keys)); Greenmask has virtual references with `polymorphic_exprs` such as `public.comments.commentable_type = 'post'` and notes such references "cannot be non_null" ([Greenmask subset docs](https://docs.greenmask.io/dev/database_subset/)); Jailer added a "Discover Associations" feature in 2026 ([site news](https://wisser.github.io/Jailer/)). For a zero-config tool: detect `<x>_type`/`<x>_id` pairs (and `content_type_id`/`object_id`), sample distinct `_type` values, map them to table names (the Rails value is a class name: underscore and pluralize), treat each mapping as a virtual FK for the parent step, and print what you inferred. If a `_type` value maps to nothing, say so; the FK verification at the end cannot catch it because there is no constraint to violate.

**Children of the root versus everything reachable.** These are different products. "Everything reachable" through child edges from 500 customers on a real schema is most of the database: orders pull products, products pull suppliers, suppliers pull every other order for that supplier if you let child edges run from a parent you reached. Snaplet's docs warn the row count "may not be exact" and "a 5% subset… may ultimately include more than 5% of the actual database" ([Snaplet docs](https://snaplet-snapshot.netlify.app/snapshot/core-concepts/capture)). Tonic restricts child pulls to tables upstream of *targets* and, when a table is upstream of several, keeps only rows referencing targeted records "in all of the target tables" ([Tonic docs](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)). The rule that keeps size predictable: follow child edges only from rows reached by child edges (root → its children → their children), never from rows reached by the parent step. Parents pulled for completeness are leaves for child traversal. Cap children per parent and total depth; plan before extracting and show the estimate, as the CONCEPT's "planning… 23 tables in slice, ~18k rows" line already promises.

**SQL pushdown versus client worklist.** Greenmask does not walk keys in the client; it turns each table's subset into a `SELECT … INNER JOIN parent … WHERE cond`, with `LEFT JOIN` for nullable references and a recursive CTE for SCCs, and it warns it "cannot be responsible for query optimization" and that unindexed condition columns make it slow ([Greenmask subset docs](https://docs.greenmask.io/dev/database_subset/)). Its worked example propagates a condition on `businessentity` to `businessentitycontact`, i.e. parent to child; how it restricts the parent side of a conditioned table is not spelled out in the pages I read, so verify before copying the design. Pushdown gives one streaming query per table and no key sets in memory; the worklist gives explicit caps, explicit explanations, and no reliance on the source planner. For a tool that must print "why this row is here", the worklist wins.

**Academic framing.** Join Synopses (Acharya, Gibbons, Poosala, Ramaswamy, SIGMOD 1999, [DOI](https://dl.acm.org/doi/10.1145/304182.304207)) define exactly our invariant: if a tuple is sampled, the tuples it references must be too, and they show that closure inflates sample size. Linked Bernoulli Synopses (Gemulla, Rösch, Lehner, SSDBM 2008, [PDF](https://www.uni-mannheim.de/media/Einrichtungen/dws/Files_People/Profs/rgemulla/publications/gemulla08fksampling.pdf)) shrink the inflation by correlating the per-table sampling decisions along the foreign key, so the parent a child needs is likely already in. The practical reading for lazysnap: inflation is inherent to sampling in the middle of the graph; start at a root with no parents of its own (customers, tenants, accounts) and it stays bounded. Dscaler (Zhang, Tay, VLDB 2016, [DOI](https://dl.acm.org/doi/10.14778/3007328.3007333)) treats scale factor s < 1 as the application-development case and reproduces key correlations synthetically; relevant only if v2 wants "representative" rather than "everything about these 500 customers".

### 1.3 Traps

- **The explosion is in child edges from parents.** See above. Jailer's own forum has a user whose unattended export "tried to collect data indefinitely" ([thread](https://sourceforge.net/p/jailer/discussion/700499/thread/953062b743/)). Budget, depth, and a plan step are not polish; they are the difference between a tool that finishes and one that does not.
- **Unindexed FK columns on the source.** The child step is `WHERE fk_col IN (...)` against the child table; Tonic warns that "if the foreign key columns are not indexed, the subsetting process can be significantly slower" ([Tonic docs](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)). Postgres does not index FK columns automatically. Check `pg_index` during planning and warn per edge.
- **`= ANY(ARRAY[...])` with big arrays.** Datadog turned a 22 s query into 0.2 s by replacing `ANY(ARRAY[...])` with `ANY(VALUES (...))` for about 11,000 keys because "the query optimizer is fooled by the use of ARRAY[...]" ([Datadog](https://www.datadoghq.com/blog/100x-faster-postgres-performance-by-changing-1-line/)); a pgsql-general thread on thousands of values reports the same class of problem and suggests VALUES or a temp table ([mailing list](https://postgresql.org/message-id/986190718.20200831123700%40am-soft.de)). PG14 added hash lookup for `IN` lists of constants ([PG14 notes](https://www.postgresql.org/docs/release/14.0/)) and PG17 made btree scans over sets of values more efficient ([PG17 notes](https://www.postgresql.org/docs/release/17.0/)), but the safe pattern is a join against `unnest($1)` in chunks of a few thousand keys.
- **Hidden relationships.** Phil Factor: relationships defined in application code rather than as constraints are the hard case ([Simple Talk](https://www.red-gate.com/simple-talk/databases/theory-and-design/database-subsetting-and-data-extraction/)). The FK check will pass and the app will 500. Report FK-less `*_id` columns as a warning.
- **Cycles with no nullable FK.** Possible only with deferrable constraints or bulk-loaded data; NULL-then-UPDATE cannot break them. Post-data FK creation (option 3) does not care.
- **Composite FK with partial NULLs under MATCH SIMPLE.** Skip, do not look up. Under MATCH FULL the source row is already invalid unless the constraint was created `NOT VALID` (`convalidated = false`); treat unvalidated FKs as hints, not guarantees.
- **Tables not connected to the root.** Tonic copies only their schema by default ([Tonic docs](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)); condenser distinguishes `excluded_tables` (empty) from passthrough. Pick one default, say it in the plan output, and never silently copy a disconnected 200 GB events table.
- **Percent is a lie.** Snaplet's docs say so ([Snaplet docs](https://snaplet-snapshot.netlify.app/snapshot/core-concepts/capture)). Plan in row counts and print the estimate.

## 2. Deterministic masking

### 2.1 Simplest correct approach: keyed hash to seed, per semantic category

The requirement is that the same input produces the same fake everywhere it appears, so joins on masked columns still match, and that nothing about the mapping is guessable without a secret. That is a keyed pseudorandom function, not a hash and not a seeded sequence.

```
K      := 32 random bytes, generated once per project, stored outside lazysnap.yml
K_cat  := HKDF(K, info = "lazysnap/v1/" + category)       // one subkey per semantic category
h      := HMAC-SHA256(K_cat, canonical(value))            // 32 bytes, deterministic
fake   := generator[category](h)                          // h drives every choice the generator makes
```

HMAC is [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104); HKDF is [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869) and is in the Go standard library as `crypto/hkdf` with `Extract`, `Expand`, `Key` ([pkg.go.dev](https://pkg.go.dev/crypto/hkdf)); `crypto/sha3` is also stdlib if you prefer SHA-3 ([pkg.go.dev](https://pkg.go.dev/crypto/sha3)). Generators consume `h` as a random source: index a name list, build an email local part from a base32 slice, pick digits for a phone. Do not seed a global faker and call it in row order; a seeded sequence depends on call order and is not a mapping.

Everyone who has shipped this landed on the same design. copycat "hashes the input values (using SipHash)" so that "for the same input, the same value will be returned regardless of the environment, process, call ordering", and `setHashKey` exists so attackers with the code still "are not able to figure out which inputs map to which outputs" ([copycat README](https://github.com/snaplet/copycat)). Greenmask's `hash` engine uses SHA-3 with a salt from `GREENMASK_GLOBAL_SALT`, "added to the hash input to prevent the possibility of reverse engineering" ([Greenmask engines](https://docs.greenmask.io/latest/built_in_transformers/transformation_engines/)). PostgreSQL Anonymizer's `pseudo_*` functions take a seed and an optional salt, fall back to the `anon.salt` GUC, and the docs insist "the salt and the algorithm… must be protected with the same level of security that the original dataset" ([pg_anonymizer](https://postgresql-anonymizer.readthedocs.io/en/stable/masking_functions/)). Tonic synchronizes deterministic output across runs with a "statistics seed" ([Tonic guide](https://www.tonic.ai/guides/deterministic-masking-explained), [consistency docs](https://docs.tonic.ai/app/generation/generators/generator-characteristics/consistency)).

Why a key rather than a salt: the EDPB's 2025 pseudonymisation guidelines treat MACs (keyed) as stronger than plain hashing and are explicit that pseudonymised data is still personal data ([EDPB Guidelines 01/2025](https://www.edpb.europa.eu/system/files/2025-01/edpb_guidelines_202501_pseudonymisation_en.pdf)); pg_anonymizer's docs warn that an attacker holding the salt and the masking rule can re-identify people by brute force or dictionary attack ([pg_anonymizer](https://postgresql-anonymizer.readthedocs.io/en/stable/masking_functions/)). Emails and names are low-entropy; an unkeyed hash of them is a lookup table waiting to be built.

Where the key lives matters for the "safe by default" principle: `lazysnap.yml` is meant to be committed for CI, so it can hold a key *fingerprint* but never the key. Read the key from an environment variable or the OS keyring; generate one on first run and tell the user where it went. Without it, a CI run still gets a fresh random key and internally consistent joins, just not the same fakes as the laptop.

**Canonicalize before hashing.** `Alice@Example.com` and `alice@example.com` must mask to the same fake if the app treats them as the same user, and the same value stored as `int` in one table and `text` in another must hash identically. Tonic's consistency doc is blunt that "consistency is a function of the both the data type and the value" and `123` versus `"123"` will not match ([Tonic consistency](https://docs.tonic.ai/app/generation/generators/generator-characteristics/consistency)). Canonicalize per category (trim, case-fold emails, strip phone formatting to E.164 with [nyaruka/phonenumbers](https://github.com/nyaruka/phonenumbers), NFKC-normalize names with [x/text/unicode/norm](https://pkg.go.dev/golang.org/x/text/unicode/norm)) and hash the canonical form.

**Propagate along foreign keys.** If a masked column is the target of an FK (users.email referenced by subscriptions.email), the referencing column must get exactly the same category and canonicalization, or the join breaks. Greenmask's `apply_for_references` exists for this, and requires a deterministic transformer with the `hash` engine ([Greenmask inheritance](https://docs.greenmask.io/latest/built_in_transformers/transformation_inheritance/)). In lazysnap the classifier's output for a unique/PK column must override whatever it decided for the FK columns pointing at it.

**Fake domains that cannot hit real people.** Use reserved names: `example.com` and the `.invalid` TLD are reserved by [RFC 2606](https://www.rfc-editor.org/rfc/rfc2606); for North American phones the 555-01XX block is reserved for fiction ([Wikipedia](https://en.wikipedia.org/wiki/555_(telephone_number))). Keeping the real domain (`@bigcorp.com`) leaks employer; decide this in the threat model, not in code.

### 2.2 Refinements

**Format-preserving encryption, and why v1 should not ship it.** FPE gives a keyed *permutation* of a domain (all 16-digit strings, all 9-digit numbers): deterministic, invertible, and collision-free by construction, which is exactly what you want for unique identifiers that must keep their shape. The state of the standard as of 2026-09-04:

- NIST SP 800-38G (2016) specified FF1 and FF3 ([CSRC](https://csrc.nist.gov/pubs/sp/800/38/g/upd1/final)). FF3 was broken over small domains in 2017 (Durak, Vaudenay, [Springer](https://link.springer.com/chapter/10.1007/978-3-319-63715-0_23)), then on large domains (Hoang, Miller, Trieu 2019, [Springer](https://link.springer.com/chapter/10.1007/978-3-030-17656-3_4)); FF3-1 is the patched variant and has its own analyses (Beyne, CRYPTO 2021, [PDF](https://iacr.org/archive/crypto2021/12826083/12826083.pdf); Amon et al. 2021, [Springer](https://link.springer.com/chapter/10.1007/978-3-030-77886-6_5)).
- Revision 1 raises the minimum domain size to one million (`radix^minlen ≥ 10^6`) and drops FF3 ([draft PDF](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-38Gr1-draft.pdf), [IPD page](https://csrc.nist.gov/pubs/sp/800/38/g/r1/ipd)); a second public draft closed comments 2025-04-04 and also forbids floating point in FF1 implementations ([CSRC news](https://csrc.nist.gov/news/2025/comment-on-the-2nd-draft-of-sp-800-38g-rev-1)). The final Rev. 1 URL returned 404 when I checked, so treat Rev. 1 as still a draft (final publication status: unverified).
- Go libraries: capitalone/fpe is archived and unreviewed since 2021 ([repo](https://github.com/capitalone/fpe)); ubiq-fpe-go is deprecated into a vendor SDK ([repo](https://github.com/ubiqsecurity/ubiq-fpe-go)); the remaining implementations are small personal projects ([go-fpe-bytes](https://github.com/Tensai75/go-fpe-bytes), [cloudtrust/fpe](https://pkg.go.dev/github.com/cloudtrust/fpe/fpe)); a stdlib proposal from 2017 went nowhere ([golang/go#18752](https://github.com/golang/go/issues/18752)).

Verdict: no maintained Go FF1 you would want to ship, a standard in flux, and small domains (4-digit PINs, 6-digit account suffixes) explicitly out of scope. If v2 needs it, implement FF1 from the spec against NIST's published example vectors ([CSRC example values](https://csrc.nist.gov/projects/cryptographic-standards-and-guidelines/example-values)) and restrict it to digit strings with domain ≥ 10^6. To keep an FPE output inside an irregular domain (valid dates, Luhn-valid card numbers), the standard trick is cycle walking: re-encrypt until the output lands in the domain (Black, Rogaway 2002, [PDF](https://www.cs.ucdavis.edu/~rogaway/papers/subset.pdf)); note it destroys checksums unless the checksum digit is recomputed after.

For v1 the pragmatic split is: surrogate keys (`id bigint`) are not PII and are not masked; natural identifiers that are PII (email, phone, national ID, card number) are replaced by keyed-hash-driven fakes with a domain large enough that collisions do not happen in practice.

**Unique-constraint collisions.** A keyed hash is not a permutation; two inputs can map to the same output. For n values drawn from a space of size d, P(collision) ≈ n²/2d ([birthday problem](https://en.wikipedia.org/wiki/Birthday_problem)). With a 64-bit-derived email local part, a million rows collide with probability about 2.7 × 10⁻⁸: ignore. With a generator whose domain is a list of 3,000 first names, 100 rows collide almost surely: that is fine for a `first_name` column and fatal for a column with a unique constraint. DataVeil's manual states the general fact: "multiple different original values can produce the same masked value", which causes "unique constraint violations", and it warns at compile time when a non-distinct mask hits a unique column ([DataVeil](https://www.dataveil.com/user-guide/topics/consistent-masking.htm)). Tonic: a consistent generator "does not guarantee that two different input values produce two different output values" ([Tonic consistency](https://docs.tonic.ai/app/generation/generators/generator-characteristics/consistency)); its Unique Email generator swaps the local part for a GUID and is documented as guaranteeing uniqueness only when the source column is itself unique ([Tonic Unique Email](https://docs.tonic.ai/app/generation/generators/generator-reference/unique-email)). Greenmask's hash engine "does not guarantee the uniqueness of generated values" and the feature is "under development" ([Greenmask engines](https://docs.greenmask.io/latest/built_in_transformers/transformation_engines/)). copycat offers `unique()` with an `attempts` counter defaulting to 10 ([copycat](https://github.com/snaplet/copycat)).

The implementable rule:

1. Introspect uniqueness properly: `pg_index.indisunique`, including expression indexes and partial indexes, not just `pg_constraint`. A unique index on `lower(email)` "would prevent creation of rows whose col1 values differ only in case" ([expression indexes](https://www.postgresql.org/docs/current/indexes-expressional.html)), so two masked emails differing only by case collide.
2. For any column under a unique index, use a generator whose domain is ≥ 2^64 and derive the value from the full hash (name-shaped fakes get a hash-derived suffix: `alice.k7v2x@example.com`). Say in the explanation that uniqueness forced the suffix.
3. Do not "retry with a counter" on collision. The retry depends on which row arrived first, so the mapping becomes order-dependent and the same value in another table (or another run) may resolve differently. If a column has a unique index and a small-domain generator is the only acceptable shape, refuse and explain rather than resolve at load time.

**Preserve what the application checks.** Length: `varchar(n)` (`atttypmod`) will reject a longer fake. `CHECK` constraints (`email ~ '@'`) and enum types constrain the shape. Validity: a phone that `libphonenumber` rejects breaks apps that validate on read ([phonenumbers](https://github.com/nyaruka/phonenumbers)). NULL stays NULL. Empty string stays empty.

### 2.3 Traps

- **Hashing without a key.** Dictionary attack on emails and names; see EDPB and pg_anonymizer above. Also the reason `md5(email)` "anonymization" scripts fail audits.
- **Key in the committed config.** Then every developer with the repo can reverse-map any masked value they can guess. Fingerprint in the file, key in the environment.
- **Frequency leaks.** Deterministic masking preserves frequency: the most common masked surname is still the most common real surname's alias, and a one-off value stays one-off. This is pseudonymisation under GDPR Article 4(5) ([gdpr-info](https://gdpr-info.eu/art-4-gdpr/)), not anonymisation; write that into the threat model instead of claiming otherwise. An HN commenter on Replibyte: "different pieces collected together can still identify particular persons" ([HN](https://news.ycombinator.com/item?id=31165538)).
- **Prefix-preserving masks.** Keeping the first character of a name is not safe; a Replibyte-thread commenter reported finding real customers behind first-character-preserving masks, particularly with Asian names ([HN](https://news.ycombinator.com/item?id=31165538)).
- **Classifier disagreement across a join.** `users.email` classified as email, `invoices.billing_email` classified as free text: masked with different generators, join broken. Propagate categories along FK edges and along identical column names before masking.
- **Faker version drift.** gofakeit's determinism is "same seed produces identical output across runs" for a given library version ([gofakeit](https://github.com/brianvoe/gofakeit)); when its word lists change, the mapping changes. Pin the version, embed your own lists for the categories that must be stable, and derive per-value seeds from `h`, never from a global sequence.
- **Partition keys and sequences.** Masking a column that is a partition key or an identity column moves rows to other partitions or beyond the sequence; details in section 4.

## 3. PII classification

### 3.1 Simplest correct approach: names plus types plus validated samples, with a reason string

Three signals, combined into a score with a human-readable reason. Every tool that ships this does the first two; the third is what makes the reason credible.

1. **Column and table names.** piicatcher's "shallow" scan was regexes over column names ([piicatcher](https://github.com/tokern/piicatcher)); Tonic's scan compares the table-plus-column name against each sensitivity type by semantic similarity with medium/low confidence bands ([Tonic scan docs](https://docs.tonic.ai/app/generation/identify-sensitive-data/running-the-structural-sensitivity-scan)). Table context matters: `name` in `products` is not PII, `name` in `users` is.
2. **Postgres types.** `inet`, `cidr`, `macaddr`, `uuid`, `citext`, `date` columns named `*birth*`, `bytea` (out of scope per CONCEPT), `jsonb` (see below). Domains over text (`CREATE DOMAIN email AS text`) are a gift: the domain name is the category.
3. **Sampled values through validators.** Sample with `TABLESAMPLE SYSTEM (p) REPEATABLE (seed)` (block-level, "significantly faster… but… less-random… as a result of clustering effects") or `BERNOULLI` ([SELECT docs](https://www.postgresql.org/docs/current/sql-select.html)). `pg_stats.most_common_vals` and `histogram_bounds` give you real values for free if the table has been analyzed, and the view "allows access only to rows… that correspond to tables the user has permission to read" ([pg_stats](https://www.postgresql.org/docs/current/view-pg-stats.html)). Run each sample through validators, not just regexes: Luhn for card numbers ([Wikipedia](https://en.wikipedia.org/wiki/Luhn_algorithm)) plus Presidio's length rule of 12 to 19 digits ([Presidio entities](https://presidio.dataprivacystack.org/supported_entities/)), mod-97 for IBAN ([Wikipedia](https://en.wikipedia.org/wiki/International_Bank_Account_Number#Validating_the_IBAN)), `net/mail.ParseAddress` for email ([pkg.go.dev](https://pkg.go.dev/net/mail#ParseAddress)), `net.ParseIP`, libphonenumber's `IsValidNumber` ([phonenumbers](https://github.com/nyaruka/phonenumbers)), a UUID parser, and a names dictionary. Presidio's own design is this: pattern matching plus checksums for structured identifiers, NER for names, context words to lift confidence ([Presidio entities](https://presidio.dataprivacystack.org/supported_entities/)).

Combine: a name hit alone is medium; a name hit plus ≥ 80% of samples validating is high; samples validating with no name hit is medium with the reason "values look like X"; special categories by name alone are high because the cost of missing them is highest. Print the reason ("column `users.email`: name matches email; 100/100 sampled values parse as addresses"). Bias toward recall; the CLAUDE.md rule is "when in doubt, mask it".

**Categories a first release must catch.** Take the union of HIPAA Safe Harbor's 18 identifiers ([45 CFR 164.514(b)(2)](https://www.law.cornell.edu/cfr/text/45/164.514)) and GDPR's definition plus Article 9 special categories ([Art. 4](https://gdpr-info.eu/art-4-gdpr/), [Art. 9](https://gdpr-info.eu/art-9-gdpr/)), then add what engineers actually put in databases:

| Category | Name signals (examples) | Value signals | Default action |
|---|---|---|---|
| Person name | `first_name`, `last_name`, `full_name`, `name` in person-like tables, `display_name` | dictionary hit rate; capitalized tokens | fake name (keyed) |
| Email | `email`, `e_mail`, `*_email`, `contact` | `ParseAddress` | fake email at reserved domain |
| Phone / fax | `phone`, `mobile`, `tel`, `fax`, `msisdn` | libphonenumber valid | fake phone in fictional range |
| Postal address | `address`, `street`, `city`, `postcode`, `zip`, `line1` | mixed digits + words | fake address; zip → HIPAA 3-digit rule is a v2 option |
| Geolocation | `lat`, `lng`, `latitude`, `geom`, `location` | numeric ranges, PostGIS types | jitter or fixed point |
| Dates about a person | `dob`, `birth*`, `date_of_birth`, `died` | date type | shift or year-only |
| National / government IDs | `ssn`, `nino`, `passport`, `tax_id`, `national_id`, `driver*licen*` | country-specific formats, checksums | fake with same shape |
| Financial account | `iban`, `account_number`, `card`, `pan`, `routing`, `sort_code` | Luhn, mod-97 | fake with valid checksum |
| Network identifiers | `ip`, `ip_address`, `mac`, `user_agent`, `device_id`, `imei` | `net.ParseIP`, inet/macaddr types | fake in documentation ranges |
| Online identifiers | `username`, `handle`, `login`, `url`, `avatar_url`, `profile` | URL parse | fake handle / URL |
| Credentials and secrets | `password`, `*_hash`, `token`, `secret`, `api_key`, `otp` | high Shannon entropy | replace with a fixed unusable value |
| Free text about people | `notes`, `comment`, `description`, `bio`, `message`, `body`, `reason` | NER hits in samples | replace whole value with same-length filler |
| Special categories (GDPR 9) | `gender`, `ethnicity`, `race`, `religion`, `health`, `diagnosis`, `disability`, `sexual*`, `union` | enum-like low cardinality | mask by name alone; never pass through |
| Photos / biometrics | `photo`, `image`, `face`, `fingerprint` | bytea | NULL out (blobs are out of scope) |
| Semi-structured | `jsonb`, `json`, `hstore`, `text[]` with any of the above as keys | key names in samples | see below |

Secrets need entropy, not names: detect-secrets ships two heuristics with default Shannon-entropy limits of 4.5 for Base64-looking strings and 3.0 for hex, and its docs say they "may require tuning" ([detect-secrets](https://github.com/Yelp/detect-secrets)). Use them on short text columns only; a UUID column trips the hex detector by design, so check the UUID parser first.

### 3.2 Refinements

**Multilingual names.** Presidio's default configuration "contains recognizers and models for English", and while regexes are language agnostic "the context words used to increase the PII detection confidence aren't" ([Presidio languages](https://presidio.dataprivacystack.org/analyzer/languages/)). A dictionary is the honest v1 answer: the name-dataset project extracted 730K first names and 983K last names across 106 countries from a leaked Facebook dump and needs about 3.2 GB of RAM in full ([name-dataset](https://github.com/philipperemy/name-dataset)); embed a trimmed top-N-per-country list with `go:embed`, NFKC-normalize and case-fold before lookup, and treat the dictionary as confirmation for a name-shaped column rather than as the sole trigger. Do not keep first characters or lengths of names (see the HN trap in section 2).

**JSON and free text.** Presidio Structured can analyze JSON via `JsonAnalysisBuilder` but "nesting objects in lists is not supported" without manual configuration, and picks a per-column entity by majority, highest confidence, or a mixed threshold strategy ([Presidio structured](https://presidio.dataprivacystack.org/structured/)). Greenmask's `Json` transformer masks by explicit path with `set`/`delete` operations and templates ([Greenmask Json](https://docs.greenmask.io/latest/built_in_transformers/advanced_transformers/json/)), i.e. it does not find PII in JSON for you. Zero-config version: sample rows, collect top-level (and one level nested) keys with `jsonb_object_keys` / `jsonb_each` ([JSON functions](https://www.postgresql.org/docs/current/functions-json.html)), run the column-name heuristics over key names, and if any key hits, mask that key's values at every path using the same category generators, keeping structure. If keys vary wildly per row (event payloads), fall back to replacing the whole document with `{}` and say why. Free text cannot be classified reliably from samples; classify it by column name and by NER hits in samples, and when it is masked, replace the whole value. Partial redaction of prose is a research problem, not a v1 feature.

**Where ML is and is not worth it.** Numbers from 2025 to 2026 evaluations:

- On four datasets, Presidio averaged macro-F1 0.608 for column-level personal-data detection, CASSED (a DistilBERT classifier) 0.643, and GPT-4o with column names, neighbouring columns and the ten most frequent values 0.865. CASSED scored 0.996 on the synthetic set it was trained on and 0.349 on Kaggle tables, the textbook overfit. The authors still judge false negatives "too high for practical applications" and flag sending data to a cloud model ([arXiv 2506.22305](https://arxiv.org/html/2506.22305v1)).
- Sherlock reaches support-weighted F1 0.89 over 78 semantic types, beating dictionary and regex baselines, using 1,588 features and 686,765 training columns ([arXiv 1905.10688](https://arxiv.org/abs/1905.10688)). Impressive, and it needs a model file and a training corpus you do not have.
- For PII in free text, the best small model in a 2026 comparison (GLiNER2-PII, 0.3B parameters, 42 types, seven European languages) averages span F1 0.471 on the SPY benchmark and "tends to over-predict name entities" ([arXiv 2605.09973](https://arxiv.org/html/2605.09973v1)). Recall 0.68 to 0.72 is not a safety property.
- A 2025 paper on contextual sensitivity argues regex and generic NER miss context-dependent sensitivity and that column context helps, on humanitarian and health data ([arXiv 2512.04120](https://arxiv.org/pdf/2512.04120)).
- Tonic's commercial scan is an LLM over table and column *names*, producing a similarity score, not a value classifier ([Tonic scan docs](https://docs.tonic.ai/app/generation/identify-sensitive-data/running-the-structural-sensitivity-scan)).

Reading: the signal ML adds over names + validators is context ("this `name` column sits next to `dob` and `ssn`"), and a cheap rule captures most of it: if a table has any high-confidence PII column, raise every ambiguous column in that table to medium. Ship rules, dictionaries, validators and explanations in v1; a local NER pass over free-text samples is a v2 signal, never the gate. A cloud LLM over production values violates "never holds… source" data hygiene and the user's compliance story.

**Quasi-identifiers.** Zip + birth date + gender identifies most people; HIPAA's rules for ZIP (first three digits only, `000` for small areas) and dates (year only, ages over 89 bucketed) exist for this ([45 CFR 164.514](https://www.law.cornell.edu/cfr/text/45/164.514)). v1 masks DOB and postcode by default and does not promise k-anonymity.

### 3.3 Traps

- **Schema drift.** The classic failure, from the Replibyte thread: people "don't update scripts to anonymize new tables or columns" ([HN](https://news.ycombinator.com/item?id=31165538)). `lazysnap.yml` must record decisions per column and the tool must fail closed on a column it has never seen, not pass it through.
- **Head-of-table sampling.** `LIMIT 100` returns the oldest rows; PII often appears later (a `notes` column that was empty for the first two years). Use `TABLESAMPLE` or `pg_stats`.
- **Identifiers stored as numbers.** `account_no bigint`, `nhs_number bigint`. Name heuristics must run on numeric columns too; value validators (Luhn, mod-11) apply to digit strings regardless of type.
- **`name` everywhere.** Products, roles, plans. Table context and the neighbouring-column rule keep this from masking your product catalogue; the reason string keeps the user from trusting a wrong call silently.
- **Hashed passwords look safe.** They are credentials; replace with a known-invalid value. Same for API keys and session tokens (entropy detector).
- **Enum and domain types.** `gender` as an enum still reveals gender; masking must produce a valid enum label.
- **Masking breaks CHECK constraints and expression indexes.** Detect before load; section 4.
- **Audit and log tables.** `audit_log.old_row jsonb` contains serialized copies of everything. Treat any jsonb column in a table named like audit/log/history/event as free text and mask whole.
- **Language-specific context words.** Presidio's own caveat; do not assume English column names. Include the obvious translations (`nombre`, `courriel`, `telefon`, `名前`) in the name lists.

## 4. Streaming extract and load at scale in Postgres

### 4.1 Simplest correct approach

Three connections: one to the source for streaming rows, one to the source for key lookups (a connection streaming a result set is busy: "The returned Rows must be closed before the connection can be used again", [pgx docs](https://pkg.go.dev/github.com/jackc/pgx/v5)), and one to the target for COPY.

**Extract.** For each table in load order, for each chunk of selected keys: `SELECT cols FROM t JOIN unnest($1::int8[]) AS k(id) ON t.id = k.id` via `conn.Query`, iterate `rows.Next()`, check `rows.Err()` after; pgx streams rows from the socket rather than buffering the result ([pgx docs](https://pkg.go.dev/github.com/jackc/pgx/v5), [pgx#1707](https://github.com/jackc/pgx/issues/1707)). A maintainer-run comparison of `Query` against raw `PgConn.CopyTo` with binary decoding on a million-row table showed no meaningful difference (7.9 s versus 7.8 s) ([pgx discussion #1599](https://github.com/jackc/pgx/discussions/1599)), so start with `Query`. `COPY (SELECT ...) TO STDOUT` cannot take bind parameters ([COPY docs](https://www.postgresql.org/docs/current/sql-copy.html)); Greenmask gets away with it because it dumps whole tables or pushes conditions into SQL and transforms "stream-based" in text format ([Greenmask architecture](https://docs.greenmask.io/latest/architecture/)).

**Transform** per row in Go, in the same goroutine or via a channel; the masker from section 2 is a pure function of (category, value, key).

**Load** with `conn.CopyFrom(ctx, table, cols, source)` where `source` is a `CopyFromFunc` that pulls the next masked row; it "returns rows until it either signals an 'end of data'… or it returns an error" ([pgx docs](https://pkg.go.dev/github.com/jackc/pgx/v5)). CopyFrom uses the binary COPY format, so "a pgtype.Type that supports the binary format must be registered for the type of each column", and enum types must be registered even though they look like strings ([pgx docs](https://pkg.go.dev/github.com/jackc/pgx/v5)). Benchmarks on PG16 with pgx v5.5: CopyFrom sustains 357,100 rows/s at 50,000-row batches, about 6.3× `SendBatch`; multi-row `INSERT` dies at the 65,535-parameter limit ([Gold Lapel benchmark](https://goldlapel.com/grounds/go-postgres/pgx-bulk-insert-benchmarks)). Postgres's own guidance: "Use COPY to load all the rows in one command" and COPY "is fastest when used within the same transaction as an earlier CREATE TABLE or TRUNCATE" because no WAL is written ([Populating a Database](https://www.postgresql.org/docs/current/populate.html)).

**Column list.** Exclude generated columns; without a column list COPY copies "all columns of the table except generated columns" ([COPY docs](https://www.postgresql.org/docs/current/sql-copy.html), [generated columns](https://www.postgresql.org/docs/current/ddl-generated-columns.html)). Identity columns are fine: "COPY FROM… will always write the column values provided in the input data, like the INSERT option OVERRIDING SYSTEM VALUE" ([COPY docs](https://www.postgresql.org/docs/current/sql-copy.html)), so `GENERATED ALWAYS AS IDENTITY` does not need special handling under COPY, unlike `INSERT`, which errors without `OVERRIDING SYSTEM VALUE` ([INSERT docs](https://www.postgresql.org/docs/current/sql-insert.html)).

**Sequences and identity.** After loading each table, for every serial or identity column: `SELECT setval(pg_get_serial_sequence('t','id'), max(id))`. `pg_get_serial_sequence` returns the internally created sequence for identity columns as well as serials ([functions-info](https://www.postgresql.org/docs/current/functions-info.html)); `setval` with `is_called = true` makes the next `nextval` return max+1, and "sequence state changes made by setval are… not undone if the calling transaction rolls back" ([functions-sequence](https://www.postgresql.org/docs/current/functions-sequence.html)). Skip empty tables (setval on NULL errors).

**Partitioned tables.** `COPY FROM` into the parent routes rows: "COPY FROM can be used with plain, foreign, or partitioned tables"; `COPY TO` from a partitioned parent is not supported, "use COPY (SELECT * FROM table) TO" ([COPY docs](https://www.postgresql.org/docs/current/sql-copy.html)). Since PG12 foreign keys may reference partitioned tables and COPY into partitions is faster ([PG12 notes](https://www.postgresql.org/docs/release/12.0/)). Always target the root, as pg_dump's `--load-via-partition-root` does when "rows do not always fall into the same partitions" ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)).

**Finish** with `ANALYZE` on every loaded table ("strongly recommended" after bulk load, [populate](https://www.postgresql.org/docs/current/populate.html)).

### 4.2 Refinements

**Constraints: pick the pg_dump strategy.** lazysnap creates the target schema, so it can split DDL the way pg_dump does: pre-data (tables, without indexes and FKs), data, post-data (indexes, FKs, triggers) ([pg_dump --section](https://www.postgresql.org/docs/current/app-pgdump.html)). Postgres's manual: dropping FKs, loading, and re-creating them is faster because "a foreign key constraint can be checked 'in bulk'", and for big loads "it may be necessary, not just desirable" because per-row FK checks queue trigger events that can "overflow available memory" ([populate](https://www.postgresql.org/docs/current/populate.html)). Creating indexes after data is also "quicker than updating it incrementally" and pgcopydb parallelizes exactly this ordering, then vacuums and resets sequences ([pgcopydb](https://github.com/dimitri/pgcopydb)). With FKs created last, insertion order and cycle breaking stop being load concerns at all; the `ALTER TABLE ADD FOREIGN KEY` at the end is the integrity verification, and if you want a report instead of a hard failure, add it `NOT VALID` then `VALIDATE CONSTRAINT`, which "validates a foreign key… by scanning the table" ([ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)).

When the target already has a schema with constraints (the CONCEPT's `shop-db-test` case), the choices are: recreate the schema (cleanest, and what a "snapshot" implies), or load in topological order with NULL-then-UPDATE for cycle-break edges, or flip FKs to `DEFERRABLE` and load in one transaction with `SET CONSTRAINTS ALL DEFERRED` ([SET CONSTRAINTS](https://www.postgresql.org/docs/current/sql-set-constraints.html)). Avoid `session_replication_role = replica` as a default path: it "disables all foreign key checks" and "only superusers and users with the appropriate SET privilege can change this setting" ([runtime-config-client](https://www.postgresql.org/docs/current/runtime-config-client.html)); pg_dump's `--disable-triggers` likewise "must be done as superuser" ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)). Managed Postgres frequently withholds both.

**User triggers on the target.** `COPY FROM will invoke any triggers and check constraints on the destination table` ([COPY docs](https://www.postgresql.org/docs/current/sql-copy.html)). An audit trigger will double-write; a validation trigger may reject masked rows. `ALTER TABLE … DISABLE TRIGGER USER` disables user triggers without touching constraint triggers (those need superuser) ([ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)); do it per table, re-enable after.

**Transactions and speed knobs.** One transaction per table: `TRUNCATE` (or fresh `CREATE TABLE`) then `COPY` in the same transaction skips WAL ([populate](https://www.postgresql.org/docs/current/populate.html)); `COPY … FREEZE` avoids a later vacuum pass but "is currently not possible… on a partitioned table" and needs the table created or truncated in the same subtransaction ([COPY docs](https://www.postgresql.org/docs/current/sql-copy.html)). `SET LOCAL synchronous_commit = off` per transaction is safe for a throwaway target: it "does not create any risk of database inconsistency", only of losing the last transactions on a crash ([runtime-config-wal](https://www.postgresql.org/docs/current/runtime-config-wal.html)). Raising `maintenance_work_mem` speeds `CREATE INDEX` and `ADD FOREIGN KEY`, raising `max_wal_size` reduces checkpoints ([populate](https://www.postgresql.org/docs/current/populate.html)); both are session-settable hints, not requirements. Load independent tables (same DAG level) in parallel; pgcopydb defaults to four COPY processes ([pgcopydb](https://github.com/dimitri/pgcopydb)).

**Key lookups at scale.** Chunk keys (a few thousand per query), join against `unnest`, keep a fixed statement shape so pgx's default `cache_statement` mode ([pgx docs](https://pkg.go.dev/github.com/jackc/pgx/v5)) reuses one prepared statement. A temporary table on the source would be faster for millions of keys, and the `TEMPORARY` privilege is granted to `PUBLIC` by default ([ddl-priv](https://www.postgresql.org/docs/current/ddl-priv.html)), but it is a write to the source session and some managed environments revoke it; the CONCEPT's "never holds write access to the source" argues for arrays. For composite keys use multi-array `unnest` (section 1.2).

**Server-side cursors.** Needed only when you must pause a result set and reuse the connection, or bound the server's memory for a sorted query: `DECLARE … NO SCROLL CURSOR` inside a transaction and `FETCH n`; `WITH HOLD` copies rows "into a temporary file or memory area" at commit ([DECLARE](https://www.postgresql.org/docs/current/sql-declare.html)). The wire protocol also supports `Execute` with a row limit and `PortalSuspended` ([protocol flow](https://www.postgresql.org/docs/current/protocol-flow.html)), but pgx v5 exposes no portal-limit API that I could find (unverified), so use `DECLARE`/`FETCH` if you need it. With pgx streaming and a chunked key join, you usually do not.

**Text versus binary COPY.** Binary is "somewhat faster" but "less portable across machine architectures and PostgreSQL versions" and "very data type specific" ([COPY docs](https://www.postgresql.org/docs/current/sql-copy.html)). Greenmask chose text so it can rewrite fields in the stream ([Greenmask architecture](https://docs.greenmask.io/latest/architecture/)). With pgx's typed `CopyFrom` you get binary for free on the load side; a raw `PgConn.CopyTo` → `PgConn.CopyFrom` text pass-through is the fast path for tables with no masked columns, at the cost of hand-parsing COPY text escaping if you ever touch a field ([pgconn docs](https://pkg.go.dev/github.com/jackc/pgx/v5/pgconn)). Note pgconn's caveat that context cancellation "will only interrupt operations on the underlying PostgreSQL network connection. Reads on r could still block."

### 4.3 Traps

- **Deferred checks fail at COMMIT.** With deferred FKs, a violation surfaces at commit, after the whole load; and the per-row trigger queue is what overflows memory ([populate](https://www.postgresql.org/docs/current/populate.html)). Post-data FK creation fails per constraint with a table name instead.
- **A failed COPY leaves dead rows.** "If the command fails, these rows are left in a deleted state… still occupy disk space"; run `VACUUM` ([COPY docs](https://www.postgresql.org/docs/current/sql-copy.html)). Wrap each table in a transaction so a failure rolls back cleanly, then vacuum on retry.
- **`ON_ERROR ignore` is not for you.** PG17 added it, for text/csv only ([PG17 notes](https://www.postgresql.org/docs/release/17.0/), [COPY docs](https://www.postgresql.org/docs/current/sql-copy.html)); silently dropping rows breaks the integrity promise.
- **Masked partition keys.** Rows route by the *masked* value; "inserting data… that does not map to one of the existing partitions will cause an error", and `BEFORE ROW` triggers "cannot change which partition is the final destination" ([partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)). Hash partitions on a masked column scatter; range partitions on a shifted date can fall off the end. Detect partition-key columns at plan time and either exclude them from masking with an explanation or fail early.
- **Masked columns under unique indexes on expressions.** `lower(email)` again ([expression indexes](https://www.postgresql.org/docs/current/indexes-expressional.html)); and unique constraints on partitioned tables "must include all of the partition key columns" ([partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)).
- **Sequence below the data.** Mask or reassign IDs and forget `setval`, and the first app insert collides. Also `setval` survives rollback ([functions-sequence](https://www.postgresql.org/docs/current/functions-sequence.html)), so set it after the data commit, not before.
- **Enum and custom types in CopyFrom.** Must be registered with the connection's type map or CopyFrom fails on the first row ([pgx docs](https://pkg.go.dev/github.com/jackc/pgx/v5)). Load `pg_type` for the schema at connect time.
- **One connection doing two things.** Fetching parents while a `Rows` is open on the same connection deadlocks or errors ([pgx docs](https://pkg.go.dev/github.com/jackc/pgx/v5)). Three connections, as above.
- **Index build memory and time.** Adding four indexes more than doubled 50,000-row insert cost in the Gold Lapel benchmark ([benchmark](https://goldlapel.com/grounds/go-postgres/pgx-bulk-insert-benchmarks)); on a fresh target, build them last.
- **`--load-via-partition-root`-class surprises.** Collation differences between source and target change routing for text partition keys ([pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)); target the root, always.
- **Giant `ANY(ARRAY)`.** Section 1.3; the planner can fall off the index at tens of thousands of keys ([Datadog](https://www.datadoghq.com/blog/100x-faster-postgres-performance-by-changing-1-line/)).

---

## What this implies for lazysnap v1 (for the ADRs, not decided here)

1. Subsetting is a client-side monotone worklist: parents uncapped, children capped and depth-limited from the root only, lookup tables whole, a row budget, and a plan printed before extraction. Composite keys as tuples; `MATCH SIMPLE` NULL rules; polymorphic pairs inferred and reported.
2. Masking is HMAC-SHA256 under per-category HKDF subkeys, key outside the yml, canonicalization per category, categories propagated along FK edges, ≥ 64-bit-domain generators for any column under a unique index, no FPE.
3. Classification is names + types + validated samples + dictionaries, with a reason per column, a neighbouring-column rule for context, whole-value masking for JSON and free text, and fail-closed on unknown columns.
4. Load is COPY via pgx, pre-data/data/post-data split, FKs and indexes created last as the verification step, three connections, per-table transactions, `setval` after commit, partition roots as targets, `ANALYZE` at the end.
