# ADR-013: A headless run's target is never chosen on the source's own cluster

Status: proposed, 2026-09-16. Narrows ADR-008 section 5 and ARCHITECTURE.md section 9 rule 1 for headless runs only — it does not supersede either, and does not touch what either says about an interactive run or an explicitly named `--target`. ADR-008 is accepted and frozen (root CLAUDE.md: "to change an accepted decision, add a new ADR that supersedes it"); this ADR adds a rule rather than changing the one ADR-008 states, which is why it narrows rather than supersedes.

## Context

The 2026-09-15 red team pointed `--source` at a production container with no `--target` and `--yes`. The discovery ladder chose the production container's own `postgres` maintenance database as the target and loaded the masked slice into it, exit 0, with nothing printed to say the write had landed on the source's own server. T-REDFIX (2026-09-15) closed what it could without a superseding ADR: `internal/core` now emits the `target.warn.same_cluster` line ARCHITECTURE.md section 9 rule 1 has always promised and that nothing read before that fix; `internal/discover`'s `chooseTarget` no longer ranks a maintenance database as target-shaped at all; and a candidate that is not on the source's own cluster now outranks one that is, ahead of every other tie-break key. `internal/discover/CLAUDE.md`'s "What the ladder will not pick as a target" section records those three changes and names the one it deliberately left alone: a same-cluster candidate is still chosen when it is the only one, because ARCHITECTURE.md section 9 rule 1 and ADR-008 section 5 both say a second database on one cluster is eligible — the ordinary compose setup — and `internal/core/gate_integration_test.go`'s `TestAGateRefusalEndsTheRunInsteadOfTryingTheRunnerUp` pins a run whose only two target-shaped candidates are exactly that. Changing that is what this ADR is for.

The question T-0184 opened: should a `--yes` run with no `--target` refuse when every reachable target-shaped candidate is on the source's own cluster, naming `--target` as the way through? The orchestrator's decision (2026-09-15): yes, and only there. An interactive run — one where Q1/Q1'/Q2 could be put to somebody, and this scenario asks none of them because target-shaped candidates already exist — asks nothing new and keeps today's behaviour: the ladder picks a winner and prints the decision and the same-cluster warning, exactly as `TestASameClusterTargetIsWarnedAbout` already pins. A `--target` named explicitly on the source's cluster stays eligible, because ADR-008 section 5 and ARCHITECTURE.md section 9 rule 1 both say a second database on one cluster is eligible by design, and this ADR does not reopen that — it only removes the ladder's licence to land there *on its own*, unsupervised, when nobody is at the terminal to see the decision line before the write happens.

## Options considered

- **Refuse in every mode whenever every candidate is same-cluster**, interactive included. Rejected: an interactive run already prints the decision header and the `same cluster as source` warning before it writes anything (`TestASameClusterTargetIsWarnedAbout`), so the operator sees the choice and can Ctrl-C. Refusing there too would make the ordinary one-cluster compose setup — `app` and `app_test` in one container, ARCHITECTURE.md section 9's own example — unusable without `--target` even when a person is watching it happen, which is the loosening root CLAUDE.md's rule on ADR-008 forbids in the other direction (docs/adr/README.md: ADR-008 "may refine ARCHITECTURE.md section 9 and may not loosen it") turned around: a rule change here must not make ADR-008 section 5's own worked case fail for someone who was never at risk.
- **Refuse only same-cluster maintenance-adjacent databases** (some heuristic narrower than "every candidate"), leaving a mixed set of same-cluster and no-candidates-at-all cases alone. Rejected: the red team's actual failure was "nothing else was reachable, so the ladder wrote to the only thing it found" — the maintenance-database fix already closed the specific database that scenario landed in, and the general shape left open is exactly "every candidate shares the source's cluster," not a narrower pattern a heuristic would have to keep in sync with `chooseTarget`'s own tie-break.
- **Make the refusal a new question (Q5) instead of a hard failure.** Rejected: ADR-008 section 7's one-question rule reserves the run's single blocking question for Q2 on the happy path, and a headless run with `--yes` takes every question's hard-failure or default branch by definition (section 7). A same-cluster-only headless run has nobody to ask; the hard failure that names `--target` is the same shape Q1's headless path already takes for "no target-shaped candidate at all," and this is its sibling for "target-shaped candidates exist, but only ones that would write beside the source."
- **Refuse and also fall through to Q1's create-target flow.** Rejected: `--create-target` is Q1's answer to "no local postgres to load into," which this state is not — a target-shaped candidate exists, it is simply on the wrong cluster. Offering to provision a fresh local container as the automatic next step would be `internal/discover` deciding, headlessly, to create infrastructure nobody asked for; the refusal names `--target` because a database the operator names is the fix, not a container lazyslice invents.

## Decision

**A headless run — `--yes`, or no controlling terminal: the run cannot ask — with no `--target` refuses, exit 4, when every reachable target-shaped candidate is on the source's own cluster.**

- The check runs in `internal/discover`'s `Resolve`, after the ladder walk and after the source is chosen, ahead of `chooseTarget`'s tie-break — so it fires before any candidate is picked as a winner, not as a second-guess of the pick. "Target-shaped" is `chooseTarget`'s own definition, unchanged by this ADR: reachable, not the source, not a maintenance database (`postgres`, `template0`, `template1`). "On the source's own cluster" is the same cheap `clusterKey` comparison `chooseTarget`'s tie-break already uses (host and port, without the database) — the address-based proxy discovery has always used, not `Target.Gate`'s live `system_identifier`/`pg_postmaster_start_time()` comparison, which needs a connection the 1 s dial budget does not allow for target selection in general (ARCHITECTURE.md section 9's gate already runs after discovery for exactly this reason).
- The condition is exactly: `--target` was not given (no flag, no positional DSN, no committed `lazyslice.yml` `target:` block — anything that short-circuits the ladder per ADR-008 section 1 bypasses this rule, because the operator named the database themselves), the run is headless (`--yes`, or no controlling terminal: the run cannot ask — the same predicate `internal/discover`'s `prompterFor`/`isHeadless` already use, not `--yes` alone: a CI job or cron entry that simply omits `--yes` has no controlling terminal either, and is exactly the red team's shape), and the target-shaped set is non-empty and every member of it shares the source's `clusterKey`. A target-shaped set that is empty already takes Q1's existing headless failure (`target.refused.none`, naming `--create-target`); this is not that state and does not change it.
- The refusal is exit 4, naming `--target` as the flag that clears it, in the same shape every other target refusal in this file's section 9 already takes: a command to run, not a document to read (CLAUDE.md, "Documentation is never the fix for a confusing first run").
- An interactive run — a controlling terminal is available and `--yes` was not passed — is unaffected: `chooseTarget`'s tie-break runs exactly as it does today, the decision header and the `same cluster as source` warning print exactly as `TestASameClusterTargetIsWarnedAbout` pins, and the run proceeds. This ADR adds no new question; the operator who is watching already sees the same-cluster line before anything is written.
- A `--target` named explicitly — by flag, positional DSN, or a committed `lazyslice.yml` — on the source's own cluster is unaffected and stays eligible, exactly as ADR-008 section 5 and ARCHITECTURE.md section 9 rule 1 already say. This rule narrows what the ladder may choose on its own; it does not touch what an operator may name.
- `--yes --create-target` is not the same case as `--yes` alone and is not refused. The "Options considered" section above rejects the ladder *automatically* falling through to Q1's create-target flow — provisioning nobody asked for — but an operator who passed `--create-target` themselves has already named the escape: the container it provisions is fresh and, by construction, not on the source's cluster (a different port), so it is not the write this ADR exists to stop. The refusal check bypasses `chooseTarget`'s tie-break entirely in this case (every reachable candidate is same-cluster, so the tie-break would still rank one of them) and goes straight to the same provisioning path Q1's "no target-shaped candidate" state already uses.
- **A second, later escalation exists in `internal/core`'s `openTarget`, added in this ADR's implementation review (finding 1) and not in the original Decision above: a headless run whose target the ladder *did* choose (the bullets above did not refuse it — the target-shaped set was not all-same-cluster at discovery time, or contained only one candidate that discovery's cheap `clusterKey` check did not flag) can still land on the source's own cluster once the gate opens it, because the gate's `Eligibility.SameCluster` is authoritative (`system_identifier`, or cluster identity/endpoint as a fallback) where discovery's `clusterKey` is a cheap address comparison that a pooler, an SSH tunnel, or `host.docker.internal` vs `127.0.0.1` can fool.** `openTarget` refuses there too, exit 4, with a distinct code (`target.refused.gate_same_cluster`, `internal/core.CodeTargetGateSameCluster`) rather than reusing this ADR's `target.refused.headless_same_cluster` — that code's catalogue message ("every reachable candidate is on {host}") describes discovery's own pre-selection refusal over the whole target-shaped set, not the gate's refusal of the one target already chosen. The condition this second check must key on is **whether the operator named the target**, not `TargetProvenance`: rung 0 carries the *file's own* provenance forward (`internal/discover/discover.go`'s doc comment — `from: compose` stays `compose`), never `pipeline.FromYml`, so a target read back from a committed `lazyslice.yml` can carry the exact same `TargetProvenance` a ladder-chosen candidate would (`FromEnvVar`, `FromContainer`, `FromCompose`) and the two are indistinguishable by provenance alone. `discover.Result` now carries `TargetNamed bool`, set wherever the ladder short-circuits on the operator's own naming of the target (`o.Target != ""` and `rung0Target`'s success path) and nowhere else; `openTarget` refuses only when `!r.targetNamed && r.headless`. A target named explicitly — flag, positional DSN, or committed yml — stays eligible at both checks, exactly as the bullet above already says for the first one.
- **A third escalation, independent of the first two, was added 2026-09-17 (T-0241, round-4 red team: `docs/reviews/2026-09-15-redteam/round4-still-leaking.json`, "a read replica"): a headless run whose source is a streaming standby refuses with no `--target`, whether or not `Eligibility.SameCluster` ever fires.** A primary and its own hot standby are one cluster by `system_identifier` and two different postmasters by the fields the first two escalations' identity check leans on when `system_identifier` is unreadable — the standby's postmaster started strictly after the primary's, so the postmaster start time disagrees by construction, which is fixed at the identity-comparison layer itself (ARCHITECTURE.md section 9 rule 1's "Fourth" amendment: a start-time disagreement no longer decides "different cluster" on its own). That fix makes `Eligibility.SameCluster` answer "possibly the same cluster" for this shape, which the first two escalations above already treat as a refusal — but it does not close the gap on its own, because a genuinely differing `data_directory` between a standby and its primary can still make the identity comparison confidently wrong the other way, and because the round-4 red team's second reproduction reached the target through a discovered `$DATABASE_URL` on a ladder whose cheap `clusterKey` check (host and port, no live connection) never flags a standby and its primary as one cluster at all — they ordinarily publish on different ports. This escalation does not depend on the identity comparison succeeding: `internal/pg`'s `Source.Replica` reads `pg_is_in_recovery()` directly, `PUBLIC`-executable and needing no grant, and a headless run with no `--target` refuses outright when it answers true (`source.refused.standby_no_target`, `internal/core.CodeSourceStandbyNoTarget`), naming `--target`. A `--target` the operator named is unaffected, exactly as the first two escalations already are — this is the same "narrows what the ladder may pick unsupervised, not what an operator may name" rule stated throughout this ADR, applied to a shape discovery's own cheap checks cannot see at all rather than to one they merely disagree with the gate about. The warning half — a header line printed whenever the source is a standby, interactive runs included — is not an escalation of this ADR's Decision; it is ARCHITECTURE.md section 9's `same cluster as source` warning's sibling, printed for the same reason (an operator watching should be told) and is recorded there and in THREAT_MODEL.md T2's 2026-09-17 amendment rather than here.

`internal/core/gate_integration_test.go`'s `TestAGateRefusalEndsTheRunInsteadOfTryingTheRunnerUp` is the test this ADR is explicitly cleared to change (its own comment, and this ADR's Context, both say so): under this rule its original scenario — `--yes`, no `--target`, and two target-shaped candidates that are both on the source's cluster — now refuses before `chooseTarget` ever runs, which is a different assertion than the gate-refusal-ends-the-run behaviour the test exists to pin.

Dropping `Yes: true` alone does not fix that, and an earlier landing of this ADR's implementation claimed it did — that claim was false and the test failed under it (`go test -tags integration -run TestAGateRefusalEndsTheRunInsteadOfTryingTheRunnerUp ./internal/core/` reported `stop = target.refused.headless_same_cluster/exit 4, want target.refused.not_empty/exit 4`, the 2026-09-16 reverify's finding). Headless is `--yes`, or no controlling terminal — the same predicate this Decision states above — and `go test` itself is a process with no controlling terminal, so a `Request` with `Yes` merely left false is still headless by that predicate and still reaches this ADR's own refusal before `chooseTarget`'s tie-break ever runs; `internal/core` had no way to construct an interactive run at all, because `discover.Options`'s `prompter` field, which is what lets `prompterFor` find somebody to ask with no real terminal, was unexported and reachable only from tests inside `internal/discover` itself.

The fix is that field: `discover.Options.Prompter` is now exported, `core.Request` carries an unexported `prompter` field (`discover.Prompter`, nil for every real run) that `resolveEndpoints` copies onto it, and the test sets it to a scripted prompter that answers as the old interactive run did. Neither Q1 nor Q2 is ever actually put to it in this scenario — target-shaped candidates already exist, so the ladder asks nothing — but `isHeadless` only checks whether somebody is here to ask, and the prompter's mere presence is what answers that yes, exactly as a real controlling terminal would. With `Yes` false and the scripted prompter set, the test again exercises `chooseTarget`'s tie-break and the gate's own refusal exactly as before T-0184; a new integration test (`internal/core/headless_same_cluster_integration_test.go`) reproduces the red team's original run — `--source` at a container, no `--target`, `--yes`, and every candidate on that source's cluster — and asserts the new refusal instead. That file's `TestACommittedYmlTargetOnTheSourceClusterStaysEligibleHeadless` is the review finding's own pin: a committed `lazyslice.yml` naming a same-cluster target (`target: from: env`), run with `--yes` and no `--target`, completes and only warns (`target.warn.same_cluster`) — neither this ADR's own refusal nor the gate-stage one fires for it.

## Consequences

- A headless run against a database with no separate target reachable — the common single-container CI or cron setup ARCHITECTURE.md section 9's `Provisioning` and Q1 already exist for — is unaffected only if nothing target-shaped is found at all; where something target-shaped *is* found but only on the source's own server, the run now stops rather than writing there silently. A CI job that relied on that silent write now needs `--target` naming the database on purpose, which is the point.
- `internal/discover/CLAUDE.md`'s "What the ladder will not pick as a target" section gets a fourth bullet recording this decision, since T-0184 was the open question it named.
- ARCHITECTURE.md section 9 rule 1 is corrected in place to note the headless narrowing, per docs/adr/README.md's rule that ADR-008 "may refine ARCHITECTURE.md section 9 and may not loosen it" — this ADR is not ADR-008, but the same discipline applies: the file states the current rule, and a superseding or narrowing ADR is where the reason lives.

## Reversal condition

If a dogfood session shows the refusal firing for an operator who had, in fact, already been shown the same-cluster write and approved it in some way this ADR did not anticipate — for instance, a CI pipeline that always runs the same known-safe same-cluster load and has no way to pass `--target` without hand-maintaining a connection string a `lazyslice.yml` should carry instead — the fix is a flag that records the operator's standing approval by name (for instance, `--target` recorded once in a committed `lazyslice.yml`, which already exempts this path under "A `--target` named explicitly... stays eligible"), not a flag that widens what the ladder may choose unsupervised. Headless here is `--yes`, or no controlling terminal: the run cannot ask, so that CI pipeline example is already inside this rule's reach even on a run that never passes `--yes` at all — a CI job ordinarily has no controlling terminal either — and is not itself grounds for reversal; the trigger is the write being pre-approved, not the process lacking a terminal. A flag that disables this refusal wholesale is the THREAT_MODEL.md rail root CLAUDE.md already forbids ("never add a flag that disables masking wholesale" is the named example; the same reasoning covers a rail that exists to keep a write off the source's own server).
