# ADR-005: Nine stages, one core, one event channel, and the safety controls that live in them

Status: accepted, 2026-09-05. Revised 2026-09-05 in the phase 2 adversarial review (tracker T-0018), before Gate 2, which is the one revision the phase workflow allows; the "Revisions" section at the end lists what changed and why. After Gate 2 this file is frozen and a change is a superseding ADR.

## Context

docs/BUILD_PLAN.md recommends six stages (introspect → classify → plan → extract → transform → load), each an interface runnable alone with a flag. research/SQLIT_STUDY.md §5.7 requires every error to name its stage, and CONCEPT.md's step 5 (verify, then write the yml) and its first-run transcript (discover) are two more stages the six do not name. research/HARD_PROBLEMS.md "What this implies for lazysnap v1" gives the algorithmic content per stage; research/SYNTHESIS.md §5 lists twenty-three binding questions, most of which land in one stage.

The three proposals converge on the stage list (eight or nine stages, one entry point, one event channel, pure classifier and transformer, bounded channels of about 2,000 rows between extract, transform and load). They diverge on the controls inside the stages, and the judges found fatal flaws in each: the target gate decided by planner statistics (mvp-first, user-first); a residual-PII confirmation that cannot confirm (mvp-first); a child cap that cannot fire (mvp-first); no sequence reset (user-first); a residual confirmation that extends the production snapshot hold through verify (risk-first); a writable-role block that fails the headline use case (risk-first); a source-target identity check missing entirely (user-first).

## Options considered

- **Six stages as BUILD_PLAN names them,** with discovery in `cmd/` and verification inside load. Rejected: an error in discovery or verification would have no stage to name, and the two stages carry the promises that "it finds your database" and "it proves it worked".
- **Eight stages** (research/proposals/user-first.md "5"): discover added at the front, verify at the back, emission folded into verify.
- **Nine stages** (research/proposals/risk-first.md "5"): emit is its own stage, so writing the yml has a stage name and an exit path, and `--no-config` disables exactly one thing.

## Decision

**Nine stages:** discover → introspect → classify → plan → extract → transform → load → verify → emit. Each is an interface in `internal/pipeline`; classify, plan and transform are engine-agnostic and pure; discover, introspect, extract, load and verify are implemented for Postgres in `internal/pg`. Each stage is runnable alone: `lazyslice introspect`, `classify`, `plan`, `verify`, each with `--json`. The Go interfaces, types, planner pseudocode and event model are in ARCHITECTURE.md; this ADR records the decisions.

**One entry point.** `core.Run(ctx, Request, event.Sink) (*Report, error)` is the whole product. `cmd/lazyslice` builds `Request` from flags and drains the sink into the line printer or NDJSON; `internal/tui` builds the identical `Request` from keystrokes and drains the same sink. Neither reaches a stage directly, so no capability can exist in one and not the other (research/proposals/mvp-first.md "D5").

**Events carry no values.** `event.Event` has fields for stage, kind, table, column, counts and a message code with identifier-only arguments; it has no free-form string field and no field whose transitive type can hold a DSN. Messages are rendered from the code by the renderer, and `docs/ERRORS.md` is generated from the same catalogue. `pgconn.PgError` `Detail` and `Where` are dropped from every rendered error unless `--show-row-values-in-errors` is passed, because Postgres writes the offending row into `Detail` (research/proposals/risk-first.md "S5"). Progress events are lossy on a full channel; stage transitions, decisions, warnings and errors are never dropped.

**Memory is bounded by construction.** Extract, transform and load are three goroutines joined by channels of `RowBatch` (2,000 rows, channel capacity 8), so a slow target back-pressures the source (research/HARD_PROBLEMS.md §4.2 "Batch size and memory"). Tables travel strictly one at a time on the channel and every table ends with a batch marked `Last`, which is the loader's commit signal; a table with no rows sends one empty `Last` batch. Selected key sets are sorted `[]int64` for single integer keys and sorted tuple slabs otherwise; the plan prints `Σ KeySet.Bytes()` (which is `keys × 8 B × 2` for the int8 form and the slab size doubled otherwise, so a UUID or composite key is counted at its real cost) and the residual filter's size, and refuses to exceed `--memory-budget` (research/HARD_PROBLEMS.md §1.2 "SQL pushdown versus a client worklist"). Roaring bitmaps are a phase 5 optimisation, not a v1 dependency.

**Source: read against one snapshot, provably read-only.**
- Every source transaction is `REPEATABLE READ READ ONLY`; one `pg_export_snapshot()` is imported by every reader with `SET TRANSACTION SNAPSHOT` (research/HARD_PROBLEMS.md §4.1). The snapshot is held through plan and extract and released before load; the plan prints the estimated hold time. Standby cancellation is exit 7 with a retry message (research/HARD_PROBLEMS.md §4.3).
- **Pooled endpoints** (research/OPEN_QUESTIONS.md item 1): a second connection probes `SET TRANSACTION SNAPSHOT`; on failure the run falls back to a single-connection serialised extract inside one transaction and prints `pooler detected: single-connection extract, slower`; `--single-connection` forces it; a source that cannot hold any snapshot is refused with exit 3 and the direct-DSN advice. Never extract without a snapshot.
- The `READ ONLY` transaction is the enforcement; the tracer is the evidence, and this ADR does not overstate it. All five pgx v5.10.0 tracers (`QueryTracer`, `CopyFromTracer`, `BatchTracer`, `PrepareTracer`, `ConnectTracer`) are registered on the source pool, because a `QueryTracer` alone sees `Query`, `QueryRow` and `Exec` and nothing else. The allowlist is the fixed set of statement **shapes** lazyslice generates — catalog introspection, `TABLESAMPLE` sampling, the typed `unnest` join shapes, `pg_export_snapshot`, `SET TRANSACTION SNAPSHOT`, the bounded lookup count, the residual confirmation probes — matched on the statement text with parameters elided; a first-keyword allowlist was rejected because `WITH x AS (DELETE ... RETURNING *) SELECT ...` and `SELECT lo_import(...)` both begin with an allowed keyword. A statement outside the set is refused by returning an already-cancelled context from `TraceQueryStart` (the only refusal mechanism the tracer interface offers) and recorded as a violation that fails the run. Source code paths use `Query` only, and `TestSourceNeverCopiesOrBatches` fails if `internal/pg` ever calls `CopyFrom`, `SendBatch` or `Prepare` on a `Source`. Invariant I4 replays the trace (research/proposals/risk-first.md "S1"). The source handle type `pg.Reader` exposes only `Query`; that is authorship hygiene, and this ADR states plainly that a type without `Exec` does not make a connection read-only, because `Query` executes arbitrary SQL.
- Role privileges are checked with `has_table_privilege` and printed. A writable role warns and proceeds; `--require-read-only-role` makes it exit 6. This overrules research/proposals/risk-first.md "S1" (block on a non-loopback source) because research/SQLIT_STUDY.md §5.2 says the opposite in terms and CONCEPT.md's first line is "point it at a production SQL database".

**Target: the gate is a hard gate, and no flag reaches a non-empty unmarked database.** The gate runs after discovery, never inside the 1 s discovery dial, and its verdict is tri-state (`NotProbed`, `Refused`, `Eligible`) so that an unfinished probe can never read as eligible. In order:
- **Identity.** Refused (exit 2) iff normalised `host:port/database` equals the source's, **or** `pg_control_system().system_identifier` equals the source's **and** `current_database()` equals the source's database. This is a disjunction over sameness, not a conjunction over difference: a second database on the same cluster (`app` and `app_test` in one container, the common compose setup) is eligible, and the decision header prints `same cluster as source` as a warning line. The earlier wording required both host and system identifier to differ and would have refused every legitimate same-cluster target.
- **Locality.** The target is local (loopback, or a container whose compose `working_dir` matches the cwd) or is named by `--allow-remote-target HOST`; otherwise refused with exit 4 naming the host and the flag. An empty, freshly provisioned remote production database passes every other rule, and CONCEPT.md's target is "a local database"; the argument that overruled a loopback restriction for the source does not apply to the side that is written (THREAT_MODEL.md T2).
- `has_schema_privilege(current_user, 'public', 'CREATE')`.
- **Marker.** `lazyslice_meta` present with `schema_version` at or below ours **and bound**: the latest row's `source_fingerprint` (and `source_system_id` when both sides have it) matches the current source, and its `schema_fingerprint` matches the fingerprint recomputed over the target's current catalog (ARCHITECTURE.md "The target"). A bound marker passes and the target is truncated with a printed line; a row still at `status = running` is a run that died and forces the same truncation. An unbound marker — another source, a changed catalog, a table we did not create, a marker someone else planted — authorises nothing and falls through to the emptiness rule. A file plus a marker therefore cannot authorise writing to a database that has acquired rows of its own since we wrote it.
- **Emptiness.** Every user table is empty by `SELECT EXISTS (SELECT 1 FROM t)` per table, exempting migration bookkeeping tables (`schema_migrations`, `_prisma_migrations`, `alembic_version`, `__diesel_schema_migrations`, `flyway_schema_history`, `goose_db_version`, `atlas_schema_revisions`, `knex_migrations`, `django_migrations`) and extension-owned tables (research/proposals/risk-first.md "S3"), over at most 2,000 user tables. **A target with more than 2,000 user tables and no bound marker is refused with exit 4 and the table count printed**; it is never sampled and never passed, overruling research/SQLIT_STUDY.md §5.2's "samples and reports past that cap", which is a fail-open reading of the one control between the tool and the catastrophic write. A table with `relrowsecurity` or `relforcerowsecurity` true, or on which the probe raises any error (`42501` included), **counts as not empty** and the refusal names the table and the reason: under forced row-level security `EXISTS` returns false over rows the session cannot see while `DROP TABLE` still succeeds. Never `pg_stat_user_tables`: `n_live_tup` is an estimate and reads zero on a restored, unanalysed production database, which is the catastrophic write.
- A migrated-but-empty compose database passes. lazyslice owns the target schema: its empty tables are dropped and recreated from the source catalog, each drop printed before it happens, and bookkeeping tables are copied whole from the source so migration state matches the schema that now exists. ARCHITECTURE.md "Schema recreation" names exactly which object classes v1 recreates (schemas, extensions, enums, domains, composites, sequences, tables with columns, defaults, generated expressions, identity, collations and all constraints, indexes, foreign keys) and which it counts and does not (views, functions, triggers, policies, rules, comments, privileges, partitions); a recreated object that depends on one we do not recreate is refused at plan with exit 13 naming it, before anything is dropped. A partitioned source table becomes one plain table in the target. **After any failure the target is either empty or carries a marker row at `running` or `failed`, and the next run truncates it**; the earlier "zero rows on any failure" was untrue under `kill -9`, because load commits per table (THREAT_MODEL.md T8).
- A non-empty unmarked database is refused with exit 4 and the row counts shown, under every flag. `--target` names a database; it does not bypass the gate. There is no `--allow-nonempty-target` and no `--replace`; the error prints the `dropdb` or `docker compose down -v` command that clears it. Where the judges disagreed, this is the second judge's call and it overrules research/SQLIT_STUDY.md §5.7 and §6 Q3: the flag's only use is to save one command, and its existence is the enabling condition of the failure that ends the project (research/SYNTHESIS.md §2 risk 2). A marked target is truncated and reloaded with a printed line, no question (research/SQLIT_STUDY.md §6 "not questions").

**Plan** (research/HARD_PROBLEMS.md §1; research/OPEN_QUESTIONS.md item 9).
- Client-side monotone worklist with `CHILD_OK` and `PARENT_ONLY` provenance; a row's mode is fixed at first push and never upgraded; parents uncapped at any depth; children only from `CHILD_OK` rows.
- **Child cap is per parent key per edge, default 100** (`--cap N` or `--cap table=N`), applied with `row_number() OVER (PARTITION BY fk ORDER BY pk) <= cap`; depth 3 from the root (`--depth`); row budget 1,000,000 (`--row-budget`); memory budget 256 MiB (`--memory-budget`). This resolves research/OPEN_QUESTIONS.md item 9 against docs/BUILD_PLAN.md PROMPT 4.3's per-table `10 × N`: mvp-first applied that number per parent key and produced a cap that could never fire; 100 is between risk-first's 100 and user-first's 20, and on Pagila (about 27 rentals and 27 payments per customer) it does not truncate, so Gate 4's slice is the whole customer.
- The walk is deterministic: FIFO queue, tables in `(schema, name)` order, edges in constraint-name order, key sets and results ordered by the identity columns, no map iteration; two runs over one snapshot select byte-identical sets, which is what makes invariants I3 and I5 and the yml as "a record of what happened" hold (ARCHITECTURE.md "The subset planner", "Determinism").
- Row identity: `--key` (or the yml's `keys:`) → PK → non-partial, non-expression unique index → pseudo-key from FK columns plus NOT NULL discriminators, probed for uniqueness on a `TABLESAMPLE` → refuse the table by name with exit 12 and `--key table=col,col` as the remedy. An explicit key is first because a pseudo-key was only ever probed on a sample, and a key given by flag is recorded in the yml so the second run needs no flag. `ctid` is cut: it is not reproducible across `VACUUM FULL`, so it breaks invariants I3 and I5 (all three judges; research/proposals/mvp-first.md planner step 4).
- Lookup tables (no outgoing FK, at least one incoming, at most 1,000 rows by a bounded count `SELECT count(*) FROM (SELECT 1 FROM t LIMIT 1001) x`, skipped entirely when `reltuples` exceeds 10,000) are copied whole and named, unless any column in them classifies at `possible` or above, in which case they are walked like any other table so the target holds only referenced rows (research/proposals/user-first.md "7" item 5, narrowed: masking still applies to every copied row). An exact `count(*)` inside the holder transaction on every FK-less table was the xmin pin THREAT_MODEL.md T9 exists to prevent. Unreachable tables get schema and zero rows, listed.
- A table the source role cannot read is decided at plan, never mid-extract: unreachable or child-only, it drops to schema-only and is listed; needed as a parent, the run stops at plan with exit 12 naming the table, the role and the `GRANT SELECT` statement. `--skip-table` drops a child-only table on request and is recorded (ARCHITECTURE.md "Unreadable tables").
- Cycles need nothing at selection; load creates FKs after data, so no edge is deferred; the plan prints each SCC and says so. Zero cycles is a first-class fixture.
- Polymorphic `_type`/`_id` and `content_type_id`/`object_id` pairs are inferred from sampled values, followed parent-direction only as virtual FKs, printed; unmapped values are printed as `not followed: no constraint`.
- Composite keys travel as tuples through multi-array `unnest` in chunks of 2,000; a `MATCH SIMPLE` composite FK with any NULL column is skipped; unindexed FK columns warn per edge.
- Root default: `inbound − outbound` FK count after discarding lookup-shaped tables, then the name preference, then row count (research/SQLIT_STUDY.md §5.4), overruling docs/BUILD_PLAN.md's "most incoming FKs".

**Load** (research/HARD_PROBLEMS.md §4): pre-data DDL for the object classes in ARCHITECTURE.md "Schema recreation", `CopyFrom` with explicit column lists excluding generated columns, types registered in `AfterConnect`, partition roots loaded into the plain table that replaces them, one transaction per table opened on the table's first batch and committed on its `Last` batch, `synchronous_commit = off` per transaction, then indexes, then FKs as `NOT VALID` plus `VALIDATE CONSTRAINT` per constraint, then `setval(seq, coalesce(max(id), 1), max(id) IS NOT NULL)` after commit, never a literal 0, then `ANALYZE`. User triggers do not exist on the target because they are not recreated. Row-level security on a target table is detected and falls back to `INSERT`, for the reload of a bound marked target where a policy was added by hand.

**Verify; any failure is a non-zero exit.**
1. Every FK validates (exit 8, naming the constraint and the cap that caused it).
2. **Residual-PII scan** (research/OPEN_QUESTIONS.md item 3; THREAT_MODEL.md T12). During transform, every masked cell's `HMAC(runKey, enc(column, path, canonical(source)))` enters a Bloom filter sized for 10⁻⁶ false positives (about 29 bits per entry; every masked JSON leaf enters separately with its path; size printed in the plan and counted against the memory budget). Verify streams every masked target column, canonicalises, and on a filter hit confirms with `SELECT EXISTS` against the source on a **new, short** `REPEATABLE READ READ ONLY` transaction opened after extract released the run snapshot — the indexable equality probe first, the case-folded probe only when it is false, at most 1,000 probes per run (`--residual-probe-cap`, printed). A confirmed hit is exit 9. A hit the source denies is printed as `unconfirmed (filter false positive or source changed since snapshot)` and does not fail. A hit that **cannot be tested** — the second transaction will not open, a probe errors, the role lacks `SELECT`, or the cap is reached with hits untested — is exit 9 naming the reason, never a printed note: an unconfirmable hit is where failing closed costs least. This keeps mvp-first's placement, risk-first's sizing, and closes the xmin-hold flaw the second judge found in risk-first's held-snapshot confirmation. This scan tests the masker, not the classifier; a column the classifier missed is never in the filter, and THREAT_MODEL.md T1 says so.
3. **Second net:** the classifier's validators run over the full contents of every column the target holds unmasked — every unmasked, non-opted-out column, and the string leaves of masked JSON columns — canonicalised by the column types in `Schema`, which `Verify` receives (the target is small, so this is a scan, not a sample). Any column reaching `possible` is exit 9 naming it (research/proposals/user-first.md "9" item 4).
4. Sequences reset in the strict-NULL form; every `ChildOK` or `ParentOnly` step holds exactly its key count and every lookup its bounded count (schema-only steps and empty lookups are reported, not failed); unmasked columns byte-identical to the source on a sample fetched by identity through the short transaction, with a row that changed or vanished since the snapshot reported, not failed.
5. **What the green tick does not prove**, printed in the README, first item first: the snapshot preserves production row identifiers, so anyone with any other reference to a production record can re-identify every row; personal data in a column classified `none` that no validator recognises; a leaked value that was truncated, reformatted or embedded in a longer string; values inside `bytea`; JSON key names; `NULL` and `''`; masked columns with a small admissible domain, recoverable by frequency; quasi-identifier combinations; frequency and prefix leaks in unmasked columns; a masked value coinciding with another row's real value; values already fake in the source.

**Exit codes** (research/OPEN_QUESTIONS.md item 10; taken from research/proposals/risk-first.md and extended): 0 ok; 2 usage, unsupported engine or version, source and target resolve to one database, a tracked secret or mapping file, a bare `--unmask` without a reason, a `where_fingerprint` in the yml with no `--where`; 3 no source or no snapshot possible; 4 target refused (non-empty and unmarked, above the table cap, a row-level-security or erroring table, remote without `--allow-remote-target`); 5 credential or key missing under `--require-key`; 6 writable role under `--require-read-only-role`; 7 extract or load failure including standby cancellation; 8 FK verification; 9 residual personal data, or residual hits that could not be confirmed; 10 schema drift under `--strict-schema`; 11 budget exceeded; 12 plan refused (no row identity, a unique column whose best generator cannot carry the row count, an unreadable table the slice needs, a `mapping_file:` missing a value); 13 target schema not recreatable (a recreated object depends on an object class v1 does not recreate); 130 interrupted with the target rolled back. Every proposal's numbering yields to this table.

## Consequences

- ARCHITECTURE.md carries the interfaces, types, pseudocode, event model and flag table; docs/ERRORS.md is generated from the event catalogue and CI fails on an error type missing from it.
- Phase 4 builds the stages in this order, each behind its subcommand, TUI last (docs/BUILD_PLAN.md phase 4).
- THREAT_MODEL.md maps every control named here to a threat and marks the v1 blockers.
- The residual scan's filter memory and the key sets are both budgeted; a schema that exceeds the budget aborts at plan with the table named and the flag that raises it.
- `lazyslice_meta` is created in the target on first write and carries run id, tool version, schema version, timestamps, source fingerprint and system id, the schema fingerprint as loaded, the classification fingerprint, root, take, key fingerprint and status; the gate reads the fingerprints, and a changed key, classification or tool version is printed before the truncation.

## Reversal condition

- If the event channel cannot carry two-way TUI actions (cancel a table mid-extract), add a `Control` channel; never a second core.
- If Gate 5's ten torture schemas show the per-parent-key cap at 100 producing slices over the row budget on more than one of them, lower the default and record the number; the semantics stay per parent key.
- If a target owner cannot accept schema recreation (a migrated compose database whose migrations must survive), add a load-into-existing-schema mode with deferred constraints as a new ADR; it is not v1.
- If the second-net scan doubles verify time on the 2M-row fixture, it becomes sampled with the sample size printed, never removed.
- If a dogfood session shows the absent `--replace` costing more than one command, add `--replace <database-name>` that requires the target's database name typed as its value, by a new ADR.

## Revisions

2026-09-05, phase 2 adversarial review (T-0018), before Gate 2:
- Target gate restated as an ordered, tri-state rule: identity as a disjunction (same-cluster targets eligible), locality with `--allow-remote-target`, marker binding, fail-closed cap, RLS and probe errors as not-empty.
- Tracer restated honestly: five tracers, shape allowlist, cancelled-context refusal, `READ ONLY` as the enforcement.
- Memory estimate is `Σ KeySet.Bytes()`; extract-to-load contract carries `Last`; deterministic walk; explicit key first; bounded lookup count; unreadable tables decided at plan.
- Schema recreation scoped by object class with exit 13; failure property restated as empty-or-marked with `running` forcing truncation.
- Residual scan filed under T12 with leaf digests, split and capped probes, and fail-closed confirmation; verify's row-count check restated per step mode; the false-negative list leads with preserved row identifiers.
- Exit codes extended.
