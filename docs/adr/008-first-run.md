# ADR-008: First run — the discovery ladder, the one blocking question, and the endpoints they resolve

Status: proposed, 2026-09-05

## Context

CONCEPT.md: first run asks at most one blocking question, then works; headless runs ask none. CLAUDE.md: "Documentation is never the fix for a confusing first run. Change the default or the question." ARCHITECTURE.md §9 already carries the v1 behaviour, adopted from research/SQLIT_STUDY.md §5.1 to §5.5 and §6 with the two changes ADR-005 makes (Q3 does not exist; `--allow-nonempty-target` does not exist). docs/adr/README.md records that this ADR is owed and that it **may refine ARCHITECTURE.md §9 and may not loosen it**.

The reason it was owed is research/OPEN_QUESTIONS.md item 5: research/SQLIT_STUDY.md rests on one repository, and the first-run design must not be written from it alone. research/FIRST_RUN_STUDY.md (written 2026-09-05) discharges that by reading lazygit, lazydocker and k9s at pinned commits, with file-and-line citations. research/OPEN_QUESTIONS.md item 7 asks specifically for a Docker context resolution order; research/FIRST_RUN_STUDY.md §2 supplies one taken from shipped code rather than from a documentation page that does not state an order.

Eight findings from that study bear on this decision, and §7 of the study numbers them. The three that change what ARCHITECTURE.md §9 says are: the Docker order is five steps, not three; an explicit endpoint should skip discovery rather than win it; and a creating question read from `os.Stdin` will consume piped data as an answer.

Three further corrections are made here because ARCHITECTURE.md §9 as written cannot be implemented as it stands, and a phase 4 task would have to invent the answer: Q1′ fires on a state its own gate rule makes impossible (§6); the target tie-break ends in a question whose precondition is false (§5); and the gate's rule order differs from ADR-005's, which changes which refusal a remote target sees (§5). None of the three loosens anything, and the last restores ADR-005's own order.

What this ADR does **not** decide, because ADR-005 and ADR-004 already did and this ADR may not loosen them: the target eligibility gate's **rules** — restated below in ADR-005's order, as the thing first run must obey, with no rule added, removed or weakened — the absence of Q3 and `--allow-nonempty-target`, the masking key lifecycle, and the `.gitignore` handling in ARCHITECTURE.md §9 "The repository". research/FIRST_RUN_STUDY.md §8 records that none of the three tools writes to anything destructible, so none of them is evidence about the gate; research/OPEN_QUESTIONS.md item 2 stays open.

## Options considered

**Where the blocking question is read from.** Three options, not two. (a) lazygit's `bufio.NewReader(os.Stdin)` (research/FIRST_RUN_STUDY.md §1): one line of code, works for a human, and `echo y | lazyslice` answers Q1 by creating a container while a password typed at Q4 comes off whatever is piped in. (b) Gate on stdin: prompt only when `isatty(os.Stdin)`, otherwise behave as `--yes`. This is safe, and it is what the first draft of this ADR described while also claiming to read the controlling terminal — two rules that together reduce to (a) with a guard, because when stdin is a TTY it *is* the controlling terminal. (c) Open the controlling terminal, write prompts to stderr, read answers from it whatever stdin is, and treat its absence as `--yes`. (c) is chosen in §7: it costs a platform-specific path, and it is the only one of the three where an implementation that reads `os.Stdin` is observably wrong and can be failed by a test.

**The default of the creating question.** lazygit's `git init` prompt is `(y/N)` and only the literal `y` proceeds (research/FIRST_RUN_STUDY.md §1). research/SQLIT_STUDY.md §6 argues the opposite for Q1 and gives the asymmetry: `git init` writes into the user's own project directory and into what they will commit, whereas Q1 creates a disposable container that lazyslice named and that exists only to be written into. ARCHITECTURE.md §9 already states `[Y/n]`.

**Resolving the Docker endpoint.** `client.FromEnv`, which is the obvious call and is wrong twice over (research/FIRST_RUN_STUDY.md §2). Or the five-step order lazydocker implements. Or shelling out to `docker context inspect`, which ARCHITECTURE.md §8 forbids by fixing the subprocess set at two.

**Reading the context store.** Import `github.com/docker/cli/cli/config` and `.../cli/context/store`, as lazydocker does — a large dependency tree for two JSON files, and not in ARCHITECTURE.md §13. Or read `config.json` and the context metadata with `encoding/json` in `internal/discover/dockerctx`.

**Fallback sockets when the resolved endpoint does not answer.** research/OPEN_QUESTIONS.md item 7 says "then the default socket paths", plural, motivated by OrbStack and Colima. Enumerating vendor socket paths would put unverified facts in the binary; CLAUDE.md forbids exactly that ("Recognizing a tool's name is not knowing its current state"). The alternative is one platform default plus `--docker-host`, and a reversal condition.

## Decision

### 1. The ladder runs only for what is not already known

`--source` and `--target` (and the positional DSN) are not rung 0 of the ladder. Each **short-circuits** discovery for its own side: given `--source`, no rung is walked for the source; given both, no rung is walked at all and no Docker call is made. This is research/FIRST_RUN_STUDY.md finding 5, and it is the behaviour of all three studied tools. ARCHITECTURE.md §2's `FromFlag` provenance therefore labels a candidate that was never discovered, and `Discoverer.Discover` is not called when both sides are given. Rung 0 (`./lazyslice.yml`) short-circuits the same way for whichever of the two references the file supplies, unless `--reconfigure` is given (ADR-004).

Otherwise the ladder is exactly ARCHITECTURE.md §9's, unchanged: 2 s listing budget, 1 s per-candidate dial, candidates printed as they resolve; rung 0 `./lazyslice.yml`, rung 1 `$DATABASE_URL`, `.env`, `.env.local`, `.env.development` plus the `POSTGRES_URL`, `PG_URL`, `DB_URL` aliases, rung 2 libpq `PG*` and `PGSERVICE`, rung 3 running Postgres containers, rung 4 exited Postgres containers shown as `stopped`, rung 5 compose service names for naming only.

### 2. What `.env` and compose may contribute

**Compose YAML is a naming source and nothing else** (ADR-004; research/SQLIT_STUDY.md §5.10). It is never parsed for a host, a port, a user, a password or a database name that becomes part of a DSN. research/FIRST_RUN_STUDY.md §3 confirms the posture in a shipped tool: lazydocker asks compose for service *names* and takes every connection-bearing fact off container labels and live port bindings.

**`.env` files contribute a complete URI or nothing.** A `.env` variable is used only when it is one of the six names at rung 1 and its value parses whole as a Postgres URI. lazyslice never assembles a DSN from `.env` fragments (`DB_HOST`, `DB_PORT`, `POSTGRES_PASSWORD` and the like), and it never uses `.env` to interpolate a compose file. This is where ARCHITECTURE.md §9 was silent and this ADR decides: the failure research/SQLIT_STUDY.md §5.1 names — "reading the YAML to *guess* a port is how you produce a connection string that does not connect" — is a property of *composition*, not of compose files, and `${DB_PORT:-5432}` resolved from `.env` produces the same wrong string whether the composing is done in the YAML or by us.

A `.env` value that names a variable rather than a value (`DATABASE_URL=${PROD_URL}`) is not expanded; the candidate is reported at rung 1 as unusable with that reason, and the ladder continues.

### 3. Docker endpoint resolution

`internal/discover/dockerctx` resolves the endpoint in this order. Steps 2 to 6 are lazydocker's `determineDockerHost` (research/FIRST_RUN_STUDY.md §2); step 1 is ARCHITECTURE.md §8's flag. This supersedes ARCHITECTURE.md §8's three-item summary "`DOCKER_HOST`, context, default sockets", which is this list abbreviated past the two steps that matter.

1. `--docker-host` when given. Nothing below runs.
2. `$DOCKER_HOST` when non-empty. Nothing below runs.
3. `$DOCKER_CONTEXT` when non-empty; otherwise the `currentContext` field of `config.json` in the Docker CLI config directory (`~/.docker`, or `$DOCKER_CONFIG` when set).
4. A context name that is empty **or the literal string `default`** resolves to the platform default socket without touching the context store. lazydocker's comment gives the reason this is not an optimisation: on Windows, `default` is what is actually stored in `config.json`.
5. Otherwise the named context's metadata is read from the context store under the Docker config directory and the `docker` endpoint's `Host` is used.
6. A context that exists but whose `Host` is empty — creatable with `docker context create foo --docker "host="` — resolves to the platform default socket, not to an empty endpoint.

Platform defaults, as build-tagged constants: `unix:///var/run/docker.sock` everywhere except Windows, `npipe:////./pipe/docker_engine` on Windows.

**No `docker/cli` dependency.** ARCHITECTURE.md §13 lists `github.com/moby/moby/client` and not `github.com/docker/cli`. `dockerctx` therefore reads `config.json` and the context metadata itself with `encoding/json`. The phase 4 task that implements step 5 verifies the on-disk store layout against a context created by a real `docker context create` before writing the reader, rather than assuming it; a layout it cannot read is step 4's fallback with the printed reason `docker context "<name>": could not read endpoint, using <default>`.

**Client construction.** `client.NewClientWithOpts(client.WithTLSClientConfigFromEnv(), client.WithHost(endpoint))` — two options, not lazydocker's three. lazydocker's third, `WithAPIVersionNegotiation()`, is written against `github.com/docker/docker/client`, which its `go.mod` pins; ARCHITECTURE.md §13 pins `github.com/moby/moby/client v0.6.0` and names `docker/docker` as explicitly not a dependency, so lazydocker's call cannot be copied across unchecked. In the pinned client that option is documented `Deprecated: API-version negotiation is now enabled by default and this options is now a no-op` and its body is `return nil` (`client_options.go` L381-L395, read in the module cache at v0.6.0 on 2026-09-05). `.golangci.yml` enables `staticcheck`, so writing it verbatim in phase 4 fails `make lint` with SA1019, for a call that does nothing.

`client.FromEnv` is still not used, for two independent reasons — the second restated against the pinned client rather than carried over from lazydocker's comment:

- It applies `WithHostFromEnv`, so it reads `$DOCKER_HOST` and nothing else and ignores contexts entirely (`client_options.go` L90-L102). This is research/FIRST_RUN_STUDY.md §2's first reason and it stands on its own; it is the whole of why steps 3 to 6 exist.
- It also applies `WithAPIVersionFromEnv`, which sets `cfg.envAPIVersion` from `DOCKER_API_VERSION` (`client_options.go` L357-L369); a non-empty `envAPIVersion` makes the constructor call `setAPIVersion` (`client.go` L226-L227), which does `negotiated.Store(true)` (`client.go` L365-L371), so negotiation is suppressed for the life of that client and an older daemon is spoken to at the pinned version. lazydocker's comment attributes the same effect to `manualOverride`; that identifier is `docker/docker`'s and does not exist anywhere in `moby/moby/client v0.6.0`. The remedy is not calling `FromEnv` — not adding an option that is now a no-op.

**Only a local endpoint yields container candidates, Q1, or provisioning.** The resolved endpoint is **local** when its scheme is `unix://` or `npipe://`, or when it is `tcp://` whose host is a loopback IP literal (`127.0.0.0/8` or `::1`). A hostname is never resolved to decide this, so `tcp://localhost:2375` counts as non-local: resolving it would put a DNS lookup inside the 2 s listing budget and would make a safety property depend on `/etc/hosts`. The unresolvable case therefore fails closed.

When the resolved endpoint is not local: rungs 3 and 4 yield nothing, **Q1 does not fire**, and `pipeline.Provisioner` is not called. The ladder prints one line naming the endpoint and the step it came from, in the same form as the degradation message below — `docker endpoint tcp://staging:2375 ($DOCKER_HOST) is not local — container discovery skipped; pass --source/--target, or set --docker-host to a local socket`. `--create-target` against a non-local endpoint is a **refusal, exit 4**, naming the endpoint and `--docker-host`; it is never a silent no-op and never a container created elsewhere, because both ARCHITECTURE.md §9 and this ADR say lazyslice never removes a container, so a `lazyslice-target-<project>` created on a remote daemon and then refused by the gate as remote would be left running on someone else's host with no cleanup path. The free port the `Provisioner` chooses is free on *this* machine, which is a second reason the same code cannot address a remote daemon.

This is a decision, not a refinement — ARCHITECTURE.md §8 admits `--docker-host` and §9 is silent on what a remote daemon means for discovery — and THREAT_MODEL.md T2 is what forces it: "the target is local unless a flag names the remote host", a v1-blocking control. A container on a remote daemon publishes on the *remote* host's interfaces, so §4's loopback normalisation would otherwise rewrite its `0.0.0.0:5432` binding to `127.0.0.1:5432`, set `Candidate.Local` on a database that is not local, satisfy the locality rule, and let the candidate collapse with a rung 1 `$DATABASE_URL` naming `localhost:5432`. `--source` and `--target` stay the way to name a database on a remote daemon, and they carry the real host, which the gate then judges.

**`ssh://` endpoints** are one case of that rule with a different reason and their own message. ARCHITECTURE.md §8 fixes the subprocess set at exactly two — `--password-command` and `git` — and tunnelling an `ssh://` endpoint needs a third, which the threat model has not scoped. The printed line is `docker endpoint <endpoint> is ssh:// — container discovery skipped; pass --source/--target, or set --docker-host to a local socket`.

**Degradation.** When the resolved endpoint does not respond, rungs 3 and 4 yield nothing and the ladder prints one line naming **the endpoint that was actually resolved and the step it came from** — `docker: unix:///var/run/docker.sock (default socket) not reachable — skipping container discovery; --docker-host` — never a hard-coded path. research/FIRST_RUN_STUDY.md §2 records lazydocker printing a hard-coded socket path in exactly this message as a defect not to copy. A Docker failure never aborts the run: rungs 0 to 2 and 5 still produce candidates, and a source found there is used.

There is no list of guessed vendor socket paths. This narrows research/OPEN_QUESTIONS.md item 7's "default socket paths" to one platform default plus `--docker-host`, because a vendor socket path we have not verified is a fact invented in the binary, and because the context store at step 5 is the mechanism a vendor-installed daemon is supposed to register through. That last clause is an expectation, not a verified fact, and it carries a reversal condition below.

### 4. Container candidates, naming and de-duplication

Rung 3 lists containers with `All: true` so that rung 4's exited containers come from the same call (research/FIRST_RUN_STUDY.md §3). Compose provenance is read from container labels — `com.docker.compose.project`, `com.docker.compose.service`, `com.docker.compose.project.working_dir` — and a container labelled `com.docker.compose.oneoff` is skipped. The display name is the compose service when present, else the container name with its leading `/` stripped, else the container ID.

**The `working_dir` filter needs a stated fallback.** ARCHITECTURE.md §9 says containers are "filtered to the compose project whose `working_dir` label is the cwd or an ancestor, then any" without saying what the header prints when the first filter is empty. It prints the provenance it actually used: `docker: no compose project for this directory — showing all Postgres containers`. lazydocker reaches the same place by a different route and needs three fallbacks to get there (research/FIRST_RUN_STUDY.md §3), which is the evidence that the empty case is common, not exotic.

**Address normalisation before de-duplication, and the precondition it depends on.** A published binding of `0.0.0.0` or `::` normalises to loopback before candidates are compared — **only because §3 has already established that rungs 3 and 4 run against a local endpoint**. `0.0.0.0` means "every interface of the machine running the daemon"; it is loopback-equivalent when that machine is this one and at no other time. Rungs 3 and 4 produce no candidates at all when the endpoint is not local, so the normalisation has no non-local input to mis-handle, and the implementation asserts that rather than assuming it: normalising a binding is a function of `(binding, endpointIsLocal)` and it is a programming error to call it with `endpointIsLocal` false.

A binding with an empty host IP counts as unpublished and yields no candidate. Candidates collapse when they agree on `(host, port, database)` after that normalisation; the lower-numbered rung wins the printed provenance and the discarded one is shown in parentheses, per research/SQLIT_STUDY.md §5.1. ARCHITECTURE.md §12 puts loopback normalisation in `internal/dsn`; this ADR states that discovery must apply it, which §9 did not say. research/FIRST_RUN_STUDY.md §3 has the `0.0.0.0` → `localhost` precedent — and records what it is precedent *for*: lazydocker's use is a helper that builds a browser link for a container the user is already looking at, so it carries no locality precondition of its own and cannot supply one here. Every container candidate carries `Candidate.Local = true` for exactly the reason ARCHITECTURE.md §2 gives, and never because a binding string was rewritten.

### 5. Source, target and the decision ladder

**Source** is unchanged from ARCHITECTURE.md §9: the most-local reachable candidate with the most tables that is not the target; local beats remote regardless of table count. Source is never a question. No source is exit 3 with the ladder printed and a command to run.

**Target** must pass the gate. The gate is ADR-005's, restated here as the thing first run obeys, with nothing added and nothing relaxed. Two things about it are stated here that neither source states, because first run is where they become observable: the order, and what happens when the first rule fails.

**Reachability is a precondition, not a rule.** Every rule below runs a query, so an unreachable candidate cannot be judged. A candidate that does not answer is not eligible and is never a target; when it is the only target-shaped candidate the run stops at **exit 4** with the event code `target.refused.unreachable`, naming the endpoint and the connect error as `Candidate.ConnectErr` already sanitises it. `Eligibility.Verdict` stays `NotProbed`, which ARCHITECTURE.md §2 already says is never eligible. This closes the branch ADR-005's exit table left unassigned; it is a code within an existing exit, not a new exit code.

**Order: ADR-005's, verbatim.**

1. **Identity.** Refused (exit 2) iff normalised `host:port/database` equals the source's, **or** `system_identifier` equals the source's **and** `current_database()` equals the source's database. A second database on the same cluster is eligible and the header carries `same cluster as source` as a warning.
2. **Locality.** `Candidate.Local`, or `--allow-remote-target HOST` naming the target's host exactly; otherwise exit 4 naming the host and the flag.
3. `has_schema_privilege(current_user, 'public', 'CREATE')`. False is **exit 4** with the event code `target.refused.no_create`, naming the role, the database and the `GRANT CREATE ON SCHEMA public` statement that fixes it, in the form ARCHITECTURE.md §9's writable-source block already uses: a statement, not a doc link.
4. **Marker.** `lazyslice_meta` present, readable, `schema_version` at or below ours, and bound to this source and this catalog. A bound marker passes and the target is truncated with a printed line, including when its latest row says `status = running`. An unbound marker falls through to rule 5 and never short-circuits it.
5. **Emptiness.** Every user table empty by `SELECT EXISTS (SELECT 1 FROM t)`, bookkeeping and extension tables exempt, over at most 2,000 user tables. Over the cap is a refusal (exit 4) printing the table count. A table with `relrowsecurity` or `relforcerowsecurity`, or on which the probe errors for any reason including `42501`, counts as **not empty** and the refusal names the table and the reason. Never `pg_stat_user_tables`.

ARCHITECTURE.md §9 lists the same five rules with `has_schema_privilege` folded into a first rule alongside reachability, which puts it ahead of identity and locality. That ordering is observable — a remote target whose role lacks `CREATE` should be refused as remote, naming the host and `--allow-remote-target`, because that is the refusal the user can act on and because locality is the T2 control — so this ADR restores ADR-005's order and ARCHITECTURE.md §9 is corrected to match. The eligible set is identical either way; only the reason printed and the exit code change. Per docs/adr/README.md this ADR may refine §9 and may not loosen it, and moving a refusal *earlier* does not loosen anything.

The gate runs after discovery, never inside the 1 s dial; the candidate list prints `probably empty` from `EmptyHint` and the decision header prints `checking…` until the gate answers. `--target` names a database and does not bypass the gate. There is no Q3 and no `--allow-nonempty-target`.

**Tie-break among eligible targets**, applied in order and terminating: one, take it; several, prefer a name matching `/(test|local|dev|snapshot|scratch)$/`; then the one carrying our bound marker; then the lowest `(host, port, database)` in byte order. The last step is new here, and it replaces "then Q1", which was not implementable: Q1's precondition is that there is *no* eligible target, and its prompt text says so, whereas this branch is reached only when there are two. Two eligible empty databases — `app_test` and `shop_test`, neither marked — is an ordinary compose layout, not an exotic one. The winner is printed as a decision with `--target` beside it, like every other computed default, and the runner-up is printed on the same line in parentheses so the choice is visible rather than merely deterministic. A final tie-break that asks a question would also break the one-question rule in the common case, since Q2 is the question a first run should see.

**The one-question rule**, unchanged: at most one blocking question per run, the first item on the ladder **source → target → root table → row count → masking** that could not be determined with confidence. Every item below the asked one takes its computed default and is printed as a decision with the flag that changes it. An item with no safe default is not asked: the run stops, prints each probe and what it found, and gives the command to run instead. On the happy path the single blocking question is **Q2, the root table, defaulting to the top-scoring table**; that is the only question CONCEPT.md's transcript shows and the only one a first run should normally see.

### 6. The question catalogue, complete

Every question the tool may ask. Nothing else is asked, ever.

| Q | Prompt | Default | Fires when | No controlling terminal or `--yes` | Flag |
|---|---|---|---|---|---|
| Q1 | `no local postgres found to load into. start one? postgres:<major> as lazyslice-target-<project> on port <free> [Y/n]` | **Yes** | source found, no eligible target, **and the resolved Docker endpoint is local (§3) and reachable** | hard failure, exit 4, naming `--create-target` | `--create-target` |
| Q1′ | `target <name> is stopped — start it? [Y/n]` | **Yes** | the only target-shaped candidate is a stopped container (rung 4) — asked **before** the gate runs, see below | takes the default | `--target` |
| Q2 | `root table? [customers]` | **the top-scoring table**; `?` prints the ranked top five with score components | source and target determined | takes the default | `--root` |
| Q4 | `password for <role>@<host>/<db>:` | none — a secret prompt, outside the one-question budget | an **explicitly given** endpoint (rung 0, `--source`, `--target`, positional DSN) whose DSN, `PGPASSWORD`, `PGPASSFILE` and `--password-command` are all empty; see below | hard failure, exit 5 | `--password-command` |

Q1, Q1′ and Q2 are blocking and mutually exclusive within a run; Q4 may accompany one of them because it is a secret prompt, not a configuration decision (research/SQLIT_STUDY.md §6). After Q4 the run prints the one-line tip in ARCHITECTURE.md §9 naming `~/.pgpass`/`PGPASSFILE` and `--password-command`.

**Q1′ is asked before the gate, not after it.** A stopped container is not reachable, and §5 makes reachability the precondition of every gate rule, so "the eligible target's container is exited" describes a state that cannot exist: as written in ARCHITECTURE.md §9 the question could never fire. The sequence is therefore:

1. Discovery finishes. If exactly one candidate is target-shaped and it is a rung 4 stopped container, Q1′ is asked at that point, with the gate not yet run and `checking…` not yet printed.
2. **Yes** (including the no-terminal and `--yes` default, which starts it — starting a container the developer already has is neither creating nor destroying, so THREAT_MODEL.md T2's headless rule does not require a flag for it): the container is started and the run waits for `pg_isready` for up to 60 s, the same wait and the same printed progress as ARCHITECTURE.md §9 "Provisioning". The gate then runs against the started container from rule 1, with nothing skipped and no rule relaxed by the fact that we started it.
3. **The container does not come up within 60 s:** exit 4 with the event code `target.refused.start_timeout`, naming the container, the elapsed wait and `docker logs <name>`. The container is left running; lazyslice never removes one.
4. **It comes up and then fails the gate:** the gate's own refusal, verbatim — its exit code, its event code and its text, unchanged by the start. A started container is not a licence.
5. **No:** the candidate is not a target and no other exists, so the run stops. Q1 cannot be the follow-up, because one blocking question has been asked; the run takes Q1's no-terminal path — exit 4 naming `--create-target` — which is the same stop the same state produces headlessly.

**Q4 fires only for an endpoint that was given, and never inside a budget.** A password prompt cannot live inside the 1 s per-candidate dial, and the ladder must not stop four times for four password-less candidates. So the two halves are separated:

- **In discovery**, a candidate whose connection has no password available is not prompted for. It resolves as `Reachable = false` with `ConnectErr` reading `no password (see ~/.pgpass, PGPASSFILE, --password-command)`, prints in the candidate list like any other unreachable candidate, and the ladder continues. It is therefore never selected as source or target, since both are chosen from reachable candidates only.
- **Q4 is therefore only ever asked for an endpoint that short-circuited the ladder** (§1): rung 0's yml, `--source`, `--target` or the positional DSN. It is asked when that endpoint is first connected, after the ladder has finished printing, outside the 2 s listing budget and outside the 1 s dial. At most two prompts occur in one run — the source's, then the target's — and each fires at most once; a wrong password is the connection's error, not a re-prompt.

That is also why Q4's exemption from the one-question budget cannot multiply into a wall of prompts: the number of Q4 prompts is bounded by the number of endpoints the user named, which is at most two.

**Not questions, printed as decisions, with their fixed defaults:** which candidate is the source (`--source`); which is the target (`--target`); rows already present in a marked target (truncated); row count (500, `--take`); whether a classified column is masked (always; `--unmask TABLE.COL=REASON` per column); which masker (the classifier's; the yml); the child cap (100 per parent key per edge, printed in the plan; `--cap`); depth (3, `--depth`); whether `lazyslice.yml` is written (always on success; `--no-config`); whether `.gitignore` gained an entry (printed; ARCHITECTURE.md §9 "The repository").

### 7. How a question is asked

These are decisions ARCHITECTURE.md §9 left implicit, taken from research/FIRST_RUN_STUDY.md findings 3 and 4.

- **Every prompt is written to stderr and read from the controlling terminal, whatever stdin is.** `os.Stdin` is never read for an answer, never checked to decide whether to ask, and never consulted at all. The trigger for the `--yes` path is the absence of a controlling terminal — `/dev/tty` cannot be opened, or on Windows the console handle cannot be got — and nothing else. In that state Q1 and Q4 become their hard failures and Q1′ and Q2 take their defaults, which is the CI case ADR-004 relies on, since a CI runner has no controlling terminal.

  The two halves are stated separately because an earlier draft ran them together and cancelled itself out: "read from the controlling terminal" plus "a pipe on stdin is treated as `--yes`" leaves the tool prompting only when stdin is already a TTY, at which point `isatty(os.Stdin)` and `bufio.NewReader(os.Stdin)` satisfy the words exactly while being the pattern the rule exists to reject. Under the rule as now written, `echo y | lazyslice` from a terminal *asks the human at the terminal* and the piped `y` is still sitting unread in the pipe; the same command from `cron` or CI takes the `--yes` path and creates nothing. lazygit's `bufio.NewReader(os.Stdin)` (research/FIRST_RUN_STUDY.md §1) is what this rejects, and the reason is safety rather than ergonomics: Q1's yes branch creates a container and Q4's answer is a password.

  The owed test is written so a stdin implementation fails it: stdin is a pipe holding `y`, a controlling terminal is present and answers nothing, and the assertion is that no container was created and that the pipe was not drained.
- **The bracketed letter is the default and the only thing a bare Enter selects.** `[Y/n]` means Enter is yes; `[y/N]` would mean Enter is no. Anything other than an empty line, `y`/`yes` or `n`/`no` (case-insensitively) re-prompts once and then takes the default.
- **Q1 keeps its `Yes` default**, against lazygit's `(y/N)` precedent for the structurally identical question. The asymmetry is research/SQLIT_STUDY.md §6's and it holds: `git init` writes into the directory the user will commit, while Q1 creates a disposable container that lazyslice named, owns, and that exists to be written into. The precedent is recorded so that the reversal condition below has something to fire against.
- **Q1 never starts the user's own compose services.** Starting containers the developer declared, with their images, volumes and networks, is a larger surprise than starting ours; when a compose Postgres service exists but is not running, the run prints `docker compose up -d <service>` and does not offer to run it.
- **`?` at Q2 prints the ranked candidates through the line printer and `$PAGER`** until the Bubble Tea screens land (ARCHITECTURE.md §14). `?` is the same key lazygit binds to its full keybinding list.

### 8. Discoverability

`--help` is grouped by pipeline stage, not alphabetically. `docs/FLAGS.md`, `docs/KEYBINDINGS.md` and `docs/ERRORS.md` are generated by `tools/docgen` from the flag table in ARCHITECTURE.md §8, the binding table and `internal/event/catalogue.yml`. The CI drift job **regenerates into a temporary directory, diffs, prints a unified diff and the exact regeneration command, and exits non-zero** — lazydocker's behaviour rather than lazygit's bare `git diff --quiet`, because the developer who hits this job is a contributor on their first run and CLAUDE.md's rule about first runs applies to them too (research/FIRST_RUN_STUDY.md finding 8). The TUI footer, when it lands, is computed from current state and shows only bindings that are both marked for display and currently enabled, as all three studied tools do.

## Consequences

- ARCHITECTURE.md §8's `--docker-host` row and §9's ladder paragraph are corrected to the six-step order in §3; the phase 4 discovery task builds against this ADR where the two differ, per CLAUDE.md's rule that the ADR wins and the file is corrected.
- ARCHITECTURE.md §9's gate list is reordered to ADR-005's — identity, locality, `has_schema_privilege`, marker, emptiness — with reachability restated as the precondition it is (§5). ARCHITECTURE.md §9's Q1 and Q1′ rows and its "Provisioning" paragraph gain the local-endpoint precondition (§3) and Q1′'s before-the-gate sequencing (§6). Same rule as above: the ADR wins and the file is corrected.
- `internal/discover/dockerctx` owns steps 1 to 6, the local/non-local predicate, and a JSON reader for `config.json` and the context store; it does not import `github.com/docker/cli`, and `go.mod` gains no dependency. The client is built with two options, not three, and `WithAPIVersionNegotiation` does not appear in the tree: it is deprecated and a no-op in the pinned `moby/moby/client v0.6.0`, so `staticcheck` would fail `make lint` on it.
- `pipeline.Provisioner` gains a stated precondition: it is called only with a local Docker endpoint. `--create-target` against a non-local endpoint is exit 4 before any container work, so no `lazyslice-target-*` container is ever created on a daemon whose containers the gate must then refuse.
- `internal/event/catalogue.yml` gains three codes, all inside existing exits: `target.refused.unreachable` and `target.refused.no_create` (exit 4, §5), and `target.refused.start_timeout` (exit 4, Q1′, §6). `docs/ERRORS.md` is generated from the catalogue, so each gets a row.
- `Discoverer.Discover` is not called at all when both endpoints are given, so a run with `--source` and `--target` makes no Docker call and produces no candidate list. The decision header still prints both lines, with `FromFlag` provenance.
- Prompting moves behind a controlling-terminal helper that never touches `os.Stdin`. `--yes` and "no controlling terminal" become one code path, which is what makes ADR-004's "the same command works in CI" true rather than nearly true.
- research/OPEN_QUESTIONS.md items 5 and 7 are discharged, by research/FIRST_RUN_STUDY.md and by §3 respectively. Item 2 (the target side has no evidence base) is **not** discharged: none of the three tools writes to anything destructible, so the gate in §5 still rests on ADR-005's reasoning alone.
- Tests owed by this ADR, named so the phase 4 task cannot skip them:
  - `TestDockerHostResolutionOrder` — the six steps, including the literal `default` short-circuit and the empty-`Host` context.
  - `TestRemoteDockerEndpointYieldsNoLocalCandidate` — with the endpoint resolved to `tcp://staging:2375`, a container publishing `0.0.0.0:5432` produces **no** candidate, no candidate is marked `Local`, Q1 does not fire, and `--create-target` exits 4 without calling the `Provisioner`.
  - `TestPipedStdinIsNotAnAnswer` — stdin is a pipe holding `y`, a controlling terminal is present and answers nothing: no container is created and the pipe is not drained. An `os.Stdin` implementation fails this.
  - `TestNoControllingTerminalBehavesAsYes` — no `/dev/tty`, stdin irrelevant: Q1 exits 4 naming `--create-target`, Q4 exits 5, Q1′ and Q2 take their defaults.
  - `TestStoppedTargetIsAskedBeforeTheGate` — a single rung 4 candidate triggers Q1′ with the gate unrun; on yes the container starts and the gate then runs from rule 1; on gate failure the gate's own exit code is returned, not Q1's; on a 60 s timeout, exit 4 with `target.refused.start_timeout`.
  - `TestPasswordlessCandidateIsUnreachableNotAPrompt` — a discovered candidate with no password available resolves `Reachable = false` and prompts nothing; Q4 fires only for an endpoint given by flag, yml or positional DSN, at most once per endpoint.
  - `TestTwoEligibleTargetsPickLowestRefDeterministically` — two unmarked, equally-named eligible targets select the lower `(host, port, database)` and print the runner-up, with no question asked.
  - `TestGateOrderIsAdr005` — a remote target whose role lacks `CREATE` on `public` is refused as remote (exit 4, naming the host and `--allow-remote-target`), not for the privilege.
  - `TestBothEndpointsGivenSkipsDiscovery`.
  - `TestCandidatesCollapseAcrossRungs` — a local endpoint's `0.0.0.0` binding and a `localhost` `DATABASE_URL` are one candidate, lower rung's provenance printed.
  - `TestEnvFragmentsAreNotAssembledIntoADSN`.

## Reversal condition

- **Q1's default.** If two dogfood sessions (ARCHITECTURE.md §14 defers provisioning to phase 5, so the first of these is phase 5's) end with a `lazyslice-target-*` container the human did not want, Q1's default flips to `[y/N]` and this ADR is superseded. lazygit's `(y/N)` is the precedent that would then apply.
- **The single default socket.** If any dogfood or issue report shows a machine with a working `docker` CLI where lazyslice's step 6 resolves to a default socket that does not respond — an OrbStack or Colima install that does not register a context — the resolution order gains a verified, cited list of vendor socket paths after step 6, and `docs/ERRORS.md` gains the code.
- **`ssh://` endpoints.** If a design partner's normal setup is a remote daemon over SSH, tunnelling is reconsidered as a third subprocess, which requires a THREAT_MODEL.md revision first.
- **Non-local endpoints generally.** If a dogfood session or issue report shows a developer whose *local* Docker containers are reached through a non-local endpoint — a `tcp://` daemon on a VM with the ports forwarded onto this machine is the plausible shape — the predicate in §3 gains a case, stated as a verified fact about that setup with the forwarding named, plus a test. It never gains "assume local"; a rung 3 or 4 candidate lazyslice cannot prove is local stays out of the list, because the wrong answer here is a write to someone else's database (THREAT_MODEL.md T2).
- **The `working_dir` filter.** If a dogfood run finds the right container only through the "then any" fallback more often than through the label, the filter is wrong and rung 3's ordering is re-derived from what compose actually stamps.
- This ADR cannot be reversed on the target gate: that is ADR-005's decision and only a superseding ADR to ADR-005 changes it.
