# lazyslice threat model

Written 2026-09-05 against docs/adr/001 to 006 and ARCHITECTURE.md; revised the same day after the phase 2 adversarial review (tracker T-0018). Each threat names the research that evidences it, its likelihood and impact, the concrete control we build, and whether that control blocks v1. "Blocks v1" means the phase 4 gate cannot be ticked without it (docs/BUILD_PLAN.md Gate 2 requires at least three; this document has thirteen threats and every one carries a blocking control). The phase 5 red team (docs/BUILD_PLAN.md PROMPT 5.4) updates this file; nothing is removed from it, only marked.

The promise this document defends is CONCEPT.md's: the output is pseudonymised, not anonymised. Deterministic masking preserves frequency; a snapshot is personal data under GDPR Art. 4(5) and must be regenerated after an erasure request (research/HARD_PROBLEMS.md §2.3). The README says so in those words.

## Assets

| Asset | Where it is | Who must not get it |
|---|---|---|
| A1 Production row values | the source database; in the process between extract and transform; in the `RowBatch` channels | anything outside the process: logs, events, the yml, the terminal, a masker we did not write, the network |
| A2 The target database | the developer's local or CI Postgres | it must never be production, and must never be half-loaded and green |
| A3 Source credentials | the DSN, `.env`, `PGPASSWORD`, `~/.pgpass`, container env, `--password-command` output | the yml, events, `--json`, `lazyslice_meta`, error text |
| A4 The masking key `K` | `./lazyslice.secret` or `$LAZYSLICE_SECRET` | git, the yml, the target, events; anyone who can confirm guesses against fakes |
| A5 The snapshot on disk | none by default: lazyslice writes to a database, not a file. `snapshots/` is reserved and gitignored for a future export | git, synced folders |
| A6 `mapping_file:` CSVs | paths named in the yml; original values in plaintext; must reach every machine that reproduces the snapshot, which is the audience the snapshot exists for (ADR-006, revised) | git; anyone who would not be given source access — the file is distributed like a source credential, by hand or through the same secret store as `LAZYSLICE_SECRET`, never through the repository |
| A7 The emitted `lazyslice.yml` | the repository | must carry references and decisions, never A3, A4 or A1 |
| A8 The release binary | GitHub releases, the Homebrew tap | must be the binary CI built from the tagged commit |
| A9 The source database's health | the source's xmin horizon, a standby's replay | a snapshot held longer than the plan said |

## Threats and controls

Each control is a mechanism, not a sentence; where a test enforces it, the test is named. Exit codes are ADR-005's.

### T1 The classifier misses a personal-data column, and the run exits 0 with cleartext in the target

Likelihood: high. Column-level detectors average macro-F1 0.61 to 0.87 and their authors call false-negative rates too high for practice (research/HARD_PROBLEMS.md §3.2); silent success is the most-evidenced failure class in the corpus, seven reports across five tools (research/SYNTHESIS.md §1 fact 3; research/COMPLAINTS.md "Frequency ranking"). Impact: the project ends; "you can't un-leak it" (research/SYNTHESIS.md §2 risk 2).

Controls. The classifier's recall is defended by exactly two things, and this row does not claim a third:
- Recall bias: `possible` and above is masked, after the neighbouring-column rule and FK propagation; a name hit alone is `possible`; special categories mask on name alone; free text and every JSON leaf are masked whole; there is no exemption by type (ARCHITECTURE.md §4, revised: the enum exemption is gone); the neighbouring-column rule raises `low` to `possible` in any table with a `likely` column.
- Composite columns fail closed (T-0094, 2026-09-09): a composite-typed column is classified over its text form; a value hit at possible or above is a plan refusal (exit 12) naming the column and offering --skip-table or a reasoned --unmask, never a silent copy; a composite with no hit is copied and the reason says so. Field-wise masking of composites is later work.
- Recall boundary (ADR-010): a value signal is silenced on timestamp, date, time, interval, boolean, bytea, numeric and tsvector families for categories whose maskers emit text; enum, xml and other families are never silenced. A tsvector is always masked to empty.
- Second net: the classifier's value validators over the full contents of every column the target holds unmasked, and the string leaves of masked JSON columns; a column at the strong threshold (0.8) is exit 9 (ARCHITECTURE.md §6 item 4). As implemented in phase 4 the net is narrower than the classifier in three ways, recorded in internal/verify/CLAUDE.md: it registers eight of the ten validators (person_name and free_text are absent until the name dictionary has a shared home, tracker T-0055); it reads character, uuid, inet, cidr and macaddr families only, so a tsvector or enum column is skipped (tracker T-0050); and it applies only the strong threshold, by decision (T-0056, 2026-09-08): the classifier's weak-plus-neighbour raise already ran over the source sample, and the net's job is the under-sampled column, for which the strong threshold over full contents is the right instrument; the alternative reading would turn the net into a 0.5-threshold scan across every table holding a masked column, a different control that would need its own T1 review. It catches a column the 200-row sample under-represented. It does **not** catch a category outside the rule pack, because it runs the same rules; a category the pack lacks is missed twice.
- Recreated DDL is inside the data boundary (amended 2026-09-14, T-0134). A string literal in a column `DEFAULT`, a `CHECK` constraint or a generated-column expression is recreated in the target verbatim (ARCHITECTURE.md §11.1), so it crosses exactly as a row value does — and no control above sees it, because every one of them scans rows. The 2026-09-09 review put `DEFAULT 'ddl.canary@example.org'` on a masked email column, watched every row be masked and the default survive into the target's `pg_attrdef`, and the run exited **0** (finding 5, `docs/reviews/2026-09-09/evidence/ddl_default.log`); the application's next `INSERT` taking that default puts the address back into a row. Three controls, all landed by T-0134: a masked column's default has its literals masked through that column's own masker, so the default stays a working default whose value is the one a row holding that literal would have (`internal/plan/ddlliteral.go`); a literal lazyslice may not rewrite — a `CHECK` or generated expression, whose meaning is the application's — that a strong validator hits is **exit 13** naming the object, and the same literal in the DDL of a column the run does not mask is **exit 12** with the per-column `--unmask` escape and its reason; and `internal/verify/catalog.go` reads the target's own `pg_attrdef`, `pg_constraint` and `pg_index` back after the load and fails **exit 9** on a strong hit, which is the second look at the artefact rather than at the plan. **What the validator set covers here, stated rather than hidden, and how it grew:** three shapes a parser decides at first (email, phone, payment card), five once national_id and IBAN joined (2026-09-15, below), and — since the 2026-09-15 amendment at the end of this row (T-0189) — every one of §4's categories that is a parse or a shape rather than a guess over anything: `network_id`, `online_id`, `person_name`, `address` and `free_text` now run too, so a person's name or a street address sitting in a `CHECK`, an index predicate, an enum label, a domain `CHECK`, a domain `DEFAULT` or a generated expression, masked column or not, is refused. `credential` still is not run, for a reason that has nothing to do with the dictionary argument the rest of this narrowing answers — see the amendment for the measured cost of including it. **One exemption, also stated rather than hidden:** the catalog pass does not judge the `DEFAULT` of a column this run masked **and whose default the planner actually rewrote**, nor the `DEFAULT` or generated expression of a column carrying an `--unmask` opt-out. The masker's output for an address is another address, so a pass that judged it on shape alone would refuse the run that masked correctly, and this stage holds no key with which to tell the masker's output from the source's value; the second net has the same arm on the row side for the same reason. It is narrow twice over. By object class: a `CHECK`, an exclusion, a generated expression on a *masked* column and an index predicate are never rewritten by anything, so a strong hit in one of those is still refused. And by provenance: the arm reads `pipeline.Column.DefaultOriginal`, which `internal/plan` writes into the schema verify is handed only when it masks that default, so a masked column whose default still holds the *source's* text is judged like any other object. That second narrowing is what kept the T-0161 gap, while it stood, from turning the exemption into a hole — with no default rewritten, none was exempt. Two gaps were filed rather than papered over, and both are now closed. The **plan-time** pass read no index predicate and no domain `CHECK` (tracker **T-0163**) while the catalog pass read both, so the miss cost the earlier and cheaper refusal rather than the control — closed 2026-09-15 (T-0189, below): the plan-time pass now walks every index it will recreate through the same never-rewritten rule a `CHECK` gets. And `internal/core` now resolves the run key ahead of the plan stage, for any run that will write, and hands it to the planner (**T-0161**, amended 2026-09-14), so a masked default that can be masked is masked rather than refused at exit 13, and the catalog pass exempts exactly the defaults arm 1 actually rewrote — no more, because the exemption is still keyed on `DefaultOriginal` and not on the decision. A plan-only run with no key yet does not regress this: it resolves a key only where one already exists rather than creating one, plans with `PlanRequest.Key` nil, and `internal/plan/ddlliteral.go` reports the affected defaults on `Plan.PendingKeyDefaults` instead of refusing or masking.
- No pass-through mode exists; the CI grep on `no-mask|disable-mask|skip-mask|unsafe` fails the build (ADR-004).
- Invariant I2 in CI on both fixtures, including `nasty.sql`'s `ref` column holding emails and its JSONB and notes traps (docs/BUILD_PLAN.md PROMPT 3.3).
- The README lists what the green tick does not prove, beginning with preserved row identifiers (ARCHITECTURE.md §6 item 6).

**Amendment, 2026-09-15 (the red team's A1, A2, A2b, A3, A4a, A4b, A5b, A11, A12 and A20).** Six of the red team's attacks came through this row and every one exited **0**. What they have in common is that both of the two controls above ask the *same* question — does a validator recognise this value, does a rule pack recognise this name — so a value or a name neither recognises is missed twice and the report affirmatively prints "no name or value signal", which reads as a clean bill of health for a column nobody looked inside.

- **A name in another language, in a column named in another language (A1, A2b).** A `klienci` table whose `nazwisko`, `imie`, `pesel`, `komorka`, `cognome` and `achternaam` columns held real-shaped Polish, Italian and Dutch values crossed verbatim: the rule pack's name rules were only accidentally multilingual (they carried *correo*, *courriel*, *nachname*, *prenom* and nothing else), and `internal/textsig/names.txt` was English only — a stated limit that ARCHITECTURE.md §14 deferred to phase 5. Both halves landed: the name, phone, national_id, email and address rules gained the spellings above and about sixty more, and `names.txt` gained the given/surname stock of twenty-one languages. The dictionary is the half that matters, because both nets read it and because **a rule pack is never complete** — the patterns are a patch and are labelled as one in `rules.yml` itself. What is still missed: a name in a language the dictionary does not carry, in a column named in that language, with no other signal in the table. That is a narrower statement than "English only" and it is not zero.
- **A value written so that no parser recognises it (A2, A3).** A phone number as "plus four four, two oh, seven nine four six, oh nine five eight"; an address as "grace.hopper AT realcorp DOT example"; a national insurance number with interleaved spaces; a payment card with "." separators, which `ValidLuhn` rejected outright — the card then matched `ValidMAC`, because a dotted sixteen-digit run parses as a hardware address, and was masked to an IP: the right direction under the wrong category, and no masking at all on a family `network_id` cannot hold. `internal/textsig/candidates.go` is the fix: `ValidEmail`, `ValidPhone`, `ValidLuhn` and `ValidIBAN` now read every spelling `textsig.Candidates` yields — the at/dot words in four languages, spelled-out digit runs with *double* and *treble*, a value grouped with spaces, and the address inside an RFC 5322 display name — and `ValidLuhn`'s separator set gained `.`, `/` and the non-breaking space. Because `internal/textsig` is the one home for a value shape, both nets gained it in one change. **The national insurance number in that list was not actually closed by the first landing** (the T-REDFIX review's third finding): `spelledDigits` required the *whole* value to be digit words, so `AB nine eight seven six five four D` — the attack's own value, letters and all — still validated as nothing, and only its all-digit spelling was tested. A field of four characters or fewer that is letters and digits is now carried through into the candidate, under three guards that keep prose out (at least one digit actually spelled, a digit floor, and an alphanumeric floor over the candidate).
- **A value in a column the classifier skips by type (A4a).** `internal/classify`'s `bestSignal` returned before any validator ran for a `bytea`, and `internal/verify`'s second net had no `bytea` in its family set, so a `bytea` holding printable UTF-8 with an address in it was read by nothing on either side — in a table with no `certain` column, so `byteaInPersonShapedTable` could not fire either. The guard is on content now: a value that is valid UTF-8 and at least 95% printable (`textsig.PrintableText`, read by both nets so they cannot disagree) is offered to the validators, and a hit makes the column `binary_personal`, which is already NULLed. A PNG fails the printability guard and is untouched. **The "cannot disagree" was not true as first landed** (the T-REDFIX review's second finding): `internal/classify` also required 95% of the *sample set* to be readable before it ran any validator, where the second net asks the per-value question and nothing else — so a `bytea` column of half documents and half images was left unmasked by the classifier and refused at exit 9 by the verifier, a run with no green path, because `binary_personal` cannot be reached for such a column by any other route. The column ratio is gone; both sides now ask exactly `PrintableText`, per value. The cost is in the fail-closed direction: a column of images holding one readable blob that a validator hits is masked rather than left alone.
- **A document could dilute its own column out of the net** (the T-REDFIX review's high finding, on the A5b fix below). The second net counted a document's leaves into the *column's* non-NULL count, which is both the ratio's denominator and the "unproven, so any hit fails" gate — so adding a JSON document to a text column *raised* the denominator and turned a refusal into silence: a two-row column holding `221 Baker Street, London` is exit 9 on the address, and the same column with a four-key object in the second row exited 0. Leaf-derived strings are now scored against their own denominator (`internal/verify/secondnet.go`'s `netTally`), so a document is evidence about the document and never about the column's own values.
- **A document inside a column declared `text` (A5b).** `internal/classify`'s leaf signal runs only under `isJSONFamily` and `internal/verify`'s leaf walk only for `json`/`jsonb`/`hstore`, so a three-level JSON document in a `text` column — one of the commonest shapes in a real schema — was seen by neither. **This is closed fail-closed and not closed properly.** The second net now walks the leaves and keys of any character value that parses as a JSON object or array, so such a column is **exit 9** rather than a silent copy; the classifier still cannot *mask* it, because `semi_structured`'s writable families are `json`/`jsonb`/`hstore` in the `mask` module, which was outside this task's paths. Tracker **T-0182** carries the rest.
- **A value in the schema rather than in a row (A4b, A11, A12).** The 2026-09-14 amendment below put string literals in recreated DDL inside the data boundary and listed four object classes. Three more were missing and all three were recreated verbatim: an **enum label**, which `internal/load/ddl` writes as a string literal in `CREATE TYPE ... AS ENUM`; a **domain's `DEFAULT`**, which lives in `pg_type.typdefault` and not in `pg_attrdef`; and a **domain's `CHECK`**, which `internal/verify` saw through `pg_constraint` and `internal/plan` did not see at all, because it read no domain. An address and a phone number crossed into `pg_enum` under a green tick, and a domain default is the 2026-09-09 finding 5 mechanism exactly — the application's next `INSERT` that omits the column materialises it back into a row. All three are read now by both passes. **None of them is rewritten, and that is a decision and not an omission:** every row of every column of an enum type references a label *by value*, so masking a label would either break the column or silently remap rows, and a domain's default belongs to the type rather than to a column, so there is no single masker whose output would be the right replacement. So the outcome is **exit 13** naming the type and the position of the label — never the label text (T4). **The escape is `--allow-type-literal TYPE=REASON`, and it had to be built** (the T-REDFIX review's fourth finding): this bullet, the refusal itself, `internal/plan/codes.go` and `testdata/regressions/016`'s header all named `--skip-table`, which cannot clear the refusal by any route — that flag drops a table to *schema only*, so its DDL and every type that DDL names are still recreated, and nothing prunes an enum or a domain from the schema. A source schema carrying one such label was therefore unrunnable, under a message naming a flag with no effect on it. The new flag is this row's rail made configurable **per type and with a written reason**, the same shape `--unmask TABLE.COL=REASON` has for a column: the name is resolved against the source's own enums and domains, so an opt-out that could never apply is exit 2 rather than silence, and `internal/verify`'s catalog pass honours the same list (`Plan.AllowedTypeLiterals`) so the run that gets past the planner is not refused at exit 9 over the object the operator was told they had allowed. What it costs is stated plainly: an operator who names a type here has turned off both looks at that type's recreated DDL, and the reason they typed is the only record of why.
- **The strong set was three validators (A20).** A `CHECK` carrying `Alice Anderson, 42 Elm St, SSN 123-45-6789, IBAN GB33BUKB20201555555555` crossed under exit 0. The paragraph below states the name-and-address half of that and gives the reason — a `CHECK` is full of English words, so a dictionary heuristic over one would refuse ordinary schemas — and that reason does not reach the other two: a US Social Security number and a UK National Insurance number are strict patterns, and an IBAN is a mod-97 checksum. `national_id` and the IBAN half of `financial_account` join the strong set used by both the plan-time and the catalog pass; `person_name` and `address` stay out for exactly the reason given, until 2026-09-15's second amendment below (T-0189) answers it. **Amendment 2026-09-15 (T-0187, T-0193, T-0194).** `national_id` is a row-path control as well, not only a DDL-literal one: `internal/textsig/nationalid.go` carries twelve formats with their real check rules, and they are split by evidence quality. The structured formats (a dashed US SSN, a UK NINO, an Italian codice fiscale, a Spanish DNI or NIE, a French NIR) are strong in classify, in the second net and in both DDL passes, which read `ValidNationalIDStructured` only: the six checksum-only formats (PESEL, BSN, SIN, TFN, CPF, Aadhaar) clear a random digit run of the right length between 9% and 26% of the time and are therefore never strong and never refuse a plan on one literal. On numeric families a nine-digit value shaped like an SSN is a digits validator under the ratio rule, and the second net may refuse on it only with corroboration: the column's name matches the `national_id` name rule, or the table already holds a likely or certain personal column; a plain run of account or invoice numbers with neither is never refused (regressions 018 to 023). What is still missed, narrowed by the amendment below: a bare nine-digit identifier with no dashes, in a column with no name signal, in a table with no other column decided `possible` or above under a person-identifying category. IBAN could not have joined before: `ValidIBAN` matched any fifteen-to-thirty-four-character run of letters and digits that cleared mod-97, which five of pagila's own film titles do, and it now requires the two ISO 13616 check digits in positions three and four. **Amendment 2026-09-15 (T-0189, the round-2 red team's R2-07, R2-08, R2-09 and R2-10; docs/reviews/2026-09-15-redteam/round2-still-leaking.json).** The reason `person_name` and `address` had stayed out — a `CHECK` is full of English words, so a dictionary heuristic over one would refuse ordinary schemas — is an argument about *identifiers* in the surrounding SQL text, and both DDL-literal passes read only the *literals* inside that text (`pipeline.Literals` never returns an identifier). Run over a literal instead of over a whole expression, the argument does not hold, and R2-07 is the proof: a table `CHECK` carrying `'Aurelio Nakamura-Okonkwo'` and one carrying `'1742 Kestrel Hollow Lane, Ashford VT 05024'` both crossed under exit 0 — as did the same two shapes, plus a special-category sentence, inside an enum label, a domain `CHECK`, a domain `DEFAULT` and a generated expression (R2-09, the same four object classes the A4b/A11/A12 amendment above taught both passes to read). **The special-category sentence is not closed, only narrowed by accident: `pipeline.CatSpecial` has no value validator at all**, in either DDL pass or the row-side second net, so R2-09's own canary is caught only because its date supplies `AddressShape`'s digit — strip the date and a health/special-category sentence with no name pair and no digit still crosses under exit 0, wherever it sits. Tracker T-0198 carries a validator for it; nothing below should be read as closing that case. Both DDL-literal passes now run `person_name`, `address` and `free_text`, and, for the same reason, the two categories the set had never carried at all — `network_id` and `online_id`. **`credential` is the one category that does not join, and the reason is unrelated to the argument above:** `textsig.LooksSecret` is an entropy guess over any string rather than a parse or a dictionary shape, and a column `DEFAULT` calling `nextval` embeds exactly that shape by construction — the literal these passes read out of `nextval('public."AccessCode_id_seq"'::regclass)` is the sequence's own quoted, mixed-case relation name. Running this amendment with `credential` included refused three of `testdata/torture/`'s ten real-world schemas (calcom, gitlab, discourse) and one regression fixture over exactly that shape, never a person's, so it was removed before landing; running a validator over a literal instead of a whole expression closes the *dictionary* argument and does nothing to close an argument about a validator's own precision, which is the same reason the checksum-only six of `national_id` stay out on T-0194's unrelated, measured argument above. **A second miss closed alongside the first:** a value on the right-hand side of a pattern operator (`LIKE`, `~`, and their kin) was exempt from every validator, not only from being rewritten, so `CHECK (email !~ '^ceo@bigcorp\.example$')` carried the exact address `ceo@bigcorp.example` and crossed under exit 0 while the semantically identical `CHECK (email <> 'ceo@bigcorp.example')` refused (R2-10). `pipeline.StripPatternMeta` reduces a pattern literal to the value hiding inside it — stripping the wildcard and anchor syntax and unescaping a backslash-escaped metacharacter to the literal it stands for — before either pass validates it; a pattern literal is still never rewritten by either. **A third closed the same day: `internal/plan` read no `pg_index` at all (tracker T-0163),** so a partial index's predicate or an expression index's key expression — which carry no `pg_constraint` row and are recreated verbatim by `internal/load/ddl` — reached the target unexamined by the plan-time pass, and the catalog pass below was the only look at it: exit 9 after the target was already loaded rather than exit 12 or 13 before anything was dropped. `internal/plan`'s `tableDDLLiterals` now walks every index the same way it walks every constraint. Together, the three findings closed one gap stated three ways: the object classes both passes read and the category list their validators cover are now the same at plan time and at the catalog pass. **Amendment 2026-09-17 (T-0240, the round-4 red team's three A9b replays: docs/reviews/2026-09-15-redteam/round4-still-leaking.json).** The corroboration gate above ("the table already holds a likely or certain personal column") missed a neighbour the run had already decided to mask but not yet raised that far: a column named for a personal category with no value signal of its own — `msisdn`, matched on `rules.yml`'s own phone pattern, with no `--phone-region` configured and no international-form value to confirm it — decides at `possible`, one confidence line below what the gate counted, so a `taxref` column beside it (a national identifier, bigint or `varchar(9)`, dense or sparse) still refused nothing even though the table held a masked personal column. The gate now also counts a masked, person-identifying neighbour at `possible` or above (`Decision.TableHasMaskedPersonalColumn`, kept apart from the `likely`-or-above field above because that field also corroborates the classifier's own guessed-region phone pass and widening what corroborates a *guessed* reading was not this fix's question), and the digits-family entry's dense-sequence exemption — sound for an uncorroborated column, where density is the only signal available — no longer overrides corroboration once corroboration exists to ask: a contiguously issued identifier block (a payroll or benefits import) reads exactly as dense as a surrogate key, and before this fix density was checked first and corroboration was never reached. **A same-day review round found that rule too wide, and the fix now has a carve-out rather than a flat override.** `corroborated` counts any masked, person-identifying neighbour, whatever it is; an ordinary foreign-key child column is dense because its values ARE its parent surrogate key's, copied verbatim, which has nothing to do with an unrelated `email` column decided elsewhere in the same table — reading `corroborated` alone let that unrelated column cancel `order_id`'s exemption and refused a correct run (`testdata/regressions/021`'s own control, restored to the shape that pins it). The exemption now stays unconditional for a column `internal/classify` has already decided is a surrogate key or a validated foreign-key child whose parent stayed unmasked (`Decision.NeverMasked`, carried the same way the three corroboration fields are); `corroborated` still defeats it for every other dense column, which is what still refuses `032` and `033` below. The character family gained the identical entry the digits family already had — `ok: textsig.ValidNationalIDDigits`, offered to `text`/`varchar`/`bpchar`/`citext` too — because a zero-padded national identifier stored as `varchar(9)` had reached no row-scanning validator at all: the character-family `national_id` entries read only `ValidNationalIDStructured` (needs a dash, a letter or NIR's fifteen characters) and `ValidNationalIDChecksumOnly` (six formats, none a bare nine-digit run with no separator), and moving the value off the numeric family changed nothing about which validator saw it. **What this amendment still misses, named rather than implied.** `Decision.TableHasMaskedPersonalColumn` is computed inside `neighbouringColumns`, in the same loop as `Decision.TableHasLikelyPersonalColumn` and before `sameColumnName`, `keyChildren` and `foreignKeys` run, and before `neighbouringColumns`'s own later arms — `guessedPhoneColumns` and `unknownColumnsBesideCertain` — ever see the table (`internal/classify/classify.go`'s six-pass order). A table whose only person-identifying column first reaches `possible` or above in one of those later passes — FK propagation onto a masked parent, a shared-column-name propagation, a guessed-region phone hit with no name signal, or the `unknownColumnsBesideCertain` free_text catch-all beside a `certain` neighbour — sets neither field, so the residual for a bare identifier beside such a column is the T-0187 amendment's sentence above, unchanged, not this one's. The residual this amendment actually closes is narrower, in classification order, than "no other column decided possible or above under a person-identifying category" reads on its own.
- **A rail under all of it (A2b's structural half).** The neighbouring-column rule raised `low` to `possible` and had nothing to say about a character column with *no* signal at all sitting beside a `certain` personal column. `unknownColumnsBesideCertain` now masks such a column as `free_text` in any table holding a column at `certain` under a category that identifies a person — deliberately not `free_text`, `semi_structured`, `binary_personal` or `derived_text`, each of which a column reaches by its type alone, because counting those made pagila's `film` table person-shaped on the strength of its own search index. Four exclusions keep it from turning a correct run into a plan refusal: a never-masked column, a type-conflicting decision, a column under a unique index, a column of two-letter codes, and a declared length under sixteen characters. It does **not** reach A2b's own table, which has no `certain` column at all; it is the rail under the next value shape neither net recognises.

**And one correction to what this row claims.** The "Second net" bullet below says it registers eight of the ten validators; it has registered all eleven since T-0055 and T-0122, and `person_name` and `free_text` are scored under a narrower rule rather than absent (internal/verify/CLAUDE.md, "the dictionary rule"). More importantly, nothing in this row should be read as saying the value validators are a net over *unrecognised* text. **They are a net over recognised shapes only.** Every control here — the classifier's signals and the second net alike — answers "is this value one of about a dozen shapes we can parse or guess at". A shape outside that list, in a column no name rule matches, in a table with no other signal, is copied; the red team's A2b is exactly that case and the multilingual dictionary is what closed the instance rather than the class.

### T2 The target is production

Likelihood: medium. The transposed-arguments report is real (research/COMPLAINTS.md PII-13); a pooler alias, a DNS name and a loopback can all name one cluster. Impact: masked fake rows written over production, "the worst possible failure" (research/SQLIT_STUDY.md §5.0).

Controls (ADR-005 "Target", revised; ARCHITECTURE.md §9 "Target" is the ordered rule):
- **Identity** is a disjunction over sameness, not a conjunction over difference: the target is refused iff normalised `host:port/database` equals the source's, or `system_identifier` and `current_database()` both equal the source's. A second database on the same cluster is eligible and the header prints `same cluster as source` as a warning. Exit 2 before any connection is used for writing.
- **Locality**: the target is `Candidate.Local` or named by `--allow-remote-target HOST`; otherwise exit 4. Every other rule is satisfied by an empty, freshly provisioned production database during a migration, and the transposed-argument report (research/COMPLAINTS.md PII-13) is as likely to name an empty remote database as a full one. The argument that overruled a loopback restriction for the source does not apply to the side that is written.
- **Marker**: `lazyslice_meta` authorises truncation only when it is bound — the latest row's `source_fingerprint` (and `source_system_id` when both sides have it) matches the current source and its `schema_fingerprint` matches the target's current catalog (ARCHITECTURE.md §11.2). A marker left by a run against another source, planted by a colleague, or sitting beside a table we did not create authorises nothing and falls through to the emptiness check. The marker is therefore not a persistent artefact that can convert a database into a truncate-on-sight target after it has acquired a life of its own; this is the sentence the previous draft got wrong.
- **Emptiness**: every user table empty by `SELECT EXISTS (SELECT 1 FROM t)`, bookkeeping and extension tables exempt, over at most 2,000 user tables. **Above the cap the target is refused** (exit 4, `target.refused.table_cap`, table count printed); it is never sampled, whatever research/SQLIT_STUDY.md §5.2 proposed. `Eligibility.Verdict` is tri-state and `NotProbed` is never eligible. A table with row-level security enabled or forced, or on which the probe errors for any reason, counts as not empty and is named: under `FORCE ROW LEVEL SECURITY` with no matching policy, `EXISTS` returns false over millions of rows while `DROP TABLE` still succeeds — the same trap as `n_live_tup`, by a different mechanism. Never `pg_stat_user_tables`.
- No flag reaches a non-empty unmarked database. `--target` names, it does not bypass; there is no `--allow-nonempty-target` and no `--replace`. The refusal (exit 4) prints the row counts and the command that would clear the database.
- The gate is re-run on every run, including Scenario D with a committed yml; the file supplies the target's name and nothing else, and the marker binding above is what stops a file plus a marker from authorising a write to a database that has since acquired rows.
- Headless: anything that would create or destroy needs its flag (`--create-target`); nothing is truncated silently except rows in a bound marked target, which is printed.
- **Ownership across the interval (amended 2026-09-14, T-0130).** Every control above is a decision the gate makes and the loader acts on several stages later, and until this amendment nothing owned the target in between: the gate released its connection, core introspected, classified and planned, and only then did the loader drop tables. The 2026-09-09 review reproduced the consequence — an empty unmarked target was approved, source introspection was held up, a row was inserted into that target, the source was released, and lazyslice deleted the row and exited **0** (finding 1, `docs/reviews/2026-09-09/evidence/target_race.py`, `race.log`). Two controls, both required, and neither is configurable away:
  - **A run lease.** A dedicated target connection opens a transaction and takes `pg_try_advisory_xact_lock` over a key derived from the target database name before the gate's first probe, and holds both until the marker row is finished, naming itself `application_name = 'lazyslice run <run_id>'` locally to that transaction. A second lazyslice run against the same target is refused at **exit 4** (`target.refused.lease_held`) naming the run id that holds it. A lease that cannot be taken is a refusal, never a fall-through. **The lock is transaction-scoped and the name is transaction-local because the target may be behind a pooler** (T-0130 review, 2026-09-14): a session-level lock taken outside a transaction is left on a server connection a transaction-pooling pooler hands to somebody else — measured, in `internal/pg/pooler_integration_test.go`'s `TestAPooledTargetLeaseIsReleasedForTheNextRun`, as both an orphaned lock that would refuse later runs with a holder that does not exist and, on the same routing, a second run taking the lock the first still believed it held. A transaction lock ends with its transaction or with its session and cannot outlive either, which is the same fail-closed direction T-0076 established for the source.
  - **Lock-and-recheck before every destructive DDL.** Each table's `DROP` runs in a transaction that first takes `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE NOWAIT` on the table when it exists, and then re-verifies what the gate approved: on an unmarked target that the table is still empty, on a bound marker that the marker row the gate read is unchanged. A change refuses at **exit 4** naming the table and its row count (`load.refused.target_changed`, `load.refused.marker_changed`) and closes this run's marker row `failed`. The rollback is the *refusing* transaction's, and that is the whole of what it undoes: the table the refusal is about is untouched, and tables dropped by earlier transactions in the same run stay dropped — each of those was dropped under its own lock after its own recheck, so no unauthorised rows are lost, but their definitions are gone and the target is left part-way through a rebuild. The next run's gate refuses it rather than finishing it silently, because a marker whose `schema_fingerprint` is the source's no longer matches a half-dropped catalog, so the gate falls through to the emptiness check and prints the command that clears the database. A single transaction over every drop would make the loop atomic and would also put a 2,000-table target into `max_locks_per_transaction`, so it is not what this does. A lock that is not free is `load.refused.target_locked` — **SQLSTATE 55P03 only**; any other failure of the `LOCK TABLE` is the load failing at exit 7, reported as itself and not retried.
- **The residual, stated rather than closed.** Neither control stops an application from writing to the target: an advisory lock coordinates only clients that ask for it, which [PostgreSQL's locking reference](https://www.postgresql.org/docs/current/explicit-locking.html) says in as many words, and `ACCESS EXCLUSIVE` bounds a writer only for the length of the drop's own transaction. A writer that inserts after the drop commits is blocked by the lock until then and afterwards writes into the fresh table lazyslice created, which is the application behaving normally against a database it was pointed at. What is closed is narrower and is the thing the review found: no lazyslice run destroys a table on a verdict that has stopped being true, and no two lazyslice runs take one target apart together.

The round-6 review that found this added a third `checkLeaseAlive` call at the very top of `Load`, before `EnsureMarker`; what the SQLSTATE wrapping below now covers on its own is only the narrower window between that call returning alive and the marker statement actually reaching the target, the same point-in-time gap every `checkLeaseAlive` call leaves open (see "What stays residual" below) — not the whole span from the gate to the load that it covered before this review. Their errors reached the caller unwrapped before this amendment, which is not one of `core`'s six refusal types, so it fell to the generic "no stage claimed this" case (`internal/core/names.go`'s `asStop`) and exit 1 whatever the real SQLSTATE was. Both are now wrapped as `*load.Refusal` under the existing `load.refused.ddl` code, the same one every other DDL statement this package sends already uses — SQLSTATE 23505 prints in the refusal's `{reason}` exactly as any other DDL failure's does, and the raw crash this bullet opened with no longer has a way to happen from either call.

  **What stays residual.** `Alive` asks a point-in-time question, the same shape `pg.ProbeEmptiness` and every lock-and-recheck already accept: a lease terminated in the instant *after* `checkLeaseAlive` returns true and *before* the statement it guards — the marker write, a drop's whole-target recheck, or one table's own lock-and-recheck — actually commits is not caught by that call, only by whichever one comes next. And `Alive` proves nothing about *why* the lock is missing: a lease that lost its lock because its own transaction ended cleanly (a bug elsewhere in this run, not an attacker) reads exactly the same "not alive" this control exists to catch, and is refused the same way — which is the fail-closed direction this file takes throughout, not a gap particular to this control.

- Tests: `TestGateRefusesPopulatedUnanalysedTarget` (a `pg_restore`d fixture with statistics reset), `TestGateAllowsSecondDatabaseOnSameCluster`, `TestGateRefusesTargetAboveTableCap`, `TestGateRefusesRLSTable`, `TestGateRefusesRemoteTargetWithoutFlag`, `TestGateIgnoresUnboundMarker`; `TestARowInsertedAfterTheGateIsNotDropped` and `TestASecondRunIsRefusedWhileAnotherHoldsTheTarget` (`internal/core/race_integration_test.go`) are the two controls above, the first written out of the reviewer's own script and shown to fail — exit 0, row deleted — with the recheck removed; `TestARefusalOnTheSecondTableLeavesTheFirstDropped` and `TestAMarkerDeletedAfterTheGateIsNotTruncated` pin the scope of the rollback and the marked-target branch, and `internal/load`'s unit suite pins the three refusal codes and the 55P03 discrimination. `TestATableCreatedAfterTheGateIsRefused` (`internal/core/race_integration_test.go`, T-0242) is the whole-target recheck's own regression, out of the same instrument; `internal/load`'s `TestARecheckOfTheWholeTargetRefusesATableThePlanDoesNotName`, `TestARecheckOfTheWholeTargetIgnoresAnOccupiedPlanTable` and `TestARecheckOfTheWholeTargetPassesWhenNothingAppeared` pin `recheckWholeTarget` as a unit against a fake target, and `internal/pg`'s own suite covers `ProbeEmptiness`. `internal/load`'s `TestADropRefusesWhenTheLeaseIsLost`, `TestTheWholeTargetRecheckRefusesWhenTheLeaseIsLost`, `TestADropProceedsWhenTheLeaseIsAlive` and `TestNoLeaseConfiguredSkipsTheCheck` pin `checkLeaseAlive` against a programmable fake lease (T-0252); `internal/load`'s `TestAMarkerStatementFailureIsRefusedWithACode` (round-6 review) drives `Load` with `EnsureMarker`'s and `StartRun`'s own statements each failing with a raw 23505 and pins the wrapped `*Refusal`; `internal/load`'s `TestALeaseTerminatedBetweenTheGateAndTheLoadIsRefusedNotRaced` (`lease_integration_test.go`) is the red team's own replay made deterministic — a real lease's backend terminated with `pg_terminate_backend`, a second run loaded into the target in full, and the first run's resumed load asserted refused rather than racing it.

Blocks v1: **yes**.

### T4 Values leave the process: logs, events, the TUI, error text, a masker, the network

Likelihood: medium. Postgres puts the offending row into `PgError.Detail` (`Key (email)=(alice@example.com) already exists`), so an unhandled unique violation prints cleartext into a CI log; verbose logging is on the phase 5 red-team list. Impact: cleartext in a CI log or a pasted ticket.

Controls:
- `event.Event` has no free-form string field; messages are codes plus identifier-only args; `TestNoValueBearingFieldSerialised` asserts that the transitive field types of `event.Event`, `pipeline.Config`, `pipeline.Plan` and `pipeline.Report` exclude `dsn.DSN`, `pipeline.RowBatch` and `pipeline.Table` (and so `Table.Samples`) under the `ref ← event ← pipeline` import graph, and that no code's template references an arg outside the enum (ARCHITECTURE.md §2 "Value-free types", §7).
- `Decision.Reason` is rendered from a template set whose placeholders admit identifiers and counts only; `TestReasonGrammar` parses every emitted reason back. `Schema.Samples` is never serialised by any subcommand, renderer or `--debug` path; `introspect --json` emits counts and fingerprints.
- `PgError.Detail`, `Where` and `Hint` are dropped unless `--show-row-values-in-errors` (ADR-005).
- No runtime-loaded masker exists; the masker is a compiled module we review (ADR-006).
- The binary opens exactly three kinds of connection — the source, the target, and the Docker socket — and spawns exactly two kinds of subprocess — `--password-command`, and `git` for the tracked-file check (T6). There is no telemetry, update check, model call or registry (ADR-007). A test runs the binary under a network namespace that allows only those endpoints, and the subprocess allowlist is a test in `internal/repo` and `internal/discover`.
- `--debug` prints the statement trace, which carries statement shapes with parameters elided, never values.
- **Values we send to the source.** Residual confirmation binds a candidate value as a parameter to a `SELECT EXISTS` on production, and under `log_statement = 'all'` or a slow probe under `log_min_duration_statement` that parameter is written to the source's log file, with the normalised text in `pg_stat_statements`. This is a value-egress path through the source's own logging, not ours. Controls: the indexable equality probe runs first and the case-folded probe only when it is false; probes are capped at 1,000 per run (`--residual-probe-cap`) with the count printed; the README's false-negative list says that confirmation sends candidate values to the source (ARCHITECTURE.md §6 items 3 and 6). The residual is accepted: the alternative is not confirming, which is T12's failure.

**Amendment, 2026-09-15 (the red team's panic-egress finding).** The first control above — "`event.Event` has no free-form string field" — is true and does not cover the **error** egress, which is a free-form string by construction. A panic message is written by whoever panics, and `mask.Apply` does not recover, so a masker (T7's central case) or any library under it — pgx's encoding, the phonenumbers parser, a JSON walker — that panics with the offending input in its message wrote a production value to stderr **at any verbosity**: `internal/core`'s `panicError.Error` formatted the recovered value with `%v`, and `cmd/lazyslice`'s `reportPanic` printed it with `%v` again. The red team registered a masker that panicked with `masker blew up on "victim.canary@bigcorp.com"` and read the address back off stderr with no flags at all.

Both now print a description of the recovered value and never the value: its type, and for an `error` the fact that it is one, through one function (`core.PanicSummary`) so the two cannot drift. The value itself is printed only under `--show-row-values-in-errors`, the flag that already exists for exactly this decision — and **not** under `--debug`, which is a different question: a stack frame carries no row value, so the stack stays behind `--debug` and the value stays behind the values flag. The other half has landed too (**T-0191**), in the module that owns the masker contract: `mask.Apply` recovers, and a panicking generator becomes `mask.ErrMaskerPanic` naming the category, the masker id and the *type* of the panic value. `mask/` is importable on its own (ADR-006), so its contract no longer depends on the parent binary's redaction, and `mask.panicKind` restates `core.PanicSummary`'s rule because that module may not import `internal/`. The same amendment closed the door this one did not check: a masker's message arriving as a **returned error** rather than as a panic. `internal/transform`'s `Refusal.Error()` interpolated it with `%v` and `cmd/lazyslice` printed it at any verbosity, so one string was withheld as a panic and printed as an error; `Refusal.Error()` now names the column, the masker and either the mask module's own refusal (every error that module returns is value-free by construction, so "no masked value fits varchar(8)" is printed rather than swallowed) or, for any other reason, its type alone; the reason's own words are reachable only through `Refusal.ReasonMessage()`, and the message does not advertise `--show-row-values-in-errors` while nothing calls that method. Wiring that method into `renderSafe` — and making redaction there the default rather than an allowlist of two error types — is tracker **T-0212**; `cmd/` was outside T-0191's paths.

Blocks v1: **yes** (event model, reason grammar, `Detail` dropping, no runtime maskers, no outbound calls, probe cap). The network-namespace test is phase 5.

### T5 Secrets in config or logs: a DSN password or the masking key lands in `lazyslice.yml`, events, `--json` or `lazyslice_meta`

Likelihood: medium. Every tool in the category has had a credential in a config file; the key in a committed file makes any guessable value reversible (research/HARD_PROBLEMS.md §2.3). Impact: source credentials or the key in a repository.

Controls:
- `dsn.Ref.String()` redacts; the yml records references (`from: env, var: DATABASE_URL`; `password_command` as the command string), never values; `lazyslice_meta` holds `sha256(host:port/database)[:16]`, `sha256(K)[:8]` and catalog fingerprints only (ARCHITECTURE.md §10, §11.2).
- The key is never in the yml, the target, or an event; the emit stage's writer refuses to serialise a struct field tagged `secret:"true"` and a test asserts every such field.
- **`--where` is operator SQL, and a predicate is exactly where a real value appears** (`email = 'ceo@bigcorp.com'`, `customer_id = 84213`): a value in a `where:` line is A1 in A7 by another route. Emit withholds any predicate containing a string or numeric literal, records `where_fingerprint` instead, and prints that it did; a later run finding a fingerprint and no `--where` is exit 2 asking for the predicate (ARCHITECTURE.md §10).
- `./lazyslice.secret` is created 0600 and appended to `.gitignore` in the same step, or not created at all when it cannot be protected (T6); the tool refuses when the file is tracked by git.
- A discovered password is never persisted without being asked; there is no keyring write in v1 (ADR-004). After a prompted password the run prints the two ways to stop being asked (`~/.pgpass`, `--password-command`), so the remedy is in the transcript.

Blocks v1: **yes**.

**Amendment, 2026-09-16 (the round 2 red team's R2-16).** The `password_command` control above says the command is recorded "as the command string", and that is exactly the hole: `--password-command 'echo Hunter2InCommand'` put the password itself, not a reference to it, into `lazyslice.yml`, whose own header promises the file "never contains a secret". A command such as `echo`, `printf` or `cat` given the value as a literal argument commits it the moment the file is.

`internal/emit`'s `PasswordCommandSuspicious` now screens the command before `Emit` puts it on the `Config` the writer records: it splits the string into shell words without executing anything, and refuses every word after the program name that does not carry a path separator. A bare word is exactly the shape a literal takes once someone writes a secret into the command instead of having the command fetch one; a flag with a value baked in or a bare credential-helper subcommand with no path-shaped argument also fails the test and is screened too — the heuristic is deliberately conservative, because a legitimate command it trips can be passed again on the next run, and a password it lets through would be in a committed file with no second chance. `internal/core`'s `buildConfig` runs the check on the `Config` `Emit` already built (naming the config path is outside `Emit`'s own signature), clears `PasswordCommand` when it is suspicious, and prints `secret.password_command.withheld` naming the file rather than the command. **The command is withheld, not the whole field's existence** — a file with a screened command carries no `password_command:` line at all, the same shape a first run with no `--password-command` has, so a later run cannot tell "never had one" from "had one and it was screened" by reading the file alone; it can only tell from this line in the transcript at the run that screened it.

This does not implement `--password-command` itself: it is accepted, plumbed as far as `internal/emit`, and never executed — nothing in `internal/discover` or `internal/dsn` reads it, so a run that relies on it to authenticate still fails. That gap is unchanged by this amendment and is filed as **T-0213**; shipping the flag as a no-op that also writes a screened placeholder into the yml is still a smaller lie than writing the password, but it is a lie either way, and the row above is owed a note once the flag is either wired or refused outright as unimplemented.

**Amendment, 2026-09-16 (T-0213 closes the gap above, for a named endpoint).** `--password-command` now runs for `--source`/`--target` — or a reference either resolves to from a committed `lazyslice.yml` — named on the command line. `internal/discover`'s `ResolvePassword` is called from `internal/core` for the source and, separately, the target, each time such a connection string is about to be dialled for real — after the precedence's first three sources (a password already in the connection string, `$PGPASSWORD`, `~/.pgpass` — all three read through the one `pgconn.ParseConfig` call the dial itself will make, so this cannot disagree with what the dial sends) have already been checked and none resolved a password, and never before. The command runs through the shell (`/bin/sh -c`, `cmd /C` on Windows) with stdin connected to the null device rather than left open for a prompt the run has no path to answer, and a 30 second timeout of its own — outside the ladder's 1 s dial and 2 s listing budgets, because those are sized for probing *discovered* candidates and `ResolvePassword` at this call site runs only for an endpoint the operator named. Its stderr goes straight to this process's stderr, unmodified, so an operator debugging their own command sees it as it printed it; its stdout is captured, trimmed of exactly one trailing newline (and, on Windows, the `\r` that `cmd /C`'s own CRLF leaves after that), and becomes the password — and stops there. A non-zero exit, the timeout, or empty stdout is a refusal (`secret.password_command.failed`, exit 5) naming only which of those three happened; the command's stdout is read by nothing else in the tree once `ResolvePassword` has taken it, so it cannot reach an event, a log line, a refusal message, `lazyslice.yml` or the trace — the same guarantee the DSN-embedded and `$PGPASSWORD` cases already had, extended to the value this control fetches itself. `TestPasswordCommandSuppliesEndpointPassword` (`internal/discover`, integration) is the positive case: a script that prints a real password, and a passwordless connection string that authenticates once `ResolvePassword` has run it. `TestPasswordCommandOutputReachesNoSink` (`cmd/lazyslice`, integration) is `TestNoCanaryReachesAnOutputSink`'s pattern applied to this value, run twice: once with a canary that fails authentication, for the refusal-text surface, and once with a canary that *is* the role's real password, so the run completes through emit and `lazyslice.yml`, the secret file and every other sink the run wrote are grepped too — the first landing of this test stopped at the failed dial and never reached emit, so the one sink T5 cares most about was never actually checked.

**This amendment did not cover a candidate the ladder itself discovers, and a review of this fix round found that gap** (R2-16's actual report: a committed `lazyslice.yml` plus `--password-command`, with no `--source`/`--target` override, still failed authentication) — `discover.Options` carried no `PasswordCommand` field, `probe` dialled a password-less candidate with none, `pg.Connect` failed authentication, the candidate came back `Reachable: false`, and `chooseSource`/`chooseTarget` skipped it before `internal/core`'s own `ResolvePassword` call was ever reached. **A same-day follow-up fix round closes that half too.** `Options.PasswordCommand` (set by `resolveEndpoints` from `Request.PasswordCommand`, beside `Yes` and `CreateTarget`) is resolved by `probe` itself, once per discovery walk and not once per candidate — a `passwordCache` shared across every candidate the walk probes, so a credential helper that prompts, calls an agent or is merely slow runs at most once no matter how many password-less candidates are on the ladder. The resolution happens before the per-candidate 1 s dial budget's context is created, so the command still gets its own 30 second budget rather than whatever is left of the candidate's second. A resolution failure is warned once, on the same channel the dropped-parameter warnings already use, and falls through to the ordinary no-password refusal on that candidate rather than aborting the walk. `TestDiscoveredCandidateAuthenticatesWithPasswordCommand` (`internal/discover`, integration) drives a real, password-less `$DATABASE_URL` candidate through `Resolve` and proves it authenticates; `TestProbeResolvesPasswordCommandOnceAcrossCandidates` proves the one-invocation guarantee against two candidates sharing a cache.

**Two further findings from the same review, both fixed in the same round.** `runPasswordCommand`'s 30 second timeout was not actually enforced: `exec.CommandContext` kills only the shell it starts, not a grandchild that inherits the captured stdout pipe (a credential helper spawning an agent, or the reviewer's own `sleep 45 &` reproduction), and without `Cmd.WaitDelay`, `c.Run()` waits on that pipe closing rather than on the shell's own exit — measured 45.01s against a refusal that said "timed out after 30s". `WaitDelay` is now set, so the pipe is force-closed about a second after the shell itself exits, whether or not every descendant has. And the trailing-newline trim left a trailing `\r` on Windows, where the command runs through `cmd /C` and `cmd`'s own line ending is CRLF — a script printing the password normally yielded `"pw\r"`, which authenticates nowhere and looks correct in every diagnostic; the trim now removes `\r` as well as `\n`, exactly one trailing line ending and nothing more.

Blocks v1: **yes** for the screen and now for `--password-command` actually running, for both a named endpoint and one the ladder discovers.

### T6 A snapshot, the secret, or a mapping file is committed to git

Likelihood: medium; it is how every "prod dump on the shared drive" begins (CONCEPT.md "The moment they reach for it"). Impact: A4 or A6 in a repository forever.

Controls, implemented in `internal/repo` and specified in ARCHITECTURE.md §9 "The repository", including the three degenerate cases:
- First run appends `lazyslice.secret`, `snapshots/` and every `mapping_file:` path to `.gitignore` when it creates or first reads them, and prints that it did. Outside a git repository the secret is written and the header says it is unprotected. When `.gitignore` is absent or unwritable inside a repository, the secret file is **not created**: the run uses an ephemeral key and prints why, `--require-key` makes that exit 5, and a mapping file in that state is exit 2. Refusing to write beats writing un-ignored.
- The run refuses (exit 2) when `lazyslice.secret` or a mapping file is tracked by git (`git -C <root> ls-files --error-unmatch`), naming the file and the `git rm --cached` command; exit 1 from git means untracked, exit 128 means no repository, and only exit 0 refuses, so the fail-closed check does not fail everywhere. With no `git` on `PATH` the check is skipped and printed; the `.gitignore` entry still protects a never-tracked file.
- lazyslice writes no snapshot file in v1; the target is a database. `snapshots/` is reserved so the rule exists before the feature does.

**Amendment, 2026-09-15 (the red team's A15 and A17).** Both controls above were applied to the *path* rather than to the *file*, and the masking key is A4 — T13's guess-confirmation oracle for every snapshot ever made with it.

- **A symlink took the key out of the repository while the transcript said it was protected.** `os.WriteFile` follows a link, and the `.gitignore` entry and the `git ls-files --error-unmatch` check were both applied to the link path, not to what it resolves to. `ln -s Dropbox/leaked.key lazyslice.secret` before a first run put the key in a cloud-synced folder, mode 0600, with the run printing "added lazyslice.secret to .gitignore" and "wrote a new masking key to ./lazyslice.secret". A secret path that is a symbolic link is now **exit 5** (`secret.refused.symlink`) before `repo.Protect` opens `.gitignore` and before anything is written. It is a refusal rather than a resolve-and-protect: following a link out of the repository would mean silently writing the key to a path the operator did not name, and a repository rule that follows a link out of the repository is not a repository rule. A `--secret-file` pointing straight at a file outside the repository is unaffected — that is an operator naming a location, and the header already says it is unprotected.
- **An existing key file's mode was never checked.** This row promises the file is "created 0600" and nothing re-read one that already existed, so a mode-0644 key on a shared machine or baked into a CI image was readable by every account and the run said nothing. A secret file granting group or other any bit is now **exit 5** (`secret.refused.permissive`) naming the `chmod 600` to run — the same shape as the tracked-by-git refusal. It is not a silent `chmod`: a key that has been world-readable may already have been read, and the operator is the one who knows whether that matters.

Blocks v1: **yes** for the `.gitignore` write, the not-created fallback, and the tracked-file refusal.

**Amendment, 2026-09-16 (the round 2 red team's R2-14 and R2-15).** Both controls in the 2026-09-15 amendment above are also applied to the path rather than to the file, one level deeper than that amendment reached: the direct-symlink check above catches `./lazyslice.secret` itself being a link, and neither of these two is that.

- **A symlinked *parent directory* carried the key out through a component the direct check never looks at.** `mkdir Dropbox && ln -s ../Dropbox cloudkeys` followed by `--secret-file ./cloudkeys/lazyslice.secret` on a first run names a file that does not exist yet, so `os.Lstat` on the file itself returns `ErrNotExist` and both of the direct checks pass — `os.WriteFile` then follows the link in `cloudkeys` and puts the key in the cloud-synced folder, with the transcript saying "added `/cloudkeys/lazyslice.secret` to `.gitignore`" and "wrote a new masking key to `./cloudkeys/lazyslice.secret`". `internal/core`'s `checkSecretParentSymlink` now walks every directory component between the repository root and the secret file with `os.Lstat`, before the direct check runs, and refuses with the same `secret.refused.symlink`/exit 5 the direct case uses. **The walk is bounded to the repository** — it starts at `repo.Root`'s own answer, not the filesystem root, and a path outside a repository (or with no repository above it at all) is not this check's business, the same carve-out the 2026-09-15 amendment already gives a `--secret-file` pointing straight outside one. That boundary is deliberate and not merely convenient: an ambient symlink *above* a repository — `/tmp -> /private/tmp` and `/var -> /private/var` on macOS are both real ones, not hypothetical — is not a path the operator wrote, and resolving from the filesystem root would refuse every run on such a system for a link nobody added. The repository root is exactly the boundary the `.gitignore` entry and the tracked check are already computed against, so it is the one a symlink check has to match too.
- **A hard link gives the key a second name no path check can see, symlinked or not.** `ln lazyslice.secret ../Dropbox/leaked.key` after a key already exists does not touch the path the run reads and writes at all — that path still resolves to exactly the file it always did, with the same mode and the same content — it merely has a second name the repository rule never learned about. `checkSecretFile` now stats the file's link count (`hardLinkCount`, platform-specific: unix reads `Sys().(*syscall.Stat_t).Nlink`, and the check is skipped rather than guessed at on a platform this build does not read a link count on) and refuses above one, with a new code, `secret.refused.hardlink`, at exit 5 — the same shape as `secret.refused.permissive`, and paired with it in the same function for the same reason: both say "this key may already have been read under a name `.gitignore` never protected," and neither is a silent fix, because only the operator knows whether that already happened.

Both are heuristics with a stated edge, not a proof: a *third* hard link made after this run finishes checking is not caught by it, and a network filesystem or container overlay that reports a link count of 1 for a file with more than one name on the host is not caught either. What both close is the case that made A15/A17 measurable — a link created before the run reads the file.

Blocks v1: **yes** for both refusals.

**Amendment, 2026-09-17 (the round 5 red team's still-leaking entry, T-0251).** Step 2's ".gitignore took the entry" was decided by `internal/repo`'s `appendMissing` matching the entry's *text* against the file's lines, never by asking git — so a `.gitignore` that lists `lazyslice.secret` and then negates it (`lazyslice.secret` followed by `!lazyslice.secret`, the ordinary shape of a stale rule someone re-enabled below) let the text search find the entry "present" and report the file protected, while git itself resolves `check-ignore` in the file's own last-match-wins order and would commit the file on `git add -A`. The masking key is A4, T13's guess-confirmation oracle for every snapshot ever made with it, and this let it be written to a path the transcript called protected.

`repo.Protect` now verifies step 2's own claim with git, the way step 4's tracked check already does: after `appendMissing`, with `git` on `PATH`, it runs `git -C <root> check-ignore -v --no-index -- <path>` on the secret file itself. `check-ignore` reports the *last* matching rule, so exit 0 alone still only means "some rule matched" — the `-v` output is read for whether that rule begins with `!`. Only exit 0 with a rule that does not begin with `!` sets `State.GitignoreWritable`, which is `MayWriteSecret`'s one input besides "no repository at all". Exit 1 (not ignored), exit 128 (no repository) and a rule beginning with `!` are each "not verified protected"; so is git being absent from `PATH` at all — the text-match answer is never used as a substitute for a verified one, which corrects the 2026-09-15 and 2026-09-16 amendments' assumption that "the `.gitignore` entry still protects a never-tracked file" whenever git cannot be asked. Every one of those cases falls back to the ephemeral key section 9 step 3 already uses, and to exit 5 under `--require-key`, because refusing to write beats writing un-ignored — the sentence this file already uses for step 3 now also governs step 2's own verification.

This is a question about the *rule* a `.gitignore` states, not about the *path* the 2026-09-15 and 2026-09-16 amendments cover (a symlink, a symlinked parent directory, a hard link): all three of those assume the matched rule actually ignores the file, and this amendment is what checks that assumption before any of them run.

Blocks v1: **yes** for the verified `.gitignore` check.

### T7 A malicious or buggy custom masker

Likelihood: low in v1 because none can be loaded; high the day one can. A masker sees every personal value and can write it anywhere (docs/BUILD_PLAN.md PROMPT 2.5). Impact: a pass-through mode with extra steps.

Controls:
- No `.so`, subprocess, expression language or WASM in v1; maskers are compiled into the `mask` module and registered at build time (ADR-006).
- A masker is a pure function of `(h, value, constraints)`; the transform stage passes it no connection, no file handle and no context.
- The reversal path (a WASM sandbox after three independent requests) requires a row in this table before code.
- A generator that panics or refuses is contained by the module, not by the caller: `mask.Apply` recovers and returns `ErrMaskerPanic`, and every error this module returns names the category and the masker id and never the value.

**Amendment, 2026-09-15 (the red team's round 2, T-0191).** "Malicious or buggy" was read here as "writes the value somewhere", and the controls above all answer that reading: a masker gets no connection, no file handle and no context. What it does get is a **string** — a panic message, an error message — and both were printed verbatim. The red team wrote three maskers against the public module and all three worked: one that returns its input (the cell shipped in cleartext with `Masked: true`, T12), one that panics with the row in its message (the panic crossed the module boundary), and one that *returns* an error quoting the row (`internal/transform` rendered it into `Refusal.Error()` and the binary printed it at any verbosity, with no flag).

Two of the three are closed where the contract is, and the third is contained rather than closed. `mask.Apply` calls a generator behind a recover and a post-condition: a panic becomes `ErrMaskerPanic` naming the category, the masker id and the panic value's type; a generator whose output follows the value it was handed — verbatim, case-folded, re-spaced or re-punctuated — becomes `ErrPassthrough`. The post-condition is not `out != in`, which would refuse the right answer: every generator is a function of `h`, so a masked value that coincides with its own source happens once in the generator's domain and is not a bug, and refusing it would abort a run over an ordinary birthdate or short-id column. So a coincidence is only the trigger: the module then calls the generator a second time under the same `h` with a sentinel input, and refuses only an output that follows that input too. That test asks the masker no question about itself — the earlier draft exempted a generator that declared `Domain(c) == 1`, which a hostile masker simply declares — but it is still a test a determined masker can pass, by recognising the sentinel or by handing the input back in a form the fold does not match. It contains a **buggy** generator; against a **hostile** one the control is the residual scan, and `mask/CLAUDE.md` records the limit. On the error-return side, `internal/transform`'s `Refusal.Error()` renders only the mask module's own value-free refusals and withholds every other reason (see the T4 amendment). None of this makes a runtime-loaded masker safe, and none of it is offered as a reason to allow one: it is the module keeping its own contract for the programs that import it directly (ADR-006).

Blocks v1: **yes** (by absence; the CI grep and ADR-006 keep it absent).

### T8 A half-loaded target that looks complete

Likelihood: medium. Interrupted extracts, a dropped connection mid-COPY, disk full on the target; four tools shipped exit-0 no-ops (research/COMPLAINTS.md TR-15, TR-16, FK-10). Impact: a developer or CI trusts a target that is missing rows, has sequences at 1, or has broken FKs.

Controls:
- One transaction per table; FKs created after data as `NOT VALID` then `VALIDATE CONSTRAINT` per constraint (exit 8 naming the constraint and the cap that caused it).
- `setval(seq, coalesce(max(id), 1), max(id) IS NOT NULL)` after commit, never a literal 0 (research/HARD_PROBLEMS.md §4.1).
- Every `ChildOK` or `ParentOnly` step holds exactly its key count, lookups hold their bounded count, unmasked columns are byte-identical to the source on a sample fetched by identity (a source that changed since the snapshot is reported, not failed), and every failed check is a non-zero exit (ARCHITECTURE.md §6 item 5).
- **After any failure the target is either empty or carries a marker row whose `status` is `running` or `failed`, and the next run truncates it.** That is the property as it is, not as the previous draft wished it: load commits one transaction per table, so a failure at table 5 leaves tables 1 to 4 committed, and under SIGKILL, an OOM kill, a container stop or power loss no cleanup runs and the row stays at `running`. The gate treats a bound marker at `running` exactly as it treats `complete`: truncate and print (ARCHITECTURE.md §11.2). A clean failure additionally rolls back the open table, marks the row `failed` and exits non-zero; SIGINT rolls back and exits 130. A target is never left with some tables loaded and `status = complete`, because `complete` is written last.
- Invariants I1, I5 and I6 in CI, plus `TestKillNineLeavesRunningMarker`: `kill -9` mid-load, then a second run must truncate and complete.

**Amendment, 2026-09-14 (T-0133, docs/reviews/2026-09-09 finding 4).** The bullet above says "complete is written last" and, until this amendment, load.Load itself wrote `status = complete` the moment its own copy finished — before core had run verify at all. A run whose verify then failed (a value the run masked still present in the target, confirmed against the source; an unresolved residual hit; a column the second net still recognises) exited non-zero while the marker it left behind said `complete`, over a target that demonstrably held personal data. `evidence/verify_failure.log` in that review reproduces it: a two-row text column with one email survives to `verify.refused.second_net`, exit 9, target still holding the email, marker at `complete`. "Complete is written last" was true of load's own moment and false of the run's.

Core owns the run's lifecycle now, not load. `load.Load` leaves the row at `StatusRunning` on a load that itself succeeds — it no longer closes the row at all — and `core.Run` closes it once verify has had its say: `StatusComplete` only after verify passes, `StatusFailed` after any verify failure. `internal/pg/marker.go` records why this reused `StatusRunning` rather than adding a fourth status: the gate already treats a bound marker at `running` and at `complete` identically, both authorising truncation, so a run that dies between load returning and core closing the row — kill -9, a crash, core losing the connection — truncates on the next run exactly as a run killed mid-copy already does. `load.Load`'s own failure path is unchanged: a load that fails on its own account (not verify) still closes its own row to `failed`, in the same call, for the same reason it always did — nothing downstream of load runs on that path for core to close the row for.

That still leaves the half of the finding that closing the row correctly does not fix on its own: a `failed` marker is enough to make the *next* run truncate, but it is not the same as the leak being gone *now*. Verify's checks split into two shapes by what a failure means for the rows already sitting in the target. The residual scan, an unconfirmable residual hit, and the second net (ADR-005 exit 9) are all findings about content: each is verify saying a specific value or a specific column, already in the target, is or may be personal data the run was supposed to mask. There, "wait for the next run's gate to truncate it" is a decision to leave a confirmed or suspected leak on disk for an unknown interval, on a target whose whole purpose is to be safer to hand around than the source — worse than the failure the check exists to catch. So on that class of failure specifically, core also drops every table this run loaded (`load.DropLoaded`) before writing the row `failed`: the target ends the run either empty or holding nothing this run wrote, never holding the value verify just found. A foreign-key failure (exit 8) and a row-count or sequence failure (exit 7, found by verify one stage later than load's own) are not that shape: each says the *shape* of the slice is wrong — a reference does not resolve, a count does not match the plan — and says nothing about whether any row in it is unmasked. Dropping the target there would destroy the only evidence an operator has to diagnose why, for no safety gained; those two leave the loaded rows in place, exactly as before this amendment.

`TestKillNineLeavesRunningMarker` needs nothing changed for this: the kill happens inside load, before this amendment's code in core ever runs, and load's own SIGKILL behaviour — the row left at `running`, no cleanup runs at all — is untouched.

**Amendment, 2026-09-15 (the red team's A07).** The amendment above says that on a content-class failure "the target ends the run either empty or holding nothing this run wrote". That was true of **tables** and false of every other object the loader creates: `load.DropLoaded` iterated `ddl.DropTables` and nothing else. The red team put the address in a **domain's `CHECK`** rather than a table's, watched `internal/verify`'s catalog pass refuse the run at exit 9 naming it, watched the quarantine drop the tables — and read the domain, with the address in its definition, straight back out of the target's `pg_constraint`. Rerunning the identical command left it there again, exit 9 every time. The quarantine now drops the sequences and types the run created too (`ddl.ObjectDrops`), after the tables that depend on them and with no `CASCADE`, for the reason `DropObjects` already gives: a type something still depends on after every table this run knows about is gone is something the run has not been told about, and a loud failure naming it beats dropping a stranger's column. Each object is announced before it is dropped (`load.target.quarantine_dropping_object`), because a transcript that named only the tables was the evidence for a promise it was not keeping. What is still owed: verify does not re-read the target to confirm the object it refused over is actually gone before the run returns (tracker **T-0183**).

Blocks v1: **yes**.

### T9 The source is written to, or pinned, by us

Likelihood: low for writes, medium for pinning. pg_sample requires write access and condenser creates a temp database on the source (research/COMPETITORS.md "Orientation"); a held snapshot pins the xmin horizon and a standby cancels after `max_standby_streaming_delay`, default 30 s (research/HARD_PROBLEMS.md §4.3). Impact: bloat or a cancelled run on production; in the worst case a write.

Controls:
- Every source transaction is `REPEATABLE READ READ ONLY`; that transaction is the enforcement. The tracer is the evidence: all five pgx tracers (`QueryTracer`, `CopyFromTracer`, `BatchTracer`, `PrepareTracer`, `ConnectTracer`) are registered on the source pool; a statement whose text does not match a registered shape (the fixed set lazyslice generates: catalog introspection, `TABLESAMPLE` sampling, the `unnest` join shapes, `pg_export_snapshot`, `SET TRANSACTION SNAPSHOT`, the bounded count, the confirmation probes) is refused by returning a cancelled context from `TraceQueryStart` and recorded as a violation that fails the run. One registered shape, `plan.seed_where`, carries a `{where}` placeholder holding the operator's own `--where` predicate; the allowlist bounds only its form (no `;`, `--`, `/*`, `\`, `$`, and parentheses that balance to depth 6), so a balanced predicate may still carry a function call, including one that opens a connection of its own (`dblink`, `postgres_fdw`) that READ ONLY does not reach, or a subquery with an unbounded aggregate; READ ONLY and the operator's own judgement, not the tracer, bound those. Near-miss recorded 2026-09-06: while a cast's type-name continuation was `[a-z]+`, the tracer admitted `SELECT t."a"::int INTO evil FROM ...` (a write); the grammar now refuses it and the READ ONLY transaction was the only thing that would have stopped it. A first-keyword allowlist was rejected because `WITH x AS (DELETE ... RETURNING *) SELECT ...` and `SELECT lo_import(...)` both begin with an allowed keyword. `TestSourceNeverCopiesOrBatches` fails if `internal/pg` ever calls `CopyFrom`, `SendBatch` or `Prepare` on a `Source`. Invariant I4 replays the trace and checks source row counts and a checksum (ADR-005, revised).
- **The discovery dial reads inside the same read-only transaction.** `internal/discover`'s probe opens `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`, runs its three catalog reads, and rolls back; the tracer refuses any statement on a source-mode connection outside a transaction, and the dial reports a broken rail as such rather than as a timeout (T-0081, 2026-09-08).
- **Read-only is set per transaction and never as a session default.** Every statement `internal/pg` sends to the source is inside an explicit `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`, the `system_identifier` read included: it was the one statement in that package on an autocommit path, and it opens a short transaction of its own rather than relying on a session setting (`internal/pg/source.go`). **That guarantee is `internal/pg`'s, not yet the binary's.** One path outside the package is not covered: `internal/discover`'s dial (`internal/discover/probe.go`) opens a source-mode pool through `pg.Connect` and sends its three catalog reads — server version, table count, marker presence — outside any transaction, so it has the dial allowlist and no server-side read-only rail. Those three shapes are fixed literal text with no placeholder, so the allowlist is an exact match and can admit only those three statements; that exact match is their residual control, and it is a weaker layering than this bullet's own near-miss above (`SELECT t."a"::int INTO evil FROM ...` matched a registered shape, and only the transaction refused it) is comfortable with. T-0081 decides it: either the dial opens a read-only transaction of its own, or it records in `probe.go` why three exact-match catalog reads do not need one. Until it closes, read the rail as per statement in `internal/pg` and per shape in the dial. The source pool briefly set `default_transaction_read_only=on` at connect time instead (T-EXTRACT, revised by T-0076). That is session state, and through a transaction-pooling PgBouncer session state is set on the *shared server connection* the pooler assigns, not on anything lazyslice owns; PgBouncer does not run `server_reset_query` in transaction mode by default (`server_reset_query_always = 0`), so the setting outlived the run and left unrelated applications on the same pooler unable to write for up to `server_lifetime` (3600 s by default) — measured, not inferred, in `internal/pg/pooler_integration_test.go`, where a second client's `CREATE TABLE` failed with SQLSTATE 25006. A rail that protects the source by breaking its neighbours is not defence in depth, and it bought nothing the transactions did not already give. It is also not a startup parameter, for the other half of the same reason: a pooler refuses the connection outright for a startup parameter outside its fixed list. The transaction is the enforcement; a pooled run leaves the pooler as it found it, and `TestAPooledRunLeavesThePoolerWritableForOtherClients` is what says so.
- The role's privileges are checked with `has_table_privilege` and printed; a writable role is the loudest header line; `--require-read-only-role` makes it exit 6. Blocking by default was rejected (ADR-005) because it fails CONCEPT.md's headline use case.
- Key lookups join against typed `unnest($1, ..., $k)` arrays in chunks; no temp table is ever created on the source. Lookup detection uses a bounded count (`LIMIT 1001`) gated by `reltuples`, never `count(*)` over a large table, because an unbounded count on a `users` table inside the holder transaction is the xmin pin this row exists to prevent (ARCHITECTURE.md §3). That bound is on lazyslice's own lookup detection only; a `--where` subquery can still run an unbounded aggregate inside the holder transaction, and the plan's printed hold estimate cannot see it.
- The plan prints the estimated snapshot hold; the snapshot is released at the end of extract, before load and verify; residual confirmation uses a new short transaction (ARCHITECTURE.md §6). Standby cancellation is exit 7 with a retry message.
- Pooled endpoints fall back to a single-connection serialised extract rather than extracting without a snapshot.

Blocks v1: **yes** (READ ONLY transactions, tracer, privilege report, snapshot release before verify). The hold estimate is v1; its accuracy is a phase 5 item.

### T10 Supply chain of releases

Likelihood: low per release, certain over the project's life. A one-line unmerged fix ended Snapshot's afterlife (research/POSTMORTEMS.md §8); a compromised release is the category's trust-ending event. Impact: a binary that is not what CI built, or a dependency that phones home.

Controls:
- Tag-triggered goreleaser builds in GitHub Actions with cosign keyless signing and a published SBOM. Release credentials are short-lived wherever a short-lived one exists: `GITHUB_TOKEN` is minted per job and cosign signs keylessly with no stored key. The one exception is `HOMEBREW_TAP_TOKEN`, a scoped PAT with write access to `Liarea/homebrew-tap` held as a repository secret, because publishing the cask crosses a repository boundary and the GitHub App that would mint an installation token does not exist yet. This is the accepted position, not an oversight; reversal condition: the App exists on `Liarea/homebrew-tap` with both secrets set, at which point the tap-token step in .github/workflows/release.yml is restored and the PAT deleted (research/SQLIT_STUDY.md §5.9; amended 2026-09-06).
- Every dependency pinned exactly; `go.sum` verified; `govulncheck` in CI; dependency bumps are their own pull requests with the reason.
- A CI job installs the built artefact on every target and runs `lazyslice --version`; the Homebrew formula pins the checksum.
- `CGO_ENABLED=0` and the no-outbound-call test (T4) mean a compromised dependency has no native code path and no network path to use.
- Agent commits are denied by hook; the orchestrator commits; accepted ADRs cannot be edited (CLAUDE.md; research/AI_PROJECT_PRACTICES.md §4 items 7 and 9).

Blocks v1: signing, pinning and the install job **yes** (Gate 3 requires `brew install` to work); SBOM and `govulncheck` are v1 but not blocking.

### T11 The runaway slice: memory, time, and the plan that lied

Likelihood: high without controls. 200 MB source, 3 GB RSS, OOM (research/COMPLAINTS.md SP-3); "tried to collect data indefinitely" (research/HARD_PROBLEMS.md §1.2); Jailer #126 put other customers' orders in customer 1's slice (a privacy bug, not only a size bug). Impact: an OOM-killed laptop, or a slice containing rows the root does not own.

Controls:
- `CHILD_OK`/`PARENT_ONLY` provenance with a row's mode fixed at first push; children only from `CHILD_OK` rows; per-parent-key cap 100; depth 3 (ARCHITECTURE.md §3).
- Row budget 1,000,000 and memory budget 256 MiB checked during planning; exceeding either is exit 11 naming the table and the flag.
- Bounded channels between extract, transform and load; sorted key sets sized and printed; the residual filter sized and printed.
- The plan and its estimate print before extraction, with `--plan` to stop there.
- Fixtures: no cycles, self-cycle, two-table cycle, overlapping SCC, keyless junction, polymorphic pair, 300-column table, 2M-row table under a memory cap (docs/BUILD_PLAN.md PROMPTS 3.3 and 4.4).

Blocks v1: **yes**.

### T12 The masker passes a value through, and nothing downstream notices

Likelihood: low per masker, certain over sixteen of them. A generator that returns its input on an unhandled type, a canonicaliser that trims to empty and falls into the `''` rule, a JSON walker that skips a leaf kind: each ships cleartext under a column the report calls masked. research/COMPLAINTS.md PII-4 and PII-5 (parallel masking reporting success over cleartext) are this class. Impact: the same as T1, under a green tick that names the column as masked.

Controls:
- Residual scan: every masked cell, and every masked JSON leaf keyed by path, adds `HMAC(runKey, enc(column, path, canonical))` to a Bloom filter at 10⁻⁶; verify tests every masked target value against it and confirms a hit on the source over a short second transaction; a confirmed hit is exit 9 (ARCHITECTURE.md §6 items 1 to 3). This is the one check that tests the masker rather than the classifier, which is why it is its own row.
- A hit that cannot be confirmed — the confirmation channel will not open, the probe errors, the role lacks `SELECT`, or the probe cap is reached with hits untested — is exit 9 naming the reason, never a printed note. A hit the source denies is printed as unconfirmed and counted.
- `mask` module tests per generator: output never equals input for non-empty input; output length is uncorrelated with input length for `free_text`; the colliding-pair encoding fixtures (§5).
- Stated limit, in the README: the filter tests canonical equality, so a value that was truncated, reformatted or embedded in a longer string is not detected.
- **Amendment, 2026-09-15 (the red team's passthrough masker).** The third control above — "output never equals input for non-empty input" — lives **only in the `mask` module's per-generator unit tests**, and this row read as though it were a property of the pipeline. It is not: the red team registered a masker against the public `mask` module that returns its input, and `mask.Apply` returned the source value with `Masked: true` and **no error**, so the residual filter was fed a digest for a cell that was never masked and the only thing between that and a shipped cleartext column was the residual scan, a later stage of a later process phase. The scan would catch it — that is what it is for — but a post-condition inside `Apply` would make this row's control local to the module that owns it, rather than a rule sixteen generators are each separately trusted to keep. It is **not** a bare equality comparison, and it was not written as one: two generators are *meant* to be able to return the input — a masked enum emits a member label, and a collapsed `special_category` emits the first one — so a global guard would refuse the correct answer and fail a closed column at plan or load.

**The post-condition has landed** (**T-0191**). `mask.Apply` compares the generator's output against the input and against the input's canonical form, byte for byte and then over letters and digits only, so a masker that folds the case of an address and hands it back trips it too. A hit is not yet a refusal: every generator is a function of `h`, so one masked value in a generator's domain coincides with its own source by arithmetic — about one distinct value in 9,000 for a `varchar(4)` national id, one in 25,567 for a `date` — and refusing that would stop the run at exit 7 for a masker bug that is not there, deterministically, so no retry would clear it. The module calls the generator a second time under the same `h` with a sentinel input and refuses only an output that follows that input too, with `mask.ErrPassthrough`, naming the category and the masker id and never the value. Nothing on that path canonicalises the output and nothing asks the masker to describe itself: the earlier draft did both, which put the phonenumbers parser on every masked cell and let a masker exempt itself by reporting a domain of 1. One further cell is exempt, and the module decides it rather than asking the masker: a JSON document whose leaves are all empty objects, empty arrays or nulls — `{"tags":[]}`, `{"prefs":{}}` — has no scalar for `semi_structured` to replace, so its masked form is itself and so is the sentinel's. Both halves of the test fire on a cell that proves nothing about the generator, and refusing it would stop a run over an ordinary `jsonb` column deterministically; the document carries no leaf a mask would have removed, and key names survive a mask by design (ARCHITECTURE.md section 6 item 6). A document with a leaf in it is judged like any other value. The stated limit is an output whose letters and digits differ from the source's — a local number handed back in E.164, a date in another layout — which the fold does not see; the residual scan does, and the scan and the per-generator tests remain the pipeline's check on the sixteen generators.

Blocks v1: **yes**.

### T13 The shared masking key is a guess-confirmation oracle held by everyone

Likelihood: certain by construction. Cross-run determinism (ARCHITECTURE.md §5 "Determinism scope") holds only when a team shares `K`; the file is gitignored, so the only distribution paths are a shared secret store or a CI environment variable. `K` plus any snapshot confirms, for every enumerable category (names, emails, phone numbers), whether a guessed real value is present: it is held by N developers and M CI jobs, never expires, and has no rotation trigger on offboarding. Impact: a former team member, or a leaked CI variable, can confirm any guessable customer against every snapshot ever produced with that key.

Controls:
- `K` is production-grade secret material, not a convenience seed, and ADR-004 (revised) says so: it is distributed only through `LAZYSLICE_SECRET` from the team's secret manager or CI secret store, never by copying `lazyslice.secret` between machines; the file is the single-laptop form.
- Rotation trigger: anyone who held `K` leaving the team, or `LAZYSLICE_SECRET` appearing in any log, rotates it; rotation is a new value, old snapshots are regenerated, and `lazyslice_meta` prints `secret changed` on the next run into every marked target.
- The README states the oracle in one sentence beside the pseudonymisation sentence.
- Nothing weakens the oracle in v1: per-entity keys and crypto-shredding are the reversal path if the phase 5 red team demonstrates confirmation at scale, and they are listed in E9.

Blocks v1: **yes** for the ADR-004 text and the README sentence; the rotation runbook is v1 but not blocking.

## Positions this document takes

- **The snapshot preserves production row identifiers.** Surrogate keys and the FK columns that reference them are copied verbatim (ARCHITECTURE.md §4), so anyone with any other reference to a production record — an admin URL, a support ticket, a log line, a payment or CRM record, an analytics replica — re-identifies every masked row exactly, without cryptanalysis and without `K`. The default `--take 500` copies the same lowest-id rows to every laptop on every run. This is the strongest correlation path in the design and the first entry in the README's false-negative list. A keyed remap of surrogate keys is a v2 item (ARCHITECTURE.md §14): it touches every FK, every sequence reset and the reproducibility invariants, and shipping v1 without it is a decision this document records rather than leaves silent.
- **Pseudonymisation, not anonymisation.** Frequency is preserved; quasi-identifiers are not handled; k-anonymity is not promised (research/SYNTHESIS.md §3). A masked column with a small admissible domain is a stable substitution that frequency recovers, and the run names every such column (ARCHITECTURE.md §5).
- **Real email domains are not kept.** Keeping `@bigcorp.com` leaks employer; fakes land in RFC 2606 domains (research/HARD_PROBLEMS.md §2.1).
- **Prefix, length and first character never survive** a mask, free text included (research/HARD_PROBLEMS.md §2.3, the Replibyte first-character transformer). `NULL` and `''` are the two stated exceptions.
- **Erasure requests.** A snapshot is personal data; the README tells users to regenerate snapshots after an erasure request and that rotating `K` makes old snapshots uncorrelatable with new ones.
- **Key compromise** lets the holder confirm guesses against fakes, not decrypt them (T13); rotation is a new value, and old snapshots are regenerated.
- **The read-only source is a checked precondition, not a guarantee** (research/SYNTHESIS.md §1 fact 7). The `READ ONLY` transaction enforces; the tracer proves what we sent; the privilege report says what the role could have done.
- **The target is local** unless a flag names the remote host (T2).
- **What the green tick does not prove** is printed, not buried (ARCHITECTURE.md §6 item 6).
